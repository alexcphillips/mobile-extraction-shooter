# Tech stack and architecture

Status: **confirmed by the user on 2026-10-26.**

## Platform: a mobile web game, not React Native
React Native / Expo Go was considered and rejected:
- Hermes (React Native's JS engine) has no JIT and no WebAssembly, so game logic would run slowly.
- `expo-gl` puts rendering and game logic on one JS thread.
- Expo Go locks you to a fixed SDK and set of native modules.

Mobile Safari has a JIT and WebAssembly, needs no build step and no Apple developer account, and installs from Add to Home Screen. Every iOS browser uses Safari's engine underneath, so Chrome on iOS makes no difference.

## Repo layout (npm workspaces monorepo)
npm, not pnpm (the user's choice, 2026-10-26). Each package lists every dependency it imports, since npm won't catch a package using a dependency that only another package declared.

Tooling (session 1):
- `@mes/shared`, `@mes/client` and `@mes/server` are the package names. `shared` has no build step: it exports its TypeScript source, and Vite and wrangler bundle it.
- TypeScript is **pinned to 6.0.x**, because typescript-eslint doesn't support TypeScript 7 yet. Move to 7 once it does.
- `shared`'s tsconfig leaves out the DOM types, and ESLint blocks imports of three.js, React and the other packages from it, so the "no rendering or UI in the simulation" rule is enforced, not just written down.
- Strict TypeScript, including `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.
- One root ESLint (flat config) + Prettier setup. Vitest runs every package as a project from the root.
```
packages/
  shared/    # game simulation, rules, data schemas. No three.js, React or DOM.
  client/    # Vite app: three.js renderer, React UI, input; includes /editor
  server/    # Cloudflare Worker
content/     # JSON game data: maps, prefabs, items, loot tables, quests, vendors, enemies
docs/
```

## Shared simulation (`packages/shared`)
- Plain TypeScript.
- **Fixed 30 Hz tick:** `step(state, world, inputs)` advances the state **in place** (decided in session 3, so a tick allocates nothing). `FixedTimestep` turns frame times into ticks. The renderer interpolates between ticks, copying the few values it draws before each tick. Look direction is applied to the camera every frame, not every tick, so turning never lags.
- **Serialisable inputs and state.** This is what lets co-op run the same code on the server later. Bit-exact determinism isn't needed (the server is authoritative in co-op).
  - The state (`SimState`) is plain JSON-safe data: entities, the tick count and the RNG state. A test checks that a JSON round trip continues identically.
  - The static map is not in the state. It's a `CollisionWorld`, built once from a plain `WorldDef` (terrain grid, boxes, ramps and ladders) that the map loader produces.
  - Inputs are per entity per tick: the move stick, absolute yaw and pitch, and sprint, crouch and jump. Crouch is the wanted stance, so hold vs. toggle stays a client setting.
  - **Prone and vaulting (2026-10-30):** `PlayerInput.prone` is optional (left out, not prone) and wins over crouch; stance is still just `Character.height` (prone below `crouchHeight`). A vault is its own `MoveMode`, `'vault'`, with the move in `Character.vaulting` (start, end, the top cleared, heights before and after, time in), so it survives a JSON round trip and a resumed raid; snapshots from before simply have no vault in progress. `startVault` (`sim/movement.ts`) finds one from the collision world when jump is pressed on the ground: a ray at knee height, `groundAt` every 10 cm across the top, `overlaps` for the gap (sliding sideways in 2.5 cm steps) and the landing. That's a few dozen grid queries, only on a jump press, and it allocates only when a vault starts. During the move nothing collides and characters aren't separated.
- **Combat (session 6):** `step(state, world, items, inputs)`. The item database (`ItemDb`, every item by id) is static like the world, so it's passed in rather than kept in the state. Each tick everyone moves (then takes fall damage), then everyone's gun updates (so shots see this tick's positions), then bleeding. Inputs gained `fire`, `aim` (both held) and `reload` (a press).
  - Character state gained `health` (HP and bleeding per zone, dead), `helmet` and `bodyArmour` (item and durability), `weapon` (item, rounds, spare rounds, cooldown, reload timer), `aim` (0–1) and the recoil offsets. Session 9 moved armour and guns into `gear` and spare rounds into the inventory (see Inventory model).
  - **Attachments (session 6b):** the weapon state has `attachments` (the item id in each slot, or null). `weaponStats(items, weapon, out)` works out the gun's stats with them into a scratch object, so a tick still allocates nothing. `attach` and `detach` change them (an attachment that doesn't fit throws; check with `fits`). Since session 10c the player changes them only through the `attach` and `detach` inventory actions (see Looting and inventory actions); `createWeapon` and loadouts still call them directly. Shot events carry `loudness` for AI hearing.
  - `state.events` lists what happened during the last tick (`shot`, `damage`, `death`) for effects, hit markers and the HUD. It's cleared each tick; events are the only allocation, and only when something happens.
  - **Hit zones** are six capsules in a fixed layout (`HIT_CAPSULES` in `sim/hit-zones.ts`), turned by yaw and squashed by crouch height. `raycastCharacters` checks each living character's bounding sphere, then its capsules. **No spatial hash for moving things:** with tens of characters, a sphere test each is cheaper than keeping a hash up to date. Revisit if a raid gets past about 100 characters.
- **Seeded RNG** for loot rolls, enemy loadouts, AI decisions, shot spread and bleeding.
- **Collision:** written in-house, no physics engine:
  - A capsule for the player and AI, against rotated boxes, the terrain height grid and stair ramps.
  - **Solids rotate about Y only** (session 3). A standing capsule against a solid is then a circle against a rectangle in XZ plus a height overlap: simple and robust. A tilted primitive in the editor is decorative or gets a Y-only collision box.
  - Ramps are wedges (solid underneath). Stairs are drawn as steps but collide as a ramp.
  - Terrain cells are two triangles split along the diagonal from (i+1, j) to (i, j+1). The renderer must use the same split, or feet float or sink.
  - The character controller is kinematic. It pushes out of walls horizontally (ignoring anything at or below step height), then follows the ground up steps and down slopes, or falls. When landing, it looks for surfaces between the old and new feet, so fast falls don't tunnel through thin floors.
  - A spatial hash (`StaticGrid`, 4 m cells) for the static solids; raycasts walk its cells in order.
  - **Doors (session 11c)** are solids after the boxes and ramps (`WorldDef.doors`, `firstDoor`, `doorOf(solid)`), each with three poses precomputed (closed, open into its +z, open into its −z); `setDoorOpen(door, open, flipped)` copies one in, and the door's grid cells cover all three. A door swings away from whoever opens it: `useDoor` sets `DoorState.flipped` from which side of the doorway they stand, and it's kept while closed so the renderer swings it back from that side. That's the only thing in the world that changes. The truth is `SimState.doors` (`{ open, locked }` by index, the order of `CompiledMap.doors`); `syncDoors(state, world, nav)` brings the world and nav grid in line, at the start of every `step` and once after loading, so a restored state on a fresh world is right. Using a door is `PlayerInput.door` (an index, a press), applied after inventory actions; `useDoor` checks reach (2 m from the doorway or the open slab) and keys, and pushes a `door` event (`opened`, `closed`, `unlocked`, `locked`, `blocked`). Opening snaps; a body it lands on is pushed out by its next move. The renderer eases the swing over 0.2 s (`updateDoors`).
  - Raycasts for hitscan and line of sight, against solids and terrain, with the hit normal. Queries reuse scratch space and allocate nothing.
- **Navigation:** a navigation grid with multiple layers (floors), generated from the map data. It links stairs and slopes, but not ladders. A* pathfinding.
  - **Session 7:** `NavGrid` (`nav/nav-grid.ts`) is built at load from the `CollisionWorld` (about 80 ms and 146k nodes for the 192 m test map on the Mac). It's static like the world and never part of the state. Columns every **0.5 m**; each holds a node for every surface (terrain, or a solid's top) where a standing body fits: no solid in the way from a step's height (0.45 m) to 1.8 m above it, within **0.2 m** (less than the body's 0.35 m radius, so 1 m doorways are always open however the grid lines up; bodies slide along the walls). A surface less than a step under another is dropped (stood on through it). Terrain steeper than 45° isn't walkable. Each node stores a bitmask of links to its 8 neighbours (a neighbour within a step's height; diagonals only if both sides are linked, so no corner cutting). Neighbours are found by looking in the column, not stored. A flood fill numbers the **connected components**, so "can it get there at all" is a lookup; the overlay and the editor's unreachable-spot view (session 17) use it.
  - `findPath` (`nav/path.ts`) is A* with an octile estimate plus climb, on preallocated typed arrays (it allocates nothing but its output). It stops after 20,000 nodes. Between different components it heads greedily for the closest spot it can find, with a smaller budget, and says `partial`. The path is smoothed by walking straight lines cell by cell over links (`straight`), so it only turns where it has to.
  - **Doors (session 11c, see design.md → AI → Doors).** The grid is **built with every door open**, both ways in turn (only spots clear of both slabs are kept, since a door can swing either way), so the open slab is kept clear of and the closed doorway is walkable. It records which links cross each door's closed footprint; `setDoorLocked` clears or restores those link bits (so A*, `straight` and the components all see a locked door without any per-search check), and `updateComponents` renumbers. Closed, unlocked doors stay links: instead of the path follower knowing which links cross a door, an enemy moving along a path opens a closed, unlocked door within 1.2 m that the line to its next waypoint crosses (`openDoorAhead`, called from `updateAi`). **The components lookup is recomputed after an unlock** (decided 2026-10-26): about 11–13 ms for the test map on the Mac (perhaps 15–25 ms on the iPhone), one dropped frame at a rare, deliberate moment. If that hitch shows on the phone: unlocking only ever joins components, never splits them, so relabelling just the smaller side (a key room's few hundred nodes) is enough.
- **AI (session 7):** each enemy is an ordinary `Character` with `ai: AiState` (plain data: awareness, activity, timers, focus, patrol and path as flat number arrays), so the state still saves and restores as JSON. **AI writes a `PlayerInput` for its character**, which moves and shoots through the same code as a player's; an input passed to `step` for that entity overrides it.
  - `step(state, world, items, inputs, nav?)`: after moving, shooting and bleeding, `updateAi` runs, so it perceives this tick's positions and events (shots, hits) and acts next tick. Without a nav grid enemies stand still (tests and the perf scene).
  - Sight and footsteps are checked every 3 ticks, staggered across enemies; shot and hit events every tick. **At most 2 path searches per tick across all enemies**; the rest wait a tick. An enemy plans again when its goal moves more than 1.5 m, or after 1.5 s stuck (and gives up after 3 tries).
  - Bodies push apart after everyone moves (`separateCharacters`, every pair, then out of walls).
  - **Combat (session 8):** `updateAi(state, world, items, nav)` (it needs the items for gun stats). Fighting is more activities in the same state machine (`engage`, `takeCover`, `cover`, `peek`, `hold`, `loiter`), with the extra state in `AiState` as plain numbers, so a save mid-fight restores exactly (tested). The enemy's skill is copied from its type into `AiState.skill` at spawn, so the state doesn't depend on content files. Its aim error wanders as a smooth function of the tick and a phase per enemy, so it needs no RNG per tick.
  - **Cover search** samples 12 random nav nodes within 10 m and keeps the nearest one that's hidden from the threat's eye at crouched-eye height, at its centre and 0.4 m either side (up to 4 raycasts per candidate, and a candidate further than the best so far is skipped before any raycast). **At most 1 cover search per tick across all enemies**, like path searches. Before each shot an enemy casts one ray through the characters to check no ally is in the way, and one through the world to choose chest or head.
  - Reachability is a components lookup (`nav.nearest` for both, then compare), every perception tick while alert. The way up to an unreachable target is the end of a partial path towards it.
- **Schemas:** zod schemas for all content. Every content file has a `formatVersion`, and old versions are upgraded by migrations when loaded.
- **Tests:** Vitest unit tests for rules (damage, armour, inventory placement, loot rolls, migrations).

## Map and prefab format
Decided in session 4. The schemas are in `packages/shared/src/content/schema.ts`, whose comments are the field-by-field reference.
- **Files:** `content/maps/<id>.json` and `content/prefabs/<id>.json`. The `id` inside must match the file name.
- **Loading:** `loadContent(format, json, source)` checks `formatVersion`, runs the migrations from the file's version up to the current one (`migrations[v]` turns v into v + 1), then validates with zod. A file newer than the build is rejected. Objects are **strict**: an unknown field is an error, so typos are caught and a migration must remove fields it renames.
- **Units and conventions:** metres; **angles in degrees** in files (radians everywhere after loading); y up, yaw 0 faces −z. **`pos` is the middle of a shape's base**, so y is where it stands. Sizes are full sizes, not half-extents. Colours are `#rrggbb`.
- **A map** has `environment` (sky colour, fog near and far), `terrain` (origin, cell size, `heights` as rows along +z of corners along +x, one ground colour), optional `water` (level, colour, opacity), optional colour slots, `nodes` and `zones`.
- **Nodes** (in maps and prefabs alike, told apart by `type`):
  - Shapes: `box`, `cylinder` (a `radiusTop` of 0 makes a cone), `ramp` (a wedge rising towards local +z), `stairs` (drawn as steps, collides as a ramp) and `ladder`. All collide unless `collide: false`.
  - **Only boxes and cylinders tilt** (`pitch`, `roll`). Tilting turns them about their centre, and they collide as their upright bounding box (solids rotate about Y only, see Collision).
  - `prefab`: a reference by id, with a position, a yaw (no tilt) and colour overrides. Prefabs can contain prefabs; a prefab that contains itself is an error.
  - `door`: width, height, hinge side, optional key item, starts open or closed.
  - Markers: `playerSpawn`, `enemySpawn` (enemy type, loadout, loot weight multipliers, optional `patrol`), `lootContainer` (container type, loot table), `lootSpawn` (loot table, optional `chance`), `extraction` (name, radius) and `questMarker` (id required). Enemy types, loadouts, loot tables and keys are plain ids for now; they're checked against their own files once those exist.
  - `patrol` (session 7): a required `id`; `points` (at least 2, in the enclosing frame), each either a plain `[x, y, z]` to walk through or a stop `{ pos, wait, radius }` (wait defaults to 3 s, radius to 0); `repeatFrom` (default 0: the points before it are the way in, walked once; at least two must repeat); and `loop` (default true; false walks back and forth over the repeating points). An `enemySpawn`'s `patrol` names a patrol **beside it** (in the same map or prefab), so a prefab can carry its own guard and route; it compiles to the patrol's path id, and a missing one is an error. `enemySpawn.radius` spawns at a random clear spot within it. `CompiledMap.patrols` has them in world space, every point as `{ x, y, z, wait, radius }` (walk-through points have 0 and 0).
- **Format 2** (session 7) added patrols, for maps and prefabs alike; 1 → 2 changes nothing.
- **Named zones** are polygons in x, z, at map level only.
- **Colour slots (recolouring):** a prefab declares slots with default colours (`"colours": { "paint": "#c0392b" }`), and its shapes use either a hex colour or a slot name. A placement overrides slots, and an override can name a slot of the enclosing prefab or map. Overriding a slot the prefab doesn't have is an error.
- **Ids:** any node can have an `id`, unique among its siblings. Markers and doors come out of compilation with **path ids**, the ids from the map down joined by `/` (for example `house-a/desk`); a node without an id is `#` and its index. Anything other content refers to (quest markers, keyed doors) should have an explicit id.
- **Compilation:** `compileMap(map, prefabs)` (in shared, so the server can use it for co-op) flattens everything into a `CompiledMap`: the `WorldDef` for collision, world-space shapes to draw, instanced groups, doors, markers and zones.
- **Buildings (session 16):** a prefab's optional `building` (`size` as width and depth, optional `centre`, optional base `colour`, a hex colour or slot) makes it a building whose floor is its y = 0. `compileMap` gives each placed building a **concrete base** (`concreteBase`): a box under the footprint from the floor down to 0.3 m below the lowest ground under it (`groundUnder` samples every half metre or less), drawn and collided with like any box; none if the ground is nowhere below the floor. `CompiledMap.buildings` has the footprints in world space. The format stayed 3, the field being optional.
- Deferred: per-cell terrain colours (roads, dirt) and scaled prefab placements. Both can be added later with a migration.


## Enemy types and loadouts
Session 8. The schemas are in `packages/shared/src/content/enemies.ts`, whose comments are the field-by-field reference. Loaded like items (`formatVersion` 1, strict zod objects, the id must match the file name).
- **`content/enemies/<id>.json`:** `name`, `loadout` (the default loadout id) and `skill` (`reaction` s, `aimError` and `aimSettled` degrees, `aimSettle` s, `holdChance` 0–1).
- **`content/loadouts/<id>.json`:** `weapons` (at least one: `weight`, `item`, `spare` as `[min, max]` rounds, optional `attachments` as `{ item, chance }` where the first to roll in a slot wins), and optional `helmets` and `bodyArmour` (`weight`, `item` or `null` for none, optional `condition` as a `[min, max]` fraction of full durability). Each part is picked by weight on its own.
- `checkEnemies` checks the references (loadouts exist, items are the right type and slot, attachments fit their gun); the client checks each map's enemy spawns name a type and loadout that exist. Both run in the client's content test.
- `equipLoadout(c, items, loadout, rng)` (`sim/loadout.ts`) rolls one onto a character, using the sim's RNG so a raid's rolls come from its seed.
- **Enemy loot (session 11):** an enemy type's optional `loot` is `rolls` (`[min, max]` items) and `tables` (loot table id → weight). Each item picks a table by its weight times the spawn's `lootWeights` for it (1 if not given; a weight of 0 turns a table off), then one item from it. The format stays 1, since the field is optional.
- The client's content test also checks that every locked door's `key` is a key item.

## Loot tables and raid configs
Session 11. Loaded like the other content (`formatVersion` 1, strict zod objects, the id must match the file name).
- **`content/loot-tables/<id>.json`** (`content/loot-tables.ts`): `name`, `rolls` (`[min, max]` items for a container) and `items`, each `{ item, weight, count? }` where `count` is a `[min, max]` only for items that stack. `checkLootTables` checks the items exist and counts stay within a stack; `checkEnemyLoot` checks enemy types name tables that exist. The client checks every `lootContainer` and `lootSpawn` marker and every spawn's `lootWeights` names a table.
- **Rolling** (`sim/loot-roll.ts`): `fillLootContainers` fills the containers `placeLootContainers` placed, and `rollEnemyLoot` stows an enemy's loot in its pockets, rig and backpack after its loadout. Both use the sim's RNG, so a seed gives the same loot. A rolled item is a new one (`createItem`): a gun comes with a full magazine and no attachments. What doesn't fit is left out. `byWeight` moved to `rng.ts` for loadouts and loot alike.
- **Loose spawns (session 11b):** `rollLootSpawns` puts one item from each `lootSpawn` marker's table on the ground (`SimState.ground`), if the marker's optional `chance` (0–1, default 1) rolls. The map format stays 2, since the field is optional.
- **`lootSpawn.oneOf`** (2026-10-30): an optional id naming a set of spots; `rollLootSpawns` first picks one spot per set with the raid's RNG (in marker order, so a seed gives the same pick), then rolls only that one's chance. Names are map-wide, not scoped by prefab. The format stays 3, the field being optional. The map editor shows it as "one of".
- Quest items (session 14b) are put on the ground by `startQuests` (see Quests), not by loot tables.
- Not yet: named zones weighting loot.
- **`content/raids/<id>.json`** (`content/raids.ts`): `name`, `map`, and `duration` in seconds (15 minutes if left out). Every player spawn and extraction point in the map is used. It will grow a playable area, loadout rules, objectives and open extractions for weekly challenges.

## Raid lifecycle
Session 11, `sim/raid.ts`. See design.md → Raids and maps → Extraction.
- `SimState.raid` (`RaidState`: the tick the timer runs out on, and the extraction points from the map's markers) is set by `startRaid`, and null outside a raid (tests, the perf scene), where nothing below happens. `Character.extracting` counts the seconds a player has stood in an extraction point (within its radius across, and `RAID.extractHeight` up or down).
- `updateRaid` runs last in `step`, after the tick count goes up. A living player who reaches `RAID.extractTime` (7 s) leaves; when the timer runs out, every living player still in the raid leaves as missing in action. **A player who leaves is taken out of `state.entities`** and kept in `state.left` (`LeftRaid`: the character with all its gear, how, where, and the tick), with a `leave` event. So nothing can shoot or follow them, and enemies who were after them calm down (they already handle a target that no longer exists). Enemies never leave. The dead stay in `entities` as bodies.
- `gearItems(gear)` lists everything a character carries; `keptItems(gear, survived)` is what a player keeps (everything after extracting; otherwise the knife and the vault). Session 12's raid end will send these.

## Item format
Started in session 6 with what combat needs; session 6b added attachments (format 2), session 9 the rest of the item types and grid sizes (format 3), and session 10b draw times and the knife's stats (format 4). The schema is `packages/shared/src/content/items.ts`, whose comments are the field-by-field reference.
- **Files:** `content/items/<id>.json`, one item each, loaded like maps (`formatVersion`, migrations, strict zod objects). The `type` field picks the kind: `weapon`, `ammo`, `armour`, `attachment`, `med`, `container`, `melee`, `key`, `quest`, `loot` or `repair`.
- **Every item** has `size`, `[width, height]` in grid cells, unrotated. Only `ammo` (required) and `loot` (optional) have `stack`, the most in one cell.
- Format 2 → 3 (session 9) guesses a size from the type (rifle-held guns 4×2, pistols 2×1, helmets 2×2, body armour 3×3, anything else 1×1) and gives ammo a stack of 60.
- **med:** `effect` (`bandage`, `splint`, `surgery` or `heal`), `useTime`, `uses` (default 1; not for heal) and, for heal only, `hp` (its pool). One effect per item keeps the heal button's choice simple.
- **container:** `slot` (`rig` or `backpack`) and `grid`, the size inside. **key:** optional `uses` (session 11c; an item instance keeps what's left in `left`, like meds); no format change, as it's optional. **quest** and **loot** have nothing else yet.
- **melee** (the knife, format 4): `damage`, `level` and `armourDamage` (format 9, as for ammo), `bleedChance`, `swingTime` (seconds between swings), `reach` (metres from the eye) and `drawTime`.
- Format 3 → 4 (session 10b) gives weapons a `drawTime` by hold (pistol 0.4 s, otherwise 0.8 s) and melee items the knife's first-guess stats. **repair:** `points`, the durability it can restore in all (used from session 13).
- **Format 4 → 5 (session 13b):** every item has a **`value`** (whole money, 0 or more: what vendors sell it for; see design.md → Economy); **loot** may have **`money: true`** (cash: deposited at full value); **repair** gained **`useTime`** (seconds, in a raid). The migration guesses a value by type and gives repair kits 8 s; the content files set their own.
- **Sounds (format 7, session 19):** `weapon` has `sounds: { shot, suppressed, reload }`, `melee` `{ swing }`, `med` and `repair` `{ use }`, each a sound file's id (`content/sounds/`). `defaultSounds` gives the first ones by hold or effect; format 6 → 7 uses it, as do blank and test items. `checkSounds` (`content/sounds.ts`) checks every sound an item names exists, and every sound the game plays itself (`GAME_SOUNDS`, client `audio/sound-ids.ts`); `loadSounds` runs it, and so does the item editor's `itemContentProblem`. The server doesn't load sounds. The content files were rewritten at format 7, except `assault-rifle.json`, which had the user's uncommitted edits (the migration gives it the same sounds); it was brought up to format 8 with the rarities, its sounds written in and its model edits left as they were.
- **Rarity (format 8):** every item has `rarity`: `common`, `rare`, `epic` or `legendary` (`RARITIES`), after `value` in the files. Format 7 → 8 makes them all common; blank items start common. The client colours tiles by it (`colourOf` in `ui/raid-screen.tsx`, also the vendors page and the item editor's swatches); the item editor has a picker. Nothing else reads it yet (loot tables and prices could later).
- **Levels (format 9, 2026-10-30; design.md → Ammo and armour levels):** `ammo` has **`calibre`** (any string; guns fire every round of their own round's calibre) and **`level`** (1–`LEVELS`, 6), and `armourDamage` is now required and means **durability per hit** (per pellet). `armour` has **`level`** in place of `absorb`. `melee` has `level` and `armourDamage`. Format 8 → 9 makes each old round its own calibre at level 1 with armour damage ×10, guesses armour's level from `absorb` (×6, rounded), and gives knives level 1 and armour damage 5. `calibreOf` and `firesRound` (`content/items.ts`) answer which guns fire what. The hit itself is `shootCharacter` with `ARMOUR`, `throughArmour` and `armourWear` (`sim/health.ts`). Every item file was bumped by its version line only, so the diffs stay small; the rounds, armour and knife were rewritten.
  - **The round in a gun** is `Item.loaded` (an ammo id of its calibre), left out while it's the gun's own round, so saved guns stay valid. `WeaponState.reloadWith` is the round a reload in progress loads (`restGear` clears it). `loadedAmmo(items, gun)` reads it; `reloadRound(c, items, w, want?)` picks what a reload loads (the round asked for if carried, else the one loaded, else the highest level carried; no allocation). A reload of another round swaps: new rounds are taken first, then the old ones stowed, or dropped with no room. `PlayerInput.ammo` asks for a round with `reload`. Everything that counted a gun's rounds as `WeaponDef.ammo` (unload, magazine changes, sell price, `countItems`) uses `loadedAmmo`, and `checkProfile` refuses a `loaded` round the gun doesn't fire.
  - **Loading by drag:** the inventory action `{ type: 'load', gun, from }`. `loadKind(state, c, items, gun, from, instant)` (`sim/looting.ts`) says what it would do: `'reload'` onto the gun in hand in a raid (sets `reloading` and `reloadWith`, so `finishReload` takes the rounds from what's carried), `'load'` at once elsewhere, or null; `loadGun` does it. The stash calls `loadGun` with `instant` true. The client's `gunZone` gives rounds a `load` drop zone on any `data-gun` element and asks `loadKind` whether it's green, so the outline and the sim agree.
  - **Loadouts** may list `ammo` per weapon (`[{ weight, item }]`): the round it's loaded with and carries spares of; `checkEnemies` checks the gun fires each. AI reloads whenever `reloadRound` finds anything, so an enemy out of its own round switches to another it carries.
  - Client: `ui/levels.ts` (the level colours, `levelOf`), a level tag on ammo and armour tiles, the ammo readout's round name with its level colour, and the reload button's long press (Shift+R) opening `HandsHud.showAmmoPicker`. The item editor has calibre and level fields, lists the guns that fire a round, and warns that a changed calibre can break saved guns.
- Not in item files yet: icons for the inventory screen (tiles are coloured by type). Icons drawn from the models were left out of session 18b: rendering them on the phone at startup is its own problem.
- **weapon:** `ammo`, the round it comes loaded with (it fires any round of that calibre), `fireMode` (`auto` or `semi`), `rpm`, `magazine`, `reloadTime`, `aimTime`, `drawTime` (format 4), `range`, `loudness` (hearing radius in metres), `slots` (any of `optic`, `muzzle`, `magazine`), `hipSpread` and `aimSpread` (degrees), and `recoil` (`up`, `side`, `recovery` in degrees per second).
- **attachment:** `slot`, optional `weapons` (the guns it fits; otherwise every gun with the slot), optional `mods` (multipliers `spread`, `recoil`, `aimTime`, `reloadTime`, `loudness`, and `magazine` as extra rounds), and for optics only `optic`: `zoom` (1 is a red dot, above 1 a scope) and `reticle` (`colour` and `shapes`: `dot`, `line` and `ring`, in % of the screen height from the aim point, y down; the scope mask's radius is `SCOPE_RADIUS`, 46).
- Format 1 → 2 (session 6b) gave weapons `loudness: 150`; slots are optional.
- **ammo:** `calibre` and `level` (format 9), `damage` (to the chest; zones multiply it), `armourDamage` (durability lost per hit; until format 9, per point absorbed), `bleedChance`. Optional `pellets` (2 or more) and `pelletSpread` (degrees), always together, for shotgun shells (2026-10-30): one round fires that many pellets, each straying up to `pelletSpread` from the shot's line and each its own hit for `damage`. They were added without a format bump, since every older file is still valid. Each pellet is its own `shot` event, numbered by `pellet`; the client plays the sound, muzzle flash and whizz only for pellet 0, and one hit-marker sound per tick.
- **armour:** `slot` (`helmet` or `body`), `level` (format 9; `absorb`, 0–1, before), `durability`.
- `checkItems` checks references between items (a weapon's ammo exists and is ammo; an attachment's guns exist and have its slot); the client's content test runs it.
- **Models (format 6, session 18b; `content/models.ts`, whose comments are the reference):** **every item has a `model`**: `parts`, each a `box`, `cylinder` (cone with `radiusTop` 0) or `wedge` with `pos` (its **centre**, unlike map shapes, whose pos is the base), `size` or `radius`/`height`/`sides`, optional `yaw`/`pitch`/`roll` in degrees (order YXZ, about the centre) and a `#rrggbb` `colour`. Metres, y up.
  - **Frames:** guns, attachments, knives and loose items are modelled with the barrel or blade along −z; a gun's origin sits on the body's weapon bone, an attachment's origin goes on the gun's mount. **Worn gear** (armour, rigs, backpacks) is modelled **on the body as it stands**: feet at 0, facing −z, 1.8 m tall; the client moves it into the rig's rest frame (`CharacterTemplate.rest`).
  - **Points:** a weapon has `grip` and `support` (the hands), `muzzle` (shots leave there with nothing fitted), `sight` (the irons: aiming lines the eye up with it) and `mounts`, one per slot it has and no others. An optic has `sight` and a muzzle device `muzzle`, both from its origin; nothing else may. A melee item has `grip`. A gun's part may say **`hiddenBy`** a slot it has: it isn't drawn while something is fitted there (irons under an optic, the standard magazine when another is fitted).
  - Format 5 → 6 gives each item **the placeholder it was drawn with** (`placeholder-models.ts`: by hold, zoom, quieter or not, slot), keeping only the mounts and hidden parts of the gun's slots; anything never drawn gets a box the size of its grid in its type's colour, as it looked on the ground. The content files were rewritten at format 6 and the 9 mm magazine given the pistol's short extension by hand (the migration can't tell which gun a magazine is for). Blank items in the editor start from the same placeholders.

Session 14. Rules in shared `quests.ts`, content in `content/quests.ts`. See design.md → Quests and vendors.

Bundled for the server too.

The sim's `startQuests(state, map, items, holder, objectives)` (`sim/raid.ts`, after `startRaid`) adds `RaidState.investigate` (`InvestigateSpot`: holder, marker, position, `done`) and puts each quest item on the ground at a spot picked with the raid's RNG. A missing marker throws.

The server's `/end` runs `raidProgress(profile, quests, items, map, investigated, keptGear)` after `checkGear`: investigate objectives on the raid's map count whatever the outcome; `takeQuestItems` takes every quest item out of the kept gear (every grid, nested too) and those an active extract objective wants count. Quest routes are refused in a raid, so quests active at the end were active at the start: no snapshot is needed. The client runs `raidProgress` on copies for the results screen.

## Vendors and money
Session 13b. Rules in shared `vendors.ts`, content in `content/vendors.ts`. See design.md → Quests and vendors → Economy.
- **`content/vendors/<id>.json`** (format 1): `name`, optional `blurb`, and `sells`, a list of `{ item, count? }` (count for stacks, one purchase's worth). `checkVendors` checks the items exist, have a value, aren't money, and fit one stack. Bundled for the server too.
- **Prices:** `buyPrice(items, offer)` is value × count; `sellPrice(items, item)` is `floor(value × VENDOR.sellShare × condition(item))` per item, plus a gun's attachments and loaded rounds, or the full value for money (`isMoney`). `cantSell` refuses a rig or backpack with anything in it and anything worth nothing.
- **`buyOffer(profile, items, vendor, index, page)`** puts a new item into copies of the stash pages (page first, then the others) and keeps them only if all of it fit; **`sellItem(profile, items, ref)`** takes an item out by a ref as the stash screen sees it (`stashGridOf` resolves the profile's grids and pages), refusing the knife. **`depositInto(profile, items)`** takes the money out of the gear's grids into the balance (capped at `PROFILE.maxMoney`).
- **Server** (`server/src/vendors.ts`): `POST /api/vendors/:id/buy` (`BuyRequest`: `version`, `offer` index, optional `page`) and `POST /api/vendors/sell` (`SellRequest`: `version`, `from`, a list of up to `MAX_SELL` (200) `ItemRef`s checked for shape; `sellItems` finds them all first and removes them by the item, not the index, all or none), each with the version read, refused in a raid, like buying a stash page. Raid ends (`/end`, and missing in action at start or `/abandon`) call `depositInto` after `keptGear`. `PUT /api/profile` also refuses `overRepaired`.
- **Client:** `StashSaver.buy` and `sell` (and `buyPage`) share `post`, which saves first and builds the body after, so it names the saved version; the stash reopens on the reply, on the page shown. `ui/vendors-page.tsx` is the vendors page; selling is `InventoryContext.sell`, set only between raids.
- **Repairs** (`sim/repair.ts`: `repairable`, `repairArmour`, `kitUsedUp`): the inventory action `{ type: 'repair', kit, armour }`. In a raid, `applyInventory` starts it as a `MedUse` with `armour` set (the kit must be in a carried grid; `ownItem` resolves your own refs), and `updateMedUse` finishes it (`finishRepair`) instead of `useMed`. `timeToUse` gives a med's or kit's use time, for the heal button's ring. `applyStash` does it at once with the kit and armour anywhere. Armour items carry `data-armour` (like `data-gun`), and the drag host's `armourZone` makes a `repair` drop zone when a kit is dragged over one.
- **Using from the inventory:** `InventoryContext.use` (a raid only) sets the next tick's `input.use`, as the heal button's picker does: a `MedRef` from **Use**, or `'cancel'` from the top bar's use pill. The raid screen redraws every 3 ticks while something is in use (otherwise every 10). Selling several is the controller's `selling` list (`startSelling`, `canPick`, `picked`); taps toggle picks and `canDrop` refuses everything meanwhile.

## Inventory model
Session 9. All in `packages/shared`, plain JSON-safe data like the rest of the state, so a co-op server can run it and the stash (session 13) reuses it.
- **`Item`** (`inventory/grid.ts`): one item or a stack wherever it is: `item` (the definition's id) and `count`, plus whatever its type needs: `durability` (armour), `left` (uses or HP left in a med, points in a repair kit), `mag` and `attachments` (guns), `grid` (rigs and backpacks). The sim's narrower types are Items with those fields required: `WeaponState` (which also keeps the reload and fire timers), `ArmourState`, `ContainerState`. So an item moves between a slot and a grid as the same object, with no conversion. `createItem` (`sim/create-item.ts`) makes a new one with the fields its type needs.
- **No item instance ids.** An item is found by its grid and index (or its gear slot). Nothing needs a lasting id yet: the heal button picks by state, not by a bound item. Add ids if co-op looting needs them.
- **`Grid`**: `w`, `h`, `containers` (whether rigs and backpacks may go in: true only for the stash and loot containers) and `items`, each with `x`, `y` (top left) and `rotated`. There's no occupancy array; overlap is checked against the item list, which is short. Operations: `findSpot`, `placeAt`, `addItem` (auto-placement with stacking), `dropAt` (drag and drop, merging stacks), `rotateAt`, `transfer` (double-tap), `countOf`, `takeFrom`, `removeAt`.
- **`Gear`** (`sim/gear.ts`) is `Character.gear`: `primary1`, `primary2`, `sidearm`, `knife`, `helmet`, `bodyArmour`, `rig`, `backpack`, `pockets` (4×1) and `vault` (2×3, null for enemies), and `hand` (which gun slot or the knife is out). **`heldWeapon(c)` is the gun in hand**; there's no separate `weapon` field, which would turn into a second copy after a JSON round trip. `equip` and `unequip` check what fits each slot; `switchHand` puts the gun away (its reload stops). `carriedGrid(gear, i)` walks pockets, rig and backpack by index, so `carriedAmmo` and `takeAmmo` (reloading) allocate nothing.
- **`attach` and `detach` return the rounds that no longer fit** the gun (a smaller magazine) for the caller to `stow`.
- **Meds** (`sim/meds.ts`): `treatments(c, items)` lists what the heal button offers, best first, as `MedRef`s (grid, index and item id); `useMed` applies one use. `Health` gained `splinted` per zone; `isBroken` is false for a splinted limb, but `dealDamage` still spills over from any limb at 0 HP.
- **Loadouts** gained optional `rigs` and `backpacks` (worn empty; since session 11 the enemy type's loot goes in them). A rolled gun goes in the sidearm slot if it's a pistol, otherwise the first primary, and the spare rounds are stowed (pockets, then rig, then backpack; what doesn't fit is left out). The format stays 1, since the new fields are optional.

## Hands, meds and the knife
Session 10b, in `shared` like the rest of the rules.
- **State:** `Character` gained `draw` (seconds left drawing what's in hand), `swing` (seconds until the knife can swing again) and `using` (`MedUse`: the med's grid, index and item id, and the seconds left, or null; since 13b also a repair kit's, with the `armour` ref). All plain numbers, so a save mid-heal or mid-draw restores exactly (tested).
- **Inputs:** `PlayerInput` gained optional presses `draw` (a hand slot) and `use` (a `MedRef` to start, or `'cancel'`). Optional, so AI inputs and tests don't change; enemies never switch or heal.
- **Tick order:** inventory actions, then for everyone the draw timer, a `draw` press (`switchHand(c, items, hand)`, which takes `drawTime`), and `updateMedUse` (start or cancel, the cancelling conditions, the timer, then `useMed`); then movement (capped at `MOVEMENT.useSpeed` while using, ×`knifeSpeed` with the knife out); then each character's gun (`updateWeapon`: no firing, aiming or reloading until drawn; no aiming while using) and knife (`updateMelee`).
- `equip` into the slot in hand starts a draw too (a gun dropped into your hands from the inventory). `giveWeapon` leaves it ready, for spawning.
- **The knife** (`sim/melee.ts`): a swing casts up to five rays from the eye (the look with recoil, then `MELEE.fan` up, down, left and right), each against the world and then characters within reach; the first that reaches a body part wins. It hurts through `shootCharacter`, which now takes a `Wound` (the damage, armour damage and bleed chance that ammo and melee items share) and a cause (`shot` or `melee`). A `swing` event (hit or miss, and where) drives the slash animations and impact puffs; there's no loudness, so AI hears nothing.

## Looting and inventory actions
Session 10. `sim/looting.ts` in `shared`.
- **Loot containers** are `SimState.loot`: each has its marker's path id, its kind (`content/loot-containers/<id>.json`: `name` and `grid`, format 1), its position and a grid that takes rigs and backpacks. `placeLootContainers` makes them from a compiled map. Dead bodies aren't copied anywhere: you loot their `gear`.
- **Inventory actions** go in `PlayerInput.inventory` and are applied at the start of `step`, before movement, each giving an `inventory` event with `ok`. So a co-op server can apply them in the same place, and the raid doesn't have to pause. An action names an `Owner` (`self`, a `body` by entity id, or a `container` by id), then a grid (`pockets`, `rig`, `backpack`, `vault`, or a container's `loot`) and index, or a gear slot, **plus the item id the sender saw**, so an action that has gone stale fails instead of moving the wrong thing. Reach (`LOOT_REACH`, 2 m across and up or down) and "the body is dead" are checked by the sim, not the UI.
- The client keeps one array of pending actions as the player's `inventory` input and empties it after each tick, so ticks allocate nothing.
- **Attachments (session 10c):** `attach` (`gun`, `from`: a loose attachment in a grid, or a `PartRef` (`gun`, `slot`, `part`) for one on another gun) and `detach` (`gun`, `slot`, `part`: the attachment id the sender saw, `to`: a `GridSpot` or null for what you carry). The gun can be anywhere you can reach: your slots or grids, a body's, a container's. A loose attachment is a plain `Item` made with `createItem`; on the gun it's only its id in `attachments`. When `attach` replaces a part, the old one goes where the new one was (same cell, either way round), else anywhere in that grid, else into what you carry. Rounds a smaller magazine hands back go into **the acting player's** carried grids, never the vault. From another gun (`movePart`), the second gun's old part goes onto the first if it fits there, else into what you carry, and both guns' handed-back rounds are checked together. Since session 11b, what has nowhere to go (the rounds, a displaced part, a part taken off into what you carry) is **dropped at the player's feet** instead of the action being refused, so `roomForRounds` and the undo are gone. Allocating here is fine: it's once per action, not per tick.
- **Items on the ground (session 11b, `sim/ground.ts`):** `SimState.ground` is a list of `GroundItem`s (the `Item`, its position and a yaw for drawing), plain data like the rest. The ground is an `Owner` (`{ kind: 'ground' }`); an item on it is an `OnGround` ref (its index in the list, plus the item id the sender saw, like grids), and a `Target` can be `{ owner: { kind: 'ground' } }`. So the existing actions cover it: `quick` from the ground to `self` picks up (the use button sends this), `quick` or `move` to the ground drops, and `move` from the ground to a gear slot swaps, leaving the old item where the new one lay. Each ground item must be within `LOOT_REACH` (`groundInReach`). `dropItem(state, c, item, world?)` places a drop 0.9 m ahead (or at the feet if a raycast at knee height finds a wall), scattered with the sim's RNG, on `world.groundAt` below; so `applyInventory` takes the world as an optional last argument, and `step` passes it.

## Client (`packages/client`)
- **Build tool:** Vite + TypeScript.
- **3D rendering:** plain three.js, not React Three Fiber, so the game loop and rendering stay outside React.
  - Static map geometry is **merged per chunk** (32 m): one mesh per chunk holding its terrain and every shape whose centre is in it.
  - **Instancing is opt-in per prefab** (`"instanced": true`, session 4), for small props placed many times, like trees and crates. Each instanced prefab and colour set becomes one `InstancedMesh` for the whole map. Merging is the default because it costs no extra draw calls; instancing saves memory and load time but adds one draw call per group, and a group is culled as a whole.
  - Colour is stored per vertex, with each face direction shaded differently; materials are unlit (`MeshBasicMaterial`); distance fog. Static geometry has the shading baked into its colours. Instanced and moving geometry (doors now, characters later) uses `shadedMaterial()`, which applies the same shading on the GPU from the world-space normal, so it stays right as the object turns.
  - Each door is its own mesh, pivoted at its hinge, so it can swing open.
  - Content is bundled into the client with `import.meta.glob`; in dev, saving a content file reloads the page.
  - The camera's far plane follows the fog distance.
  - **The first-person gun is drawn in a second pass** after the world, with the depth buffer cleared, so it never pokes into walls (`render/viewmodel.ts`). One extra draw call. It's built from the item models (session 18b), with the arms (session 8b) in the same mesh: `gunModel` (`render/gun-model.ts`) puts each fitted attachment's parts on its mount, leaves out the gun's parts hidden by it, and takes the sight from the optic (mount + its sight point) and the muzzle from the muzzle device. Aimed, the gun sits so its sight is straight ahead of the eye. The bodies use the same `gunModel` and `knifeModel`.
  - The viewmodel rebuilds its one mesh only when the gun or its attachments change. **Optic reticles and the scope mask are one SVG overlay** (`hud/optic.ts`, rebuilt only when the optic changes), not 3D, so they cost no draw calls; while scoped the gun isn't drawn at all.
  - Tracers and impact puffs come from fixed pools (`render/effects.ts`): one line mesh and one instanced mesh, so shooting allocates nothing and costs two draw calls.
  - Recoil is simulation state, so the camera interpolates it between ticks like the eye position.
- **UI:** React DOM overlays for menus, inventory, settings and the editors.
  - **React is loaded lazily** (session 5): menus are dynamic imports, so React is a separate chunk (about 70 kB gzipped) fetched the first time a menu opens, not part of startup. No `@vitejs/plugin-react`: Vite compiles JSX itself (`"jsx": "react-jsx"`), so there's no fast refresh and a change to a component reloads the page. ESLint runs the React hooks rules on `.tsx`.
  - **The raid screen** (session 10) is lazily loaded like settings. React draws it from the live sim state and never changes it: it sends inventory actions instead. `InventoryController` (plain TS) holds the selection, taps and the drag; the drag (`ui/drag.ts`) is plain DOM, so a drag never re-renders React. Drop targets are described by a `data-drop` JSON attribute. The selected gun's attachment slots are drop targets too (`{ gun, slot }`), and a fitted attachment drags as a `PartRef` (shared with the sim) rather than an `ItemRef`, so it can drop on a grid or on another gun. The controller remembers the selected item object as well as its ref, so the selection follows a gun whose index changed (an attachment taken out of the same grid). Guns carry a `data-gun` attribute with their ref: while a loose attachment that fits is dragged over one, `gunZone` makes the gun itself the drop target (a `part` zone for the attachment's slot), and otherwise the drag falls through to the grid or gear slot as before. A drag swallows the mouse click it ends with, so dropping on an empty attachment slot doesn't also tap it. The game redraws the screen after a tick with an inventory event, and every 10 ticks for reach and changes made by others.
  - **Items on the ground (session 11b):** `render/ground-items.ts` draws them as one merged mesh of their item models (session 18b; one draw call), rebuilt only when the list or an entry's item changes (checked each tick by identity). Each item's model is laid down once and cached: guns, knives and magazines on their side, body armour, rigs and backpacks on their back, centred, resting on their lowest point. The lit item's vertex colours are scaled in place. `play/loot.ts` picks what the use button acts on: an item in reach whose direction from the eye is within 20° of the look wins over containers and bodies. The item it would take is drawn lighter, and `RaidHud` shows its name, or "No room for …" when the pickup's `inventory` event comes back refused, in `#prompt` under the crosshair. The raid screen's right column shows the ground panel when nothing is open: a `data-drop` zone for the ground (`DropZone` kind `ground`) with the items in reach as draggable tiles; the bottom bar has **Drop** (`quick` to the ground).
  - **The map tab (session 11b, `ui/map-tab.tsx`):** an SVG built from the `CompiledMap` (now in `RaidContext`): every shape's and instanced copy's footprint (box and wedge corners turned by yaw, cylinders as circles; under 0.08 m² left out), sorted by top height, water cells merged along rows, zones, extraction points and the player's arrow. The static layer is built once per map (a `WeakMap` cache) and memoised as one React element, so a redraw only reconciles the labels and arrow. Sizes are scaled by metres per screen pixel, measured with a `ResizeObserver`.
  - **The raid (session 11):** the play page starts a raid from a config (`?raid`, default `test-raid`). `hud/raid-hud.ts` shows the timer (top left, red under 2 minutes) and, in an extraction point, its name and countdown. `render/extractions.ts` draws every extraction point as a faint green column of its radius, one draw call for all of them (kept after the map tab, the user's call). When the raid ends for you (a `leave` event, or your character dead, checked from the state since a debug hit kills outside the tick) the raid screen closes, and the **results screen** (`ui/results.tsx`, lazily loaded, 1.5 kB) comes up at once, or 1.5 s after a death: how it ended, where or by what, time in raid, kills, and what you kept and lost. The game then pauses (a new `ended` pause reason). Its button (**Continue** since session 13) reloads the page, which opens on the main menu. The old death overlay is gone.
  - **Saving raids (session 12b):** `prepareRaid` in `main.ts` runs before the play page: sign in if needed (`fetchProfile`, else the sign-in screen), sync settings, send a result left in local storage (`sendPending`), then `POST /api/raids` (`startServerRaid`); the player wears the reply's `profile.gear` (`PlayOptions.gear`). If the profile had a raid open with nothing pending, a notice says it counted as missing in action. Any request failing to reach the server shows **No connection** with Try again, which runs it all again. At the end, `saveResult` writes `{ raid, end }` to local storage (`mes.pendingRaid`) **before** sending it, and clears it once the server has it or refuses it (`raid-over`, `not-found`, `invalid`; `stale` is retried once); offline or signed out it stays for next time. The results screen shows Saving…, Saved, Not saved yet, or why it was refused. **No service worker** (decided 2026-10-27): raids can't start offline, so one would only replace Safari's offline page with ours, and cached clients outliving a deploy would talk to an API they no longer match. Add one if opening offline matters later.
  - **Main menu and stash (session 13):** `main.ts` runs `prepareMenu` (sign in, sync settings, send a pending result, and an unfinished raid: tell the player, then `POST /api/raids/:id/abandon` counts it as missing in action), then the main menu (`ui/main-menu.tsx`, lazily loaded, in `#menu`), then the raid it returns. With no connection when starting, it says so and goes back to the menu. The results button reloads the page, which lands on the menu again: simpler and leak-free compared with tearing down the renderer. Settings open over the menu (`#ui` is above `#menu`), with **Done** instead of Resume; the layout editor hides the menu while it runs (`body:has(#layout-bar)`).
  - **The stash reuses the raid inventory whole.** Shared `stash.ts`: `openStash(profile)` wraps the profile in a tiny `SimState`, one player wearing `profile.gear` beside a loot container (`STASH_ID`) whose grid is `profile.stash`, the same objects, so actions edit the profile in place. `applyStash` runs `applyInventory`, refuses drops to the ground, moves anything dropped into the stash, and puts the profile back (from a JSON copy taken first) if the stash had no room or the knife left its slot; if the slot in hand was emptied, the knife is in hand. **Pages:** each stash page is its own loot container (`stashOwner(i)`, id `stash-<i>`; `stashPageOf`), so dragging works per page as on any container; the controller's target is the page shown, and a `quick` into a page that can't take all of it is tried on the others in turn (`applyStash`'s `page` is also where dropped things go first). A page's tab is a drop zone of a new kind, `into` (`data-drop` `{ into: owner }`): `canDrop` wants another owner with a free spot or a stack to top up, and `drop` sends a `quick` to it. Buying: `StashSaver.buyPage` saves first, then `POST /api/stash/pages`, and the stash reopens on the new page. The raid screen's `Inventory` is exported and takes an `InventoryContext` (the raid's `RaidContext` adds the map); `stash: true` hides Drop. `StashSaver` (client `stash.ts`) sends the whole profile 800 ms after the last change, one request at a time, keeps editing the same objects (only the version moves on), and on `stale`, `invalid` or `in-raid` reads the profile afresh and reopens the stash with a note. Starting a raid calls `flush` first and won't start if it failed.
- **Resuming a raid (session 13):** on `visibilitychange` to hidden and on `pagehide`, `play/` writes a `RaidSnapshot` to local storage (`mes.raidSnapshot`: the server raid id, the raid config, the spawn, the player's entity id, each enemy spawn marker's entity id, kills, and the whole `SimState`, about 12 kB on the test map). `prepareMenu` resumes it if it names the raid still open on the server (`readSnapshot`; anything else is thrown away): `startPlay` with `options.resume` uses the saved state instead of spawning and rolling, matches enemies to their markers for bodies and names, and takes the look from the player. It's cleared when the raid ends for you. A snapshot that fails to load is abandoned (missing in action) and the page reloads to the menu.
- **Settings sync (session 12b):** the store keeps when they were last changed (`mes.settings.at`). At startup the newer of this device's and the account's wins (`syncSettings`); later changes are sent 2 s after the last one (`PUT /api/settings`), which the server only stores if newer than what it has (`accounts.settings`, `settings_at`), so an old device coming online can't undo a newer change. A failed send is fine: the next startup sends them, being newer.
  - **Signing in (session 12b, done early):** before the play page starts a raid, `account.ts` asks `GET /api/profile`. Signed out, `ui/account.tsx` (lazily loaded, `#account`, over everything) shows a plain `<form>` with `autocomplete` names (`username`, `current-password`, `new-password`), so Safari's Keychain fills and saves it. Creating an account asks for the password twice, since there's no reset. Inputs are 16 px (smaller zooms iOS on focus) and turn `user-select` back on (the page's `none` stops typing in iOS Safari). It also shows in portrait (it hides `#portrait`), where typing is easier. Settings has an Account section with Sign out, which reloads. If the server can't be reached the game starts anyway, until 12b's offline handling.
  - **Hand slots and the heal button** (`hud/hands.ts`, session 10b) are plain DOM: slot icons by item kind, the heal button's choice (worked out about 10 times a second, since `treatments` allocates), an SVG progress ring, and the long-press picker. The first-person knife and the draw, lowering and slash motions are in `render/viewmodel.ts`; the body's slash is IK on the right arm in `render/character-body.ts`, with the placeholder knife in `render/gun-model.ts`.
  - The HUD doesn't re-render through React every frame. Values that change every frame are written straight to the DOM, or throttled to about 10 Hz. **The in-game HUD buttons are plain DOM** (`hud/`), as is the layout editor, which moves the real buttons over the paused game.
- **Input:** Pointer Events for the virtual sticks and buttons (`input/controls.ts`). Moves and lifts are listened for on `window`, so a touch that started on a button keeps working when it slides off. **The layout is stored in settings** as each moved control's centre (a fraction of the screen) and a size multiplier; unmoved controls follow the defaults in `hud/layout.ts`.
  - **Desktop (2026-10-30):** `input/mode.ts` keeps `inputMode` (`touch` or `desktop`) from `(hover: hover) and (pointer: fine)`, then from each pointerdown's `pointerType`, and writes it to `body[data-input]`; CSS hides the touch-only controls on desktop. `input/cursor-lock.ts` (`CursorLock`, owned by `Controls` as `controls.cursor`) does pointer lock on the canvas: the game says `want(true/false)` (the play screen each tick: not while the raid screen or heal picker is open or the raid has ended, and from `closeScreen` directly, since browsers only lock on a user gesture). Wanted but not locked shows `#cursor-lock` and pauses with reason `'cursor'`; a request still unanswered (up to 1 s) doesn't flash it. Mouse pointers never drive the touch stick; locked `mousemove` turns the view by `movementX/Y` (deltas over 400 px dropped as browser glitches), and `mousedown`/`mouseup` (not pointer events, which merge chorded buttons) fire and aim. Settings gained `mouseSensitivity` (falls back on its own; no format change). `RaidHud.setPrompt` takes the key to show as a `<kbd>`.
- **Pistols out of the primary slots (2026-10-30):** `fitsSlot` refuses a pistol in `primary1`/`primary2`, which covers the sim, the raid screen's drop targets and the server's checks. Saves from before can have one there, and moving it needs the items, so it isn't a profile format migration: `settleGuns` (shared) moves it to an empty sidearm, else onto the first stash page with room. The server runs it in `parseProfile` and on a raid result before `checkGear`.
- **Settings:** stored locally first (`localStorage`, key `mes.settings`) and synced to the account (session 12b, see Client → Settings sync). The schema is in `shared` (`settings.ts`), versioned like content files, and every field falls back to its default on its own, so a bad value never wipes the rest. `settings.ts` in the client is the store: changes save and apply straight away.
- **Pausing** (`app/pause.ts`): the game pauses for a reason (portrait, a menu, the page hidden). While paused the frame loop stops, every touch is let go, and the time away doesn't count as a frame. Co-op will need a different rule: the raid can't stop.
- **PWA:** web app manifest (`public/manifest.webmanifest`, landscape, standalone) and Apple meta tags, plus the Safari workarounds in design.md. The icons are placeholders drawn by a one-off script. **No service worker:** iOS doesn't need one to add to the home screen, and session 12b decided against one (see Client → Saving raids).
- **Audio:** Web Audio API, unlocked on the first tap (`app/audio.ts`: the first `touchend`, `pointerup` or key creates the context and plays a silent sample; later taps resume it after iOS suspends it). **Sounds are generated** with Web Audio (the user's call, 2026-10-30), not recorded samples (session 19).
  - **Sound files** (`content/sounds/<id>.json`, format 1, `packages/shared/src/content/sounds.ts`): `gain`, `range` (metres heard to), `pitchJitter` and `layers`, each `noise` (`colour` white, pink or brown) or `tone` (`wave` sine, triangle, square or saw, `freq` [from, to]), with `at`, `attack`, `hold`, `decay`, `curve`, `gain`, optional `drive` (tanh soft clipping), `filter` (lowpass, highpass or bandpass, `freq` [from, to], `q`) and `sweep` (how long the glides take).
  - **`audio/synth.ts`** renders a recipe to samples in plain TypeScript (seeded noise, a phase-accumulator oscillator, an RBJ biquad updated every 32 samples while gliding), not Web Audio nodes: the same in tests as on the phone, and done once per sound, so playing costs a buffer source. A sound peaking over 1 is turned down to fit; a content test keeps every sound under 1.5.
  - **`audio/sounds.ts`** (`SoundPlayer`, one for the game from `sounds()`, at the settings' volume): renders each sound the first time it plays (`prepare()` renders all at raid start, once audio is unlocked), then plays it as **buffer source → lowpass (only if muffled) → stereo panner (only if off centre) → gain → master**. 16 voices; when full, the quietest stops for a louder one; the same sound again within 20 ms is dropped. **`audio/spatial.ts`** (`place`) works out gain, pan and cutoff from the listener: (1 − d/range)² × 40/(40 + d), cutoff from 20 kHz to 700 Hz across the range, duller and quieter from behind, and 600 Hz and ×0.45 through a wall. Cheaper than `PannerNode`'s HRTF, and testable.
  - **`audio/cues.ts`** (`SoundCues`): after each tick, the sim's events and what it doesn't report become sounds: footsteps by distance walked on the ground (a step every 1.1 + 0.1 × speed metres), landing, ladder rungs, a reload or med starting, drawing, the extraction countdown and the two-minute warning. The listener is the player's eye and the controls' yaw. Each positional sound casts one ray (`CollisionWorld.raycast`) to decide if it's muffled. **The sim didn't change.**
  - Menus: a click on a button in `#ui` ticks (`main.ts`); `Stash.post` (buying, selling, pages, quests) plays money on success and a refusal on failure.

## Editors (`/editor` route in the client)
- Desktop only (mouse and keyboard).
- **Saves through a Vite dev-server plugin** that writes JSON into `content/`.
  - The editor routes and the save endpoint exist **only in the dev server**, never in the production build. That makes them admin-only without needing an auth system.
  - Content changes go through git like code.
  - **Admin page (2026-10-30, the user's call):** the main menu's **Admin** button (dev builds only) gives items into your stash free, for testing, through `POST /api/admin/give`. The Worker allows `/api/admin/*` only when `ADMIN` is `"1"`, which only the server's `npm run dev` sets (`wrangler dev --var ADMIN:1`); the deployed Worker answers not-found, before sign-in, so nothing hints the route exists. It works from the iPhone when it plays against the dev server over the LAN, not in the live game.
  - **Cheats:** infinite health, infinite ammo and peaceful are sim flags on the player (`Character.admin`, optional, so saved raids without it still load), so a co-op server could honour them the same way. The client sets them only in dev builds. Keeping your gear on death is the server's to grant: the end-of-raid request's `keepGear` is ignored unless `ADMIN` is `"1"`. Infinite consumables is a sim flag too (`AdminCheats.infiniteConsumables`); enemy health bars are client-only (`hud/enemy-bars.ts`, a DOM overlay like the quest markers).
  - **Spawner guns:** a weapon's optional `spawns` (an enemy type id, checked by `checkEnemies`) makes an admin gun. No item format bump: the field is optional. The sim can't spawn the enemy itself (it has no enemy types or loadouts), so a shot that hits something pushes a `spawnRequest` event and whoever runs the raid spawns and arms it: today the client, between ticks, like `?respawn`. A co-op server would do the same. The raid save keeps them as `spawner:<type>:<entity>` keys in its enemy map.
- **Built in session 15** (`packages/client/src/editor/`, plugin `packages/client/editor-save.mjs`):
  - `main.ts` imports the editor only behind `import.meta.env.DEV`, so a build leaves it out. `?map=<id>` picks the map.
  - **The save plugin** (`apply: 'serve'`) takes `POST /__editor/save` with `{ files: [{ file, doc, create? }] }` (a batch since session 16b) for `maps/` or `prefabs/` only, **from the Mac only** (loopback, same origin, `application/json`; the dev server listens on the LAN for the phone). It lays the JSON out like the hand-written files (objects one key per line, items of lists other than `nodes` and `zones` on one line) and formats it with Prettier, so an unchanged map saves to the same bytes. It skips the reload for a file it just wrote, so the editor keeps its state; other open tabs need a reload to see the change.
  - **The editor edits the file's own JSON**, not the parsed copy (zod gives keys in schema order), with a JSON snapshot before each edit for undo (200 deep). After every edit it rebuilds the scene and runs the same checks the game would (schema, `compileMap`, enemy, key, loot and quest-marker references); a map with a problem can't be saved.
  - **Camera for a trackpad** (`EditorView.wheel`): the page takes the wheel events itself, so a pinch (a wheel with `ctrlKey`) zooms the scene, not the page. OrbitControls does only the drags; its left button is switched to rotate while Option is held (a capture listener on `window`, before it and the gizmo see the press).
  - **Each node is its own object** at its pos and yaw, its mesh built by shared `compileNodes` at the origin (shaded on the GPU, so turning it shades right); a group's object holds its nodes' objects. Markers and patrols are drawn with `buildDebug`, doors with `buildDoor`. Nothing is merged, unlike in play; it's the desktop. The terrain is one mesh per chunk and can't be selected (the "locked ground layer").
  - **The gizmo** is three.js's `TransformControls` on a pivot in the frame of the group being edited, unturned so the grid lines up with it: on the one selected node, or the middle of several. The editor does its own snapping (absolute for one node, whole steps for several) and drops what's dragged sideways onto the first surface from 0.3 m above its base (not markers), or the terrain. A drag ends as a move-and-turn about the pivot (`moveWith`), which also carries a patrol's points.
- **Session 16** (`editor/terrain.ts`, `editor/overlap.ts`):
  - **Terrain brushes** (`applyBrush`) work on a `Float64Array` copy of the corner heights while the mouse is down; the view redraws only the 32 m chunks touched (the terrain is one mesh per chunk, built with the same `TriangleBuilder.terrain` as play) and the bases. On release, `setHeights` writes the heights rounded to a centimetre and moves everything whose base was within 2 cm of the old ground by the change (patrol points one by one; groups' own positions never; buildings never), as one edit. The view rebuilds the ground (terrain, water, zones, sky) only when those change.
  - **Overlaps** (`findOverlaps`) are worked out after every edit from each placed thing's collision solids (`compileNodes` boxes and ramps, cached per prefab), as rectangles turned about y with a bottom and top, by the separating axis test with 5 cm of tolerance. Buildings compare footprints only. `edit` refuses a change that raises the number of overlapping building pairs (counting, since indices shift). The view draws bases itself from each object's world matrix (`compileNodes` has no terrain), so they follow a drag.
  - The save plugin watches `content/maps` and `content/prefabs` (outside Vite's root, so new files there weren't seen), and `create: true` refuses to overwrite.
- **Session 16b (prefabs):**
  - **Paths step into prefabs:** `nodesAt(map, path, prefabs)` goes into a placed prefab's file as into a group, so the scope can be inside a prefab (inside a prefab…). The view builds the entered copy part by part (outlined purple; the panel says every copy changes, and how many there are); every other copy is one mesh, rebuilt with the edited prefab after each edit. Entering or leaving rebuilds the scene.
  - **One undo history across files:** the editor keeps the map and every prefab as their files (`MapEditor.prefabs`), and a snapshot is every file's JSON by name. Unchanged files share their strings between snapshots, so only what an edit changed costs memory. After an edit, a changed prefab gets a new object, and the overlap cache (`forgetPrefabSolids`) is dropped, since prefabs nest.
  - **Saving** sends every changed file in one request (new prefab files with `create`, before the map); the plugin formats them all before writing any. It's refused while the map has a problem or a changed prefab fails its own schema, or if **any other map** gets a problem it didn't have with the prefabs as saved (`check` on each, from `mapSources`). The plugin runs `enforce: 'post'` and skips the reload in `hotUpdate`, which, unlike `handleHotUpdate`, also sees new files: the content globs would otherwise reload the page when a new prefab is written.
  - **Making a prefab** (`makePrefab` in `doc.ts`) groups the selection (middle, lowest point), moves the group's nodes into a new prefab file and puts one placement where the group was. The file's colour slots that they use come along with their values, and the placement passes the file's own slots on (`"colours": { "paint": "paint" }`), so nothing changes colour. A placement gets an id (from the prefab's, made unique) when what's in it has ids, and the prefab tool does the same for buildings. Ids inside a prefab compile as `placement/id`, so the edit is refused if the map then has a problem it didn't have (a quest's marker, say).
  - **Unpacking** (`unpackPrefab`) puts a group (named after the placement, at its pos and yaw) of copies of the prefab's nodes in its place, slot colours resolved to the placement's (a hex colour, or the enclosing file's slot), ids made unique and patrols repointed (`copyNode`); refused the same way.
  - The **prefab's own settings** show when nothing inside it is selected: name, instanced, colour slots (default colour, add, remove), building footprint (size, centre, base colour) and **Fit footprint**, which fits the solids whose bottom is within 0.3 m of the floor (so a roof's overhang doesn't count). A placement's inspector has a colour per slot: the prefab's, custom, or a slot of the file it's in.
- **Session 17 (gameplay):**
  - **Markers, doors, patrols and zones** have their own fields in the inspector, filled from the content they name (enemy types, loadouts, loot tables, containers, key items, quests). Patrols and zones are drawn a click at a time (`EditorState.drawing`); their points are **handles** (`EditorView.setHandles`, worked out from the state in `MapEditor.handles` on every change), dragged onto surfaces, or the terrain for zones. The format didn't change.
  - **Nav overlay:** `NavGrid` from the compiled map, rebuilt a moment after each edit, drawn with `buildNavOverlay` coloured by `Exposure.kind`. **`Exposure`** (`packages/shared/src/nav/exposure.ts`, no rendering) labels each node reachable, seen or hidden, `step(n)` at a time; the editor runs it in 30 ms slices. It's in shared so a content check could use it later.
  - **Play-test:** `writePlayTest` puts the map and prefab files in localStorage; `/play-test` (dev only, like `/editor`) compiles them and runs `startPlay` with `test: { map, raid }`, which skips the result, the snapshot and the server. The profile is `newProfile` with the new-player kit.
- **Session 18 (the item editor, `packages/client/src/item-editor/`):**
  - `/item-editor?item=<id>` (dev only, imported behind `import.meta.env.DEV` like `/editor`) is a React page with no 3D. `ItemEditor` keeps **every item file's JSON** by id (`itemSources`, the files as written, for their key order) and one undo history across them; a snapshot is the whole map of strings, so unchanged files cost nothing. A drag in the reticle designer is one undo step (`beginGesture`, `edit(…, true)`).
  - After each edit every file is parsed with `ITEM_FORMAT`; if all pass, **`itemContentProblem`** (`content.ts`) runs `checkItems`, `checkEnemies`, `checkLootTables`, `checkVendors`, `checkQuests`, every map's door keys, and `newProfile` + `checkProfile` for each starting kit, against the edited items (the other kinds are loaded raw, without the game's checks against content/items). Any problem blocks saving. `itemUses` lists what names an item (`item` fields, kit gear, door keys, guns' ammo, attachments' guns).
  - `storageRisks` (`risk.ts`) compares an item as saved with as edited, mirroring what `checkProfile` limits, and the page warns.
  - The **reticle designer** uses `reticleMarkup` from `hud/optic.ts` (the overlay's own SVG) and `aimedFov` for the person's size, so the preview is what the phone shows.
  - The map editor's form fields moved to `editor/fields.tsx` for both editors. The save plugin accepts `items/<id>.json` and watches `content/items`.
- **Session 19 (the sound editor, `packages/client/src/sound-editor/`):** `/sounds?sound=<id>` (dev only). `SoundEditor` is the item editor's state (every file's JSON, one undo history, gestures, checks, one save request) for sound files; `soundContentProblem` checks the items' and game's sounds are still there. `Audition` plays the open sound as edited with its own `SoundPlayer` (centred, or placed with `place`). The bound fields (`get`, `put`, `N`, `P`, `Row`, `Check`) moved from the item editor's panel to `editor/bound-fields.tsx` for both. The save plugin accepts `sounds/<id>.json`, and its layout keeps objects inside one-line list items on one line (a layer's filter) instead of breaking them.
- **Session 18b (models, `item-editor/model-*.ts`):** a **model** tab beside **stats** (the list's tab buttons). `model-panel.tsx` lists the parts (add box, cylinder or wedge; copy, mirror across x, delete) with each one's fields, and the item's points with x/y/z; `model-view.ts` is the 3D view, kept while switching items. **Build**: each part its own mesh at its place, picked by clicking and moved or turned with `TransformControls` (snap 0–5 cm, 0–45°; W, E), points as dots drawn on top, the sight line dashed; a drag is one undo step, and the view waits for the gizmo to let go before redrawing. What the item goes with is drawn but not pickable: the attachments chosen for each of a gun's slots (its hidden parts faint), the gun an attachment is previewed on (moved so the attachment stays at the origin), and the mannequin for worn gear. **Hip** and **aimed** use the game's own `Viewmodel`, field of view and `reticleMarkup` (only once every item passes its checks). `model-edit.ts`: `setSlots` keeps a gun's mounts and `hiddenBy` in step with its slots (a new slot gets the placeholder's mount), `fitPointsToSlot` an attachment's points with its slot. ## Server (`packages/server`)
- **Cloudflare Workers (free plan)** with **Hono** for routing and **D1** (SQLite) for accounts, stash, vault, quest progress and vendor state.
- **Responsibilities:** accounts and sessions, profile and stash persistence, starting and ending raids (raid results go through sanity limits), vendor transactions, quest state.
- **Solo raids run entirely on the phone.** The server only sees the start and the result.
- **Co-op (later):** one Durable Object per co-op raid runs the shared simulation at 30 Hz, connected by WebSocket. It stays awake for the length of the raid (about 112 GB-s for a 15-minute raid, against a free allowance of 13,000 GB-s per day). Incoming WebSocket messages are billed at 20 per request, against 100k requests per day.
- **Free-plan limits are hard caps:** going over makes requests fail until midnight UTC. Nothing is charged.
- **Built in session 12** (`packages/server/src`): Hono routes `auth.ts` (register, login, logout, the `signedIn` middleware), `profiles.ts` (GET and PUT `/api/profile`) and `raids.ts` (POST `/api/raids`, POST `/api/raids/:id/end`). The request and reply types, `ACCOUNT` rules and `ApiErrorCode`s are in shared `protocol.ts`; an error is `{ error, message? }` with a 4xx status (`errors.ts`).
  - **D1 schema** in `packages/server/migrations/` (`accounts`, `sessions`, `profiles`, `raids`). `npm run db:migrate -w @mes/server` applies it locally; `predeploy` applies it remotely. Times are Unix milliseconds.
  - **The profile is one JSON document** (shared `profile.ts`, `PROFILE_FORMAT` with migrations like content): `money`, `stash` (pages of 10×30 that hold containers: format 2 since session 13, which migrates format 1's one grid into the first page; `PROFILE.pagePrices`, `nextPagePrice`, `buyStashPage`), `quests` (format 3 since session 14; see Quests; format 4 in session 19za only renames item ids, `ammo-556` → `ammo-762x39` and `mag-556-45` → `mag-762x39-45`, in grids and fitted attachments) and `gear` (the sim's `Gear`, vault and knife included). It's always read and written whole, with a **version** that goes up on every write; writes are `UPDATE … WHERE version = ?`, and a batch's other statements check the same version, so two devices can't interleave (the loser gets `stale`). `checkProfile`/`checkGear` are the sanity limits (design.md → Trust model), `itemGained` the "no items from nothing" rule, `restGear` puts guns down before storing. New accounts get `newProfile` from `content/starting-kits/new-player.json` (a new content kind, format 1) plus the knife.
  - **Raids:** a row per raid, at most one open per account (a partial unique index). `PUT /api/profile` refuses a change in the number of stash pages; `POST /api/stash/pages` (`stashRoute` in `profiles.ts`, with the version read, like PUT) buys the next one. Since session 13, `POST /api/raids/:id/abandon` ends an open raid as missing in action without starting another (the game opening on the menu calls it); for a raid already ended it replies with the profile. Start: an open raid is ended as `mia` (gear → `keptGear(gear, false)`), the new row inserted and the profile bumped, in one batch. End: the gear sent is cut down by `keptGear` (shared `raid.ts`, the knife falling back to the profile's), checked, and stored; the request is stored as `result`, and the same request again replies with the profile (a retry whose reply was lost), anything else `raid-over`.
  - **Accounts:** usernames 3–20 of `A–Z a–z 0–9 _ -`, unique ignoring case; passwords 8–200 characters. **PBKDF2-SHA256 with 50,000 iterations** and a 16-byte salt, stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>`: 100k measured 12 ms on the Mac, over the free plan's **10 ms CPU** per request, 50k about 6 ms. The count is per hash, so it can go up later. Ten wrong passwords in a row lock the account for 5 minutes. **Sessions:** a random 32-byte token in an HttpOnly, `SameSite=Lax` cookie on `/api` (Secure over HTTPS only, so plain-http dev on the LAN still works), stored as its SHA-256, for 180 days, extended when past half.
  - **Content on the server:** wrangler can't glob like Vite, so `scripts/bundle-content.mjs` writes the items, raids, starting kits and vendors (13b) into `src/generated/content.js` (gitignored), run before the server's dev, deploy, typecheck and tests. `loadById` (moved from the client into shared `content/format.ts`) loads them.
  - **Tests** run the Hono app in Node against a small D1 stand-in over `node:sqlite` (`src/test/d1.ts`), built from the migrations. `@types/node` isn't installed (its globals clash with workers-types); `src/test/node.d.ts` declares the few Node APIs used.

## Hosting and testing
- **One Worker serves both the client and the API** (decided 2026-10-26, session 1). The built client is the Worker's static assets (`packages/server/wrangler.jsonc` points at `packages/client/dist`). Only `/api/*` runs Worker code; any other unknown path falls back to `index.html`. Sharing one origin means no CORS, and session cookies work with no extra setup. Pages was the alternative; Cloudflare is moving new projects to Workers static assets anyway.
- In dev, the client (Vite, port 5180) and the Worker (`wrangler dev`, port 8787) run separately, and Vite proxies `/api` to the Worker. `wrangler dev` refuses to start if the assets folder is missing, and `dist` is gitignored, so the server's `predev` creates an empty `packages/client/dist` (decided 2026-10-30). A fresh clone runs `npm run dev` without building first.
- **Phone testing during development:** run `vite --host` and open it on the iPhone over the local network. When HTTPS is needed (installing as a home-screen app, some browser features), use a Cloudflare preview deployment or a `cloudflared` tunnel.
- Each milestone ends with a performance check on the real iPhone (FPS counter in dev builds).

## Characters (confirmed, see design.md → Characters)

Built in session 8b:
- **The asset:** `packages/client/public/characters/mannequin.glb`, from Quaternius's Universal Animation Library (Standard, CC0; licence and source in the README next to it). `scripts/build-character.mjs` builds it from the pack's GLB with glTF Transform and meshoptimizer: 15 clips kept, UVs dropped, the mesh simplified from 13.7k to 5.8k triangles, only rotation tracks kept (plus the hips' translation). 556 kB, 279 kB gzipped, fetched at startup rather than bundled. Quaternius's site moved new downloads to its own licence (QAL, August 2026), which forbids redistributing the files; this copy is CC0, but check before adding later downloads to the public repo.
- **One draw call per character, gear included** (`render/character.ts`). At load, the body is baked into flat triangles with face normals; each face takes the outfit part of the bone that weighs on it most (joint bands 20% darker). Each look (outfit, worn items, gun) is one geometry, built once and cached, with gear bound rigidly to its mount bone. Shading happens on the GPU from the skinned normal, with the same formula as the map. Bodies cull by a fixed sphere, since animation moves them far from their rest-pose bounds.
- **Animation** (`render/character-body.ts`): two layers, legs and upper body, from clips split by bone. The legs pick idle, walk, jog, sprint, crouch, crouch walk, jump or death by speed and stance, paced to the speed. When strafing, the hips turn towards where it's going (up to about 70°) and the chest turns back to face forward; going backwards plays the clip in reverse. The upper body leans with the look pitch and flinches when hit. **Gun hold by IK:** a two-bone IK per arm, with the hand rotations measured once from the pistol aim clip. The gun's position and tilt per hold are in `HOLD` there.
- **three.js's mixer only writes a bone when its clip value changes**, so posing on top of clips must put each bone back to its clip rotation before every update; otherwise turns pile up frame after frame. `CharacterBody` does this for the bones it poses.
- **LOD:** a body animates every frame within 20 m, every 2nd frame to 45 m, every 4th beyond, and every 8th off screen. It uses IK within 30 m; beyond that the gun goes in the hand. The dead stop animating 3 s after falling. Positions and yaw are interpolated between ticks.
- `/bodies` shows every pose with the hit zones over them, and `?hitzones` does the same in play.
