# Tech stack and architecture

Status: **confirmed by the user on 2026-10-26.**

## Platform: a mobile web game, not React Native
React Native / Expo Go was considered and rejected:
- Hermes (React Native's JS engine) has no JIT and no WebAssembly, so game logic would run slowly.
- `expo-gl` puts rendering and game logic on one JS thread.
- Expo Go locks you to a fixed SDK and set of native modules.

Mobile Safari has a JIT and WebAssembly, needs no build step and no Apple developer account, and installs from Add to Home Screen. Every iOS browser uses Safari's engine underneath, so Chrome on iOS makes no difference.

## Repo layout (npm workspaces monorepo)
npm, not pnpm (the user's choice, 2026-10-26). Each package lists every dependency it imports, since npm won't catch a package using a dependency that only another package declared.

Tooling (session 1):
- `@mes/shared`, `@mes/client` and `@mes/server` are the package names. `shared` has no build step: it exports its TypeScript source, and Vite and wrangler bundle it.
- TypeScript is **pinned to 6.0.x**, because typescript-eslint doesn't support TypeScript 7 yet. Move to 7 once it does.
- `shared`'s tsconfig leaves out the DOM types, and ESLint blocks imports of three.js, React and the other packages from it, so the "no rendering or UI in the simulation" rule is enforced, not just written down.
- Strict TypeScript, including `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.
- One root ESLint (flat config) + Prettier setup. Vitest runs every package as a project from the root.
```
packages/
  shared/    # game simulation, rules, data schemas. No three.js, React or DOM.
  client/    # Vite app: three.js renderer, React UI, input; includes /editor
  server/    # Cloudflare Worker
content/     # JSON game data: maps, prefabs, items, loot tables, quests, vendors, enemies, zombies modes
docs/
```

## Shared simulation (`packages/shared`)
- Plain TypeScript.
- **Fixed 30 Hz tick:** `step(state, world, inputs)` advances the state **in place** (decided in session 3, so a tick allocates nothing). `FixedTimestep` turns frame times into ticks. The renderer interpolates between ticks, copying the few values it draws before each tick. Look direction is applied to the camera every frame, not every tick, so turning never lags.
- **Serialisable inputs and state.** This is what lets co-op run the same code on the host's device (and, if ever needed, a server). Bit-exact determinism isn't needed (the host is authoritative in co-op).
  - The state (`SimState`) is plain JSON-safe data: entities, the tick count and the RNG state. A test checks that a JSON round trip continues identically.
  - The static map is not in the state. It's a `CollisionWorld`, built once from a plain `WorldDef` (terrain grid, boxes, ramps and ladders) that the map loader produces.
  - Inputs are per entity per tick: the move stick, absolute yaw and pitch, and sprint, crouch and jump. Crouch is the wanted stance, so hold vs. toggle stays a client setting.
  - **Prone and vaulting (2026-10-30):** `PlayerInput.prone` is optional (left out, not prone) and wins over crouch; stance is still just `Character.height` (prone below `crouchHeight`). A vault is its own `MoveMode`, `'vault'`, with the move in `Character.vaulting` (start, end, the top cleared, heights before and after, time in), so it survives a JSON round trip and a resumed raid; snapshots from before simply have no vault in progress. `startVault` (`sim/movement.ts`) finds one from the collision world when jump is pressed on the ground: a ray at knee height, `groundAt` every 10 cm across the top, `overlaps` for the gap (sliding sideways in 2.5 cm steps) and the landing. That's a few dozen grid queries, only on a jump press, and it allocates only when a vault starts. During the move nothing collides and characters aren't separated.
- **Combat (session 6):** `step(state, world, items, inputs)`. The item database (`ItemDb`, every item by id) is static like the world, so it's passed in rather than kept in the state. Each tick everyone moves (then takes fall damage), then everyone's gun updates (so shots see this tick's positions), then bleeding. Inputs gained `fire`, `aim` (both held) and `reload` (a press).
  - Character state gained `health` (HP and bleeding per zone, dead), `helmet` and `bodyArmour` (item and durability), `weapon` (item, rounds, spare rounds, cooldown, reload timer), `aim` (0–1) and the recoil offsets. Session 9 moved armour and guns into `gear` and spare rounds into the inventory (see Inventory model).
  - **Attachments (session 6b):** the weapon state has `attachments` (the item id in each slot, or null). `weaponStats(items, weapon, out)` works out the gun's stats with them into a scratch object, so a tick still allocates nothing. `attach` and `detach` change them (an attachment that doesn't fit throws; check with `fits`). Since session 10c the player changes them only through the `attach` and `detach` inventory actions (see Looting and inventory actions); `createWeapon` and loadouts still call them directly. Shot events carry `loudness` for AI hearing.
  - `state.events` lists what happened during the last tick (`shot`, `damage`, `death`) for effects, hit markers and the HUD. It's cleared each tick; events are the only allocation, and only when something happens.
  - **Hit zones** are six capsules in a fixed layout (`HIT_CAPSULES` in `sim/hit-zones.ts`), turned by yaw and squashed by crouch height. `raycastCharacters` checks each living character's bounding sphere, then its capsules. **No spatial hash for moving things:** with tens of characters, a sphere test each is cheaper than keeping a hash up to date. Revisit if a raid gets past about 100 characters.
  - **Head offset (2026-11-04):** `headOffset(c, out)` in `sim/hit-zones.ts` gives the head capsule's side, height and forward shift from `vx`/`vz`, `height` and `pitch`, measured from the mannequin's clips (head vertices averaged over each clip). `capsuleEnds` adds it before squash and lean, and `CapsuleBody` draws it for `?hitzones` and `/bodies`. Re-measure if the clips or the `spineLean`/`headLean` numbers change.
  - **Leaning (2026-11-01):** `PlayerInput.lean` (−1..1) and `Character.lean` (optional; missing is 0), eased in `moveCharacter` and cut short by `fitLean` (a ray from the upright eye to the leaned one, called in `step` after bodies push apart). Everything above `MOVEMENT.leanPivot` × height turns about the forward axis through that point: `eyeX`/`eyeZ`/`eyeHeight` for the eye, `bodyPoint(c, h, out)` for a point on the centre line, and `capsuleEnds` for each hit capsule's ends (squashed first, then tipped). Anything measuring from a character's eye must use all three eye functions, not `c.x, eyeHeight(c), c.z`. Enemies' sight (`sightRate`) and aim (`fight`) use `bodyPoint` on their target; their own eyes stay at `c.x, c.z` since they don't lean. `sightRate` multiplies by `AI.leaningRate` scaled by how far the target leans.
- **Seeded RNG** for loot rolls, enemy loadouts, AI decisions, shot spread and bleeding.
- **Collision:** written in-house, no physics engine:
  - A capsule for the player and AI, against rotated boxes, the terrain height grid and stair ramps.
  - **Footprints rotate about Y only** (session 3). A standing capsule against a solid is then a circle against a rectangle in XZ plus a height overlap: simple and robust.
  - **Tilted solids are slabs (the user's call, 2026-11-05, replacing "a tilted solid collides as its upright bounding box"; a bounding box made a container tilted as a ramp a 5 m invisible block):** `BoxDef` stays the solid's bounds, so loot, overlaps and the cut view need no change, and an optional `slope` (`BoxSlope`) adds a sloped top and underside over the footprint. You can walk up the top, walk under the raised end and walk around inside something hollow, and rays hit the same planes. Tilted boxes and cylinders (as their box) become these, with `tiltedBox` in `compile.ts` picking as top and underside the pair of faces with the most floor under them, so a thin board stays a board however steep. The ends are upright, not leaning, and the slab is cut to the box's bounds. A tilted wedge has a top and underside of its own (`tiltedWedge`). `pushOut` backs a head up a sloped underside rather than out through a side. Full oriented boxes were turned down: they'd rewrite the circle-against-rectangle core for little gain on a phone.
  - **Touching isn't under (2026-11-03):** `ceilingAt` ignores solids that reach less than 1 mm (`SOLID_CONTACT`) over the circle. `pushOut` leaves a capsule against a wall at its radius, give or take rounding, so a roof flush with the wall's face (every shipping container) stopped any jump made against it. **`groundAt` does the same (2026-11-04):** the container's floor slab is flush with the wall's face too, so walking into the wall lifted you onto a floor on its far side. Its reach is clamped at radius 0, since point queries pass 0.
  - Ramps are wedges (solid underneath). Stairs are drawn as steps but collide as a ramp.
  - Terrain cells are two triangles split along the diagonal from (i+1, j) to (i, j+1). The renderer must use the same split, or feet float or sink.
  - The character controller is kinematic. It pushes out of walls horizontally (ignoring anything at or below step height), then follows the ground up steps and down slopes, or falls. When landing, it looks for surfaces between the old and new feet, so fast falls don't tunnel through thin floors.
  - A spatial hash (`StaticGrid`, 4 m cells) for the static solids; raycasts walk its cells in order.
  - **Doors (session 11c)** are solids after the boxes and ramps (`WorldDef.doors`, `firstDoor`, `doorOf(solid)`), each with three poses precomputed (closed, open into its +z, open into its −z); `setDoorOpen(door, open, flipped)` copies one in, and the door's grid cells cover all three. A door swings away from whoever opens it: `useDoor` sets `DoorState.flipped` from which side of the doorway they stand, and it's kept while closed so the renderer swings it back from that side. That's the only thing in the world that changes. The truth is `SimState.doors` (`{ open, locked }` by index, the order of `CompiledMap.doors`); `syncDoors(state, world, nav)` brings the world and nav grid in line, at the start of every `step` and once after loading, so a restored state on a fresh world is right. Using a door is `PlayerInput.door` (an index, a press), applied after inventory actions; `useDoor` checks reach (2 m from the doorway or the open slab) and keys, and pushes a `door` event (`opened`, `closed`, `unlocked`, `locked`, `blocked`). Opening snaps; a body it lands on is pushed out by its next move. The renderer eases the swing over 0.2 s (`updateDoors`).
  - Raycasts for hitscan and line of sight, against solids and terrain, with the hit normal. Queries reuse scratch space and allocate nothing.
- **Navigation:** a navigation grid with multiple layers (floors), generated from the map data. It links stairs and slopes, but not ladders. A* pathfinding.
  - **Searched looks (2026-11-03, design.md → Inventory and UI → Looting):** `loot.searched` on a node names a prefab (optional, so maps and prefabs stay format 3); it's placed in the node's frame, drawn only, and takes the colours of slots it shares with the container's scope. `compileMap` gives `searchedLooks` ({ id, closed, searched }, by container id). **`CompiledMap.shapes` keeps the closed shapes**, so the map tab and anything else reading it get the closed look, and `compileNodes` has no looks, so the editor and thumbnails do too; only `buildMap` leaves those shapes out of the chunks (`closed` are the same objects). A prefab holding such a container, or one that is the container, is flattened even if `instanced`. A missing prefab is a content error. The truth is `LootContainer.searched` (missing is false, as in older saves) in `SimState.loot`, set only by `searchContainer` from `PlayerInput.search` (a container id, a press), which checks reach and pushes a `search` event the first time. The client sends it in one place, where the use button opens a container; a timed search would send it when it ends. The renderer draws each such container's two looks as baked meshes of their own, one visible, so that's one draw call per container with a look; `updateSearchedLooks` follows the sim every frame and once on loading, so a resumed raid shows them open. If maps fill with cabinets, merge a chunk's unsearched looks. **Aiming follows the look:** `lootableInReach` also tests the crosshair against the bounds of a searched container's `searched` shapes, up to the first solid it meets (`searchedAimedAt`, boxes cached per `sim.loot`). The look still has no solids, so it doesn't block walking or shots.
  - **Glass (2026-11-02, design.md → Movement → Glass)** are solids after the doors (`WorldDef.glass`, `firstGlass`, `glassOf(solid)`): a thin box per pane. `setGlassBroken` moves a broken pane's solid 1e9 m away, so every query misses it without a check of its own. `raycast(..., hit, seeThrough)` skips glass for lines of sight (AI sight and hearing, `exposure.ts`, blast reach to glass). The truth is `SimState.glass` (true is broken, by the order of `CompiledMap.glass`; filled in all whole for a state saved before glass); `syncGlass` runs with `syncDoors`. `sim/glass.ts`: `breakGlass` pushes a `glass` event (loudness 12); `castShot` breaks panes in the way (up to 4) and re-casts, unless someone is hit first; the knife breaks the pane its swing hits; `explode` (not flash or smoke) runs `breakGlassNear`; an impact fuse breaks the pane it hits. The nav grid is unchanged: a window was never walkable. The renderer draws all panes as **one instanced mesh** (`MeshBasicMaterial`, opacity 0.3, no depth write, a colour per instance) and scales a broken one to 0 (`updateGlass`); breaking scatters 10 puffs of its tint (`Effects.shatter`) and plays `glass-break`.
  - **Links through thin things (2026-11-05):** a side link also needs its halfway point as clear as a node, because two nodes can straddle a 4 cm fence bar (a strip 0.44 m wide on a 0.5 m grid). It took Northpoint's nav build on the Mac from about 360 ms to 580 ms (857k nodes, one run each).
  - **Session 7:** `NavGrid` (`nav/nav-grid.ts`) is built at load from the `CollisionWorld` (about 80 ms and 146k nodes for the 192 m test map on the Mac). It's static like the world and never part of the state. Columns every **0.5 m**; each holds a node for every surface (terrain, or a solid's top) where a standing body fits: no solid in the way from a step's height (0.45 m) to 1.8 m above it, within **0.2 m** (less than the body's 0.35 m radius, so 1 m doorways are always open however the grid lines up; bodies slide along the walls). A surface less than a step under another is dropped (stood on through it). Terrain steeper than 45° isn't walkable. Each node stores a bitmask of links to its 8 neighbours (a neighbour within a step's height; diagonals only if both sides are linked, so no corner cutting). Neighbours are found by looking in the column, not stored. A flood fill numbers the **connected components**, so "can it get there at all" is a lookup; the overlay and the editor's unreachable-spot view (session 17) use it.
  - `findPath` (`nav/path.ts`) is A* with an octile estimate plus climb, on preallocated typed arrays (it allocates nothing but its output). It stops after 20,000 nodes. Between different components it heads greedily for the closest spot it can find, with a smaller budget, and says `partial`. The path is smoothed by walking straight lines cell by cell over links (`straight`), so it only turns where it has to.
  - **Doors (session 11c, see design.md → AI → Doors).** The grid is **built with every door open**, both ways in turn (only spots clear of both slabs are kept, since a door can swing either way), so the open slab is kept clear of and the closed doorway is walkable. It records which links cross each door's closed footprint; `setDoorLocked` clears or restores those link bits (so A*, `straight` and the components all see a locked door without any per-search check), and `updateComponents` renumbers. Closed, unlocked doors stay links: instead of the path follower knowing which links cross a door, an enemy moving along a path opens a closed, unlocked door within 1.2 m that the line to its next waypoint crosses (`openDoorAhead`, called from `updateAi`). **The components lookup is recomputed after an unlock** (decided 2026-10-26): about 11–13 ms for the test map on the Mac (perhaps 15–25 ms on the iPhone), one dropped frame at a rare, deliberate moment. If that hitch shows on the phone: unlocking only ever joins components, never splits them, so relabelling just the smaller side (a key room's few hundred nodes) is enough.
- **AI (session 7):** each enemy is an ordinary `Character` with `ai: AiState` (plain data: awareness, activity, timers, focus, patrol and path as flat number arrays), so the state still saves and restores as JSON. **AI writes a `PlayerInput` for its character**, which moves and shoots through the same code as a player's; an input passed to `step` for that entity overrides it.
  - `step(state, world, items, inputs, nav?)`: after moving, shooting and bleeding, `updateAi` runs, so it perceives this tick's positions and events (shots, hits) and acts next tick. Without a nav grid enemies stand still (tests and the perf scene).
  - Sight and footsteps are checked every 3 ticks, staggered across enemies; shot and hit events every tick. **At most 2 path searches per tick across all enemies**; the rest wait a tick. An enemy plans again when its goal moves more than 1.5 m, or after 1.5 s stuck (and gives up after 3 tries).
  - Bodies push apart after everyone moves (`separateCharacters`, every pair, then out of walls).
  - **Combat (session 8):** `updateAi(state, world, items, nav)` (it needs the items for gun stats). Fighting is more activities in the same state machine (`engage`, `takeCover`, `cover`, `peek`, `hold`, `loiter`), with the extra state in `AiState` as plain numbers, so a save mid-fight restores exactly (tested). The enemy's skill is copied from its type into `AiState.skill` at spawn, so the state doesn't depend on content files. Its aim error wanders as a smooth function of the tick and a phase per enemy, so it needs no RNG per tick.
  - **Cover search** samples 12 random nav nodes within 10 m and keeps the nearest one that's hidden from the threat's eye at crouched-eye height, at its centre and 0.4 m either side (up to 4 raycasts per candidate, and a candidate further than the best so far is skipped before any raycast). **At most 1 cover search per tick across all enemies**, like path searches. Before each shot an enemy casts one ray through the characters to check no ally is in the way, and one through the world to choose chest or head.
  - Reachability is a components lookup (`nav.nearest` for both, then compare), every perception tick while alert. The way up to an unreachable target is the end of a partial path towards it.
  - **Factions (AI rework session 1, 2026-11-07; `sim/factions.ts`):** `AiState.faction` (missing in older saves: scav). `hostile(a, b)`: a player and any enemy (zombies too); never two players; never a zombie and another AI; scav and boss are allies; a PMC is hostile to every other enemy, other PMCs included unless they're in the same squad (AI-3). Sight (`look`) notices any hostile character, so enemies fight each other on sight and pick up targets that are other AI; `alarm`, cover, aim and the rest already worked on any `Character`. Damage and fire from a hostile alarm it as a player's do. A shot from an ally goes to `allyShot` (join the fight, as before, only towards a target hostile to the listener); a hostile enemy's shot is heard exactly like a player's (near miss and the 15% tier alarm it to the shooter, the rest is a noise to check). **Footsteps stay players' only**, so enemies don't track each other down. The 2-responder cap counts only the listener's allies. `clearOfAllies` holds fire only for an ally in the way; `byAlly` (was `byEnemyOnEnemy`, `sim/health.ts`) cancels only allies' hits.
  - **Hearing scale:** `SimState.hearingScale` (missing is 1), set from `CompiledMap.hearingScale` (`MapFile.hearingScale`, optional, so the map format stays 4) when a raid starts. `hearEvents` multiplies every shot's, blast's and pane's `loudness` by it; footsteps' fixed ranges aren't scaled. Editor: a number field under the spawn clearance. Northpoint is 0.6.
  - **Cost (measured 2026-11-07, Mac, Node 22):** 20 armed AI on Northpoint (14 scavs at its enemy spawns, 6 PMCs at player spawns, nobody meeting): `step` 0.10 ms a tick on average, `updateAi` 0.04 ms (worst 0.5 ms). 10 scavs and 10 PMCs in open view of each other 30 m apart on flat ground, fighting to the end: `step` 0.075 ms on average, worst 1.8 ms, against a 33 ms tick. No extra staggering needed; `perceiveEvery` stays 3.
  - **Scav waves (AI rework session 2, 2026-11-07; `sim/waves.ts`):** `startEnemies(state, world, map, items, { types, loadouts, tables, patrols })` replaces the client's own spawning: it rolls the enemy spawns as `rollEnemySpawns` did, puts every non-scav in, makes a `WaveSlot` per scav sector (`spots`, `entity`, `due` tick) and starts a third. Everything later spawns need (types' skill, faction, outfit count and loot, loadouts, loot tables, patrols) is copied into `SimState.waves` (`WavesState`), as zombies mode copies its rules, so `step` needs no content and a saved raid keeps its queue. `updateWaves` runs in `step` after the AI: the trickle every tick (reads this tick's `shot` events into `waves.gunfire`), slots once a second. Its spot check is one ray per living player per candidate spot, and only when a slot is due. A spawn radius that lands somewhere seen or too close puts the scav back on its spot. `SimState.waves` is null without scav spawns and missing in older saves (no waves, as before). Tuning in `SCAV_WAVES`; a map's optional `scavStartShare` (`MapFile`, compiled into `CompiledMap`) overrides the start share.
  - **`Character.look`** (`{ type, outfit }`, set by `spawnEnemy` when given a `type`) replaces AI-1's `AiState.outfit`. Co-op guests aren't sent `ai` (or `waves`), so the look has to be on the character for them to draw the right outfit and draw enemies that arrive mid-raid. The client draws any character with a look it hasn't drawn yet, every tick (`drawNewEnemies` in `play/index.ts`), host and guest alike. `Welcome.spawned` is gone; `RaidSnapshot.enemies` is optional and read only for raids saved before looks.
  - **Erratic and narrower sight:** `EnemySkill.erratic` (0–1) and `fov` (degrees), both optional. `quirks` in `sim/ai.ts` runs at the end of `behave` and changes only that tick's wish and stance, with `AiState.quirk`, `quirkTime` and `quirkNext` (missing in older saves). A stop resets `stuck`, so it isn't taken for being stuck.
  - **PMC squads (AI rework session 3, 2026-11-07; `sim/squads.ts`, squad AI in `sim/ai.ts`):** a map's optional `pmcs` (`{ enemy?, count: [min, max] }`, `MapFile` → `CompiledMap`; the format stays 4) makes `startEnemies` call `startSquads`: `squadSizes` splits the count into squads of 2–4, `pickSpawn` gives each an unused player spawn (none within 30 m of or seen by a living player, by `playerDistance`, moved here from `waves.ts`; preferring 60 m+ and 50 m apart and out of sight of the other squads), and the members spawn straight from the content (not through `SimState.waves`: they don't replenish), leader on the spawn and the rest at their formation places when clear. RNG is drawn only when a map has `pmcs`, so other maps' seeds play as before.
    - `AiState.squad` (the first leader's entity id) and `squadSlot` (0 leads), both missing for lone enemies; `hostile` makes two PMCs of the same squad allies, so allies' shots, `byAlly`, `clearOfAllies` and the responder cap all apply inside a squad for free. `joinSquad(c, squad, slot)` sets them. `squadLeader` is the living member with the lowest slot; a follower that finds its leader gone and itself next (`leadSquad`) takes slot 0 and guards where it stands.
    - **`follow`** activity: what `calmDown` gives a member with a slot over 0. `followSpot` (perception ticks only, and only while the leader moves or the place isn't set) puts it at `SQUAD.formation[rank]` (back, side, watch angle) from where the leader will be in 0.6 s, by the leader's heading (its home yaw while it guards, so it doesn't shuffle); else straight behind; else 2.5 m from the leader on its own side. `standable` checks height, overlap, a clear line from the leader and no drop half way (4 rays/queries at most). A turn of over 120° swaps a follower's sides (`followYaw`, `followSide`) so the squad doesn't cross over. Pace is `patrolPace + 0.1 × metres off`, up to `alertPace`. Once it gets as close as it can, that spot is its place until the leader moves (otherwise a place off the nav grid replanned every tick: it cost 1 ms a tick on average on Northpoint before the fix).
    - **Shared awareness:** `shareTarget` on a member's perception tick while it's alert and sees its target (or lost it under `AI.intuition` ago): mates not alert are `alarm`ed to it, mates fighting it out of sight get its position as their focus. **A follower's noise goes to the leader** (`tellLeader`, when its `look` ends wanting to investigate): the leader checks it unless fighting or already checking something, and the follower goes back to following.
    - **Cost (Mac, Node 22):** Northpoint, 10-minute raids from all 9 spawns with 3–6 PMCs and the scavs, nobody fighting: `step` 0.06–0.11 ms on average, worst 1–3 ms (one 15 ms outlier). A squad of 3–4 fighting you at 10–25 m: 0.07–0.3 ms on average, worst 6 ms warm.
  - **PMC routes, looting and extracting (AI rework session 4, 2026-11-07; `sim/routes.ts`, behaviour in `sim/ai.ts`):**
    - **`poi` marker** (map format stays 4: a new optional node): `kind` `loot` or `choke`, `weight` (default 1), `radius` (default 8 for loot, 2 for a choke). A `CompiledMarker` like the others; in the editor's marker tool for extraction maps, with kind, weight and radius in the inspector, drawn teal by the debug overlay.
    - **State:** `SimState.pois` (the map's, copied in by `startPois` from `startSquads`) and `SimState.squads` (`SquadState` per squad: current `stop`, `visited`, `extract` and a standing spot in it, `leaveTick`, `leaving`, `looted` container ids, `kills` to search). Missing or empty pois (older saves, maps without any) leave squads guarding as in AI-3: a squad only gets a `SquadState` when its map has pois, and the leader's `guard` switches to `route` only when it has one. All plain data, so a saved raid resumes its routes.
    - **Activities:** `route` (the leader: `walkRoute`), `loot` (any member: `lootStep`), `extract` (every member, standing in the zone). The leader's `wait` at a choke ends with `endStop`. Followers join the leader's searching at a loot stop (`joinLeader`, on perception ticks: the nearest unclaimed container in the stop's radius) and go into the extraction with it from within 20 m. `AiState.loot` (`LootTarget`: search key, position, seconds left searching), `reroute`, `hunt`, `legTries`, `detour`/`detours`, `unstick`/`unstickSide`: all optional.
    - **Stops:** `pickStop` weights each poi by `weight` × a walk factor (full from 15 to 70 m, less nearer, (70/d)² beyond), visited ones ×0.2, never the one it just left, and only those in its nav component. `nearestStop` after a fight or a check (`reroute`); `stopToward` for far gunfire.
    - **Looting:** `pickContainer` (in the stop's radius and 2 m of its height, not looted by the squad or seen searched and empty, not claimed by a mate, reachable), `pickBody` (its kills within 40 m). Searching takes 0.6 s an item (at least 1.5 s), then `searchContainer` (the searched look and event, as a player's) and `takeLoot`: the most valuable for its size first, into rig then backpack, by `addItem`; worn gear is never touched, its own or a body's.
    - **Leaving:** `updateSquads` (after `updateWaves` in `step`) counts `Character.extracting` for members in `extract` inside their zone (`inExtraction`), and after `RAID.extractTime` takes them out of `state.entities` in place with a `leave` event (not into `state.left`, which is players'). The client draws out any enemy no longer in the state (it did that only in zombies mode), and `EnemyBars.remove` drops its bar. `chooseExtraction` keeps only zones whose standing spot is in the leader's nav component *now* (`syncDoors` updates components for locked doors), always-open first.

## Map and prefab format
Decided in session 4. The schemas are in `packages/shared/src/content/schema.ts`, whose comments are the field-by-field reference.
- **Files:** `content/maps/<id>.json` and `content/prefabs/<id>.json`. The `id` inside must match the file name.
- **Loading:** `loadContent(format, json, source)` checks `formatVersion`, runs the migrations from the file's version up to the current one (`migrations[v]` turns v into v + 1), then validates with zod. A file newer than the build is rejected. Objects are **strict**: an unknown field is an error, so typos are caught and a migration must remove fields it renames.
- **Units and conventions:** metres; **angles in degrees** in files (radians everywhere after loading); y up, yaw 0 faces −z. **`pos` is the middle of a shape's base**, so y is where it stands. Sizes are full sizes, not half-extents. Colours are `#rrggbb`.
- **A map** has `environment` (sky colour, fog near and far), `terrain` (origin, cell size, `heights` as rows along +z of corners along +x, one ground colour), optional `water` (level, colour, opacity), optional colour slots, `nodes` and `zones`.
- **Nodes** (in maps and prefabs alike, told apart by `type`):
  - Shapes: `box`, `cylinder` (a `radiusTop` of 0 makes a cone), `ramp` (a wedge rising towards local +z), `stairs` (drawn as steps, collides as a ramp; optional `sides` (2026-11-03) adds a 0.1 m solid side wall each side whose top is one straight slope that far above the steps, a box plus a wedge each, drawn only) and `ladder`. All collide unless `collide: false`. **A box's `invisible: true` (2026-11-07, the user's request, to keep players in Northpoint's loading yard):** it isn't drawn, and it compiles to a blocker (`WorldDef.blockers`, after the barricades' so their order still matches) rather than a box, so movement and the nav grid respect it but shots, sight and throws pass through, and nobody sees a shot stop in mid-air over a low wall. It can't tilt, be a loot container or a switch, or have `collide: false` (compile errors). The editor draws it faint blue (`compileNodes(...).invisible`), pickable but not a surface to place things on, and the box panel has an "invisible" checkbox. Use it for map edges, 10 m high. **A box's `bulge` (2026-11-03, the user's request for bags of concrete, then per face):** `[−x, +x, bottom, top, −z, +z]` in metres, before turning; each face's middle is pushed out that far, making it a low pyramid of four triangles. Drawn only: it collides as the plain box, so keep bulges small. A bag of concrete bulges its four sides and leaves top and bottom flat. Optional, so the map format stays 3. **A box's `top` and `lean` (2026-11-03, for a jacket hanging from a hook):** `top` is the top face's `[width, depth]` (0 tapers to an edge or point) and `lean` moves its middle `[x, z]` from over the bottom's. Still 8 corners and 12 triangles, drawn only, collides as the plain box. `TriangleBuilder.poly` finds a face's normal from all its corners (Newell's method) so faces with corners that meet still wind the right way. The user wants everything kept low-poly: taper and bulge change outlines, never add curves.
  - **Boxes, cylinders, prefabs and groups tilt** (`pitch`, `roll`). A box or cylinder turns about its centre; a prefab or group (2026-11-05) turns about its `pos` with everything in it, its `Frame.tilt` carrying the whole turn down through the compiler. A tilted solid collides as a slab (see Collision). A door inside is a panel fixed shut, as doors only swing about y; ladders, glass, barricades and buildings inside are a compile error. An instanced prefab is flattened when tilted. The editor refuses to ungroup a tilted group, as ramps, stairs and walls have no tilt to take on; unpacking a tilted prefab gives a group with the same tilt. Pitch and roll are typed in; the gizmo stays yaw only.
  - `prefab`: a reference by id, with a position, a yaw (no tilt) and colour overrides. Prefabs can contain prefabs; a prefab that contains itself is an error.
  - `door`: width, height, hinge side, optional key item, starts open or closed.
  - `wall` (2026-11-02): a straight wall with its openings as data: pos (middle of its base), yaw, size (length along local x, height, thickness), colour, collide, and `openings` ({ along, width, bottom, top, glass? }: along is the middle's distance from the wall's middle; glass is a tint). Compiles (`content/walls.ts` → `wallPieces`) to boxes, the stretches between openings and each one's sill and lintel, and a glass pane for each glazed one (id `<path>/glass<k>`); an opening past the end or overlapping another is a content error. Doors aren't openings (they swing, and are their own nodes). A new node type, so no format change.
  - `glass` (2026-11-02): pos (bottom middle), yaw, size (width, height), thickness (default 0.02), colour. A new node type, so no format change.
  - `wire` (TU-2, 2026-11-09): barbed wire, pos (middle of its base), yaw, size; can't tilt. A new node type, so still format 4. It's neither drawn nor solid: `compileMap` puts it in `WorldDef.wires`, and `CollisionWorld.touchesWire(x, z, r, low, high)` tests an upright capsule against them (looped, not gridded: few maps have any). `snagOnWire` (`sim/wire.ts`), after moving each tick, starts a leg bleeding (which leg is a hash of the tick and the id, not the rng) and pushes a `wire` event when a character goes in, tracked by `Character.inWire` (optional). Not for one health bar or infinite health. The `barbed-wire` prefab draws a 1.2 m coil with one inside it.
  - Markers: `playerSpawn`, `enemySpawn` (enemy type, loadout, loot weight multipliers, optional `patrol`), `lootContainer` (container type, loot table), `lootSpawn` (loot table, optional `chance`) `questMarker` (id required) and `poi` (PMC routes: `kind`, `weight`, `radius`; AI-4); until map format 4, `extraction` (name, radius), now a zone's `extraction: { y }`. Enemy types, loadouts, loot tables and keys are plain ids for now; they're checked against their own files once those exist.
  - `patrol` (session 7): a required `id`; `points` (at least 2, in the enclosing frame), each either a plain `[x, y, z]` to walk through or a stop `{ pos, wait, radius }` (wait defaults to 3 s, radius to 0); `repeatFrom` (default 0: the points before it are the way in, walked once; at least two must repeat); and `loop` (default true; false walks back and forth over the repeating points). An `enemySpawn`'s `patrol` names a patrol **beside it** (in the same map or prefab), so a prefab can carry its own guard and route; it compiles to the patrol's path id, and a missing one is an error. `enemySpawn.radius` spawns at a random clear spot within it. `CompiledMap.patrols` has them in world space, every point as `{ x, y, z, wait, radius }` (walk-through points have 0 and 0).
- **Format 2** (session 7) added patrols, for maps and prefabs alike; 1 → 2 changes nothing.
- **Named zones** are polygons in x, z, at map level only.
- **Colour slots (recolouring):** a prefab declares slots with default colours (`"colours": { "paint": "#c0392b" }`), and its shapes use either a hex colour or a slot name. A placement overrides slots, and an override can name a slot of the enclosing prefab or map. Overriding a slot the prefab doesn't have is an error.
- **Ids:** any node can have an `id`, unique among its siblings. Markers and doors come out of compilation with **path ids**, the ids from the map down joined by `/` (for example `house-a/desk`); a node without an id is `#` and its index. Anything other content refers to (quest markers, keyed doors) should have an explicit id.
- **Compilation:** `compileMap(map, prefabs)` (in shared, so the server can use it for co-op) flattens everything into a `CompiledMap`: the `WorldDef` for collision, world-space shapes to draw, instanced groups, doors, markers and zones.
- **Buildings (session 16):** a prefab's optional `building` (`size` as width and depth, optional `centre`, optional base `colour`, a hex colour or slot) makes it a building whose floor is its y = 0. `compileMap` gives each placed building a **concrete base** (`concreteBase`): a box under the footprint from the floor down to 0.3 m below the lowest ground under it (`groundUnder` samples every half metre or less), drawn and collided with like any box; none if the ground is nowhere below the floor. `CompiledMap.buildings` has the footprints in world space. The format stayed 3, the field being optional.
- Deferred: per-cell terrain colours (roads, dirt) and scaled prefab placements. Both can be added later with a migration.


- **Switches (2026-11-05, map format still 3: new optional fields and one new node):** `switch: { name?, useTime?, rows: [{ opens, timer?, noise?, lasts?, openNoise? }] }` on a box, cylinder, group or placed prefab, compiled like `loot`: its solids are what you aim at, in `world.switches` (`SwitchDef`, reach 2 m from their edge). `opens` is a door's id beside the switch, else its path id in the map; a row naming no door fails the compile, and a door named by a row is `switched`, so locked. `lasts` defaults to `timer`. The editor's `doorTargets` lists doors in placed prefabs too and gives whatever holds the door an id on linking (`linkSwitch`), as a `#index` path breaks when the list changes.
  - **Sim (`sim/switches.ts`):** `state.switches` (used, by index) and `state.noises`; the timer lives on the door (`DoorState.opening`, `openingFor`, `openSound`), so the gate, lamp and mover all read one number (`openingProgress`). `PlayerInput.switch` is sent while the use button is held, merged for co-op guests; `holdSwitch` counts `useTime` on `Character.switching`, which starts over on letting go, looking away or leaving reach, and the HUD's `#use-ring` reads it. Events `switch` and `doorSwitched`. Noises are client sounds (`SoundCues.noises`, repeated end to end, centred, 0.5–1 gain by distance over 80 m), with no part in the AI's hearing.
  - **Door fields:** `rollUp` (a look that's drawn rolling up: scaled from its top) and `lamp` (`pos`, `size` in the door's frame, one draw call). A door with a look `vanishes` when a switch opens it, and nav leaves out its swing, as for a door with a cost.
  - **`mover` node:** `prefab`, `travel` (its own frame), `door` (beside it). `CompiledMover`, one mesh each, moved by `updateDoors` and hidden on arrival. Drawn only, so what it arrives as must already be solid in the map; `compileNodes` draws it where it starts.

## Enemy types and loadouts
Session 8. The schemas are in `packages/shared/src/content/enemies.ts`, whose comments are the field-by-field reference. Loaded like items (`formatVersion` 2 for enemies since AI-1, 1 for loadouts; strict zod objects, the id must match the file name).
- **`content/enemies/<id>.json`:** `name`, `loadout` (the default loadout id) and `skill` (`reaction` s, `aimError` and `aimSettled` degrees, `aimSettle` s, `holdChance` 0–1).
- **`content/loadouts/<id>.json`:** `weapons` (at least one: `weight`, `item`, `spare` as `[min, max]` rounds, optional `attachments` as `{ item, chance }` where the first to roll in a slot wins), and optional `helmets` and `bodyArmour` (`weight`, `item` or `null` for none, optional `condition` as a `[min, max]` fraction of full durability), and since AI-6 optional `grenades` (`weight`, `item` or `null`, optional `count` as `[min, max]`). Each part is picked by weight on its own.
- `checkEnemies` checks the references (loadouts exist, items are the right type and slot, attachments fit their gun); the client checks each map's enemy spawns name a type and loadout that exist. Both run in the client's content test.
- `equipLoadout(c, items, loadout, rng)` (`sim/loadout.ts`) rolls one onto a character, using the sim's RNG so a raid's rolls come from its seed.
- **Enemy loot (session 11):** an enemy type's optional `loot` is `rolls` (`[min, max]` items) and `tables` (loot table id → weight). Each item picks a table by its weight times the spawn's `lootWeights` for it (1 if not given; a weight of 0 turns a table off), then one item from it. The format stays 1, since the field is optional.
- The client's content test also checks that every locked door's `key` is a key item.
- **The tutorial's flags (TU-2, 2026-11-09; map format still 4, loadout still 1):** an `enemySpawn` may have `deaf`, `passive`, `harmless`, `once` and `noLoot` (each `true` or left out). They become `AiState.deaf`/`passive`/`harmless` (through `EnemySpawnOptions` and `WaveSpot`). **Deaf** skips `listenForSteps`, `listenForHands` and every event in `hearEvents` but damage, ignite and death. **Passive** skips `look` too, until a damage or ignite event from a hostile deletes it. Both keep it out of the trickle (`freeToCheck`). **Harmless** sends its hits down `woundZone`'s infinite-health branch: a `damage` event of 0 and the aim punch, no HP, armour wear or bleed (burning isn't covered; no harmless enemy carries fire). **`once`** spawns it at raid start like a boss, so a scav there isn't a wave slot and never respawns; **`noLoot`** skips `rollEnemyLoot`. A loadout's optional **`carried`** (`{ item, count? }`) is stowed right after the rig and backpack, before grenades, so it lands in the pockets: the tutorial scav's key.
- **Format 2 (AI rework session 1, 2026-11-07):** `faction` (`scav`, `pmc` or `boss`, required) and `outfits` (a list, at least one; a plain default if left out) in place of `outfit`. The 1 → 2 migration makes a file a scav and puts its outfit in a list; `boss-scav.json` was rewritten as a boss. `spawnEnemy` takes `faction` and `outfits` (the count) and rolls the outfit's index with the sim's RNG, only when there's more than one, so one-outfit types draw nothing and older seeds play the same. The client draws `type.outfits[c.look.outfit]` (`outfitOf` in `play/index.ts`), so co-op guests and a resumed raid see the same look (in `Character.look` since AI-2; it was `AiState.outfit`, which guests never got). Zombies keep their single `outfit`.

## Loot tables and raid configs
Session 11. Loaded like the other content (`formatVersion` 1, strict zod objects, the id must match the file name).
- **`content/loot-tables/<id>.json`** (`content/loot-tables.ts`): `name`, `rolls` (`[min, max]` items for a container) and `items`, each `{ item, weight, count? }` where `count` is a `[min, max]` only for items that stack. `checkLootTables` checks the items exist and counts stay within a stack; `checkEnemyLoot` checks enemy types name tables that exist. The client checks every `lootContainer` and `lootSpawn` marker and every spawn's `lootWeights` names a table.
- **Rolling** (`sim/loot-roll.ts`): `fillLootContainers` fills the containers `placeLootContainers` placed, and `rollEnemyLoot` stows an enemy's loot in its pockets, rig and backpack after its loadout. Both use the sim's RNG, so a seed gives the same loot. A rolled item is a new one (`createItem`): a gun comes with a full magazine and no attachments. What doesn't fit is left out. `byWeight` moved to `rng.ts` for loadouts and loot alike.
- **Loose spawns (session 11b):** `rollLootSpawns` puts one item from each `lootSpawn` marker's table on the ground (`SimState.ground`), if the marker's optional `chance` (0–1, default 1) rolls. The map format stays 2, since the field is optional.
- **`lootSpawn.oneOf`** (2026-10-30): an optional id naming a set of spots; `rollLootSpawns` first picks one spot per set with the raid's RNG (in marker order, so a seed gives the same pick), then rolls only that one's chance. Names are map-wide, not scoped by prefab. The format stays 3, the field being optional. The map editor shows it as "one of".
- **Loot mixes and container kinds' loot (2026-11-02, the user's request):** a `LootMix` (`content/schema.ts`) is `tables` (table id → weight), an optional `empty` weight, and `each`. Without `each`, a container picks one table (or nothing) by weight and rolls that table's `rolls` (a house fridge: household 80 / parts 20); with `each`, it takes the rolls of a table picked by weight and picks a table (or nothing) for every item, so one container holds a mix. A container's loot is its own `mix`, else its one `lootTable` (as before; a one-table mix rolls exactly as the old table did, same RNG draws), else its kind's default `loot` (`content/loot-containers/<id>.json`, optional, so the format stays 1). `lootTable` became optional on `lootContainer` markers and on a node's `loot`; the map format stays 3. `containerMix` resolves it, `rollMix` rolls it, and `fillLootContainers` now takes the kinds. The client checks every container resolves to loot whose tables exist (`checkLootContainers`), and every kind's tables exist (`checkLootKinds`).
- Quest items (session 14b) are put on the ground by `startQuests` (see Quests), not by loot tables.
- Not yet: named zones weighting loot.
- **`content/raids/<id>.json`** (`content/raids.ts`): `name`, `map`, and `duration` in seconds (15 minutes if left out). Every player spawn and extraction point in the map is used. It will grow a playable area, loadout rules, objectives and open extractions for weekly challenges.
- **`offline: true` on a raid (TU-2, 2026-11-09, still format 1):** played on the device only, never on the server: the client's `raidIds` (the raid list) and the item sources leave it out, and `POST /raids` refuses it as if it didn't exist. Only the tutorial's raid has it.

## Raid lifecycle
Session 11, `sim/raid.ts`. See design.md → Raids and maps → Extraction.
- `SimState.raid` (`RaidState`: the tick the timer runs out on, and the extraction points from the map's extraction zones since map format 4; before, its markers) is set by `startRaid`, and null outside a raid (tests, the perf scene), where nothing below happens. `Character.extracting` counts the seconds a player has stood in an extraction point (within its radius across, and `RAID.extractHeight` up or down).
- `updateRaid` runs last in `step`, after the tick count goes up. A living player who reaches `RAID.extractTime` (7 s) leaves; when the timer runs out, every living player still in the raid leaves as missing in action. **A player who leaves is taken out of `state.entities`** and kept in `state.left` (`LeftRaid`: the character with all its gear, how, where, and the tick), with a `leave` event. So nothing can shoot or follow them, and enemies who were after them calm down (they already handle a target that no longer exists). Enemies never leave. The dead stay in `entities` as bodies.
- `gearItems(gear)` lists everything a character carries; `keptItems(gear, survived)` is what a player keeps (everything after extracting; otherwise the knife and the vault). Session 12's raid end will send these.

## Zombies mode
2026-11-04, `sim/zombies.ts` and `content/zombies.ts`. See design.md → Zombies.

The client's `loadZombies` checks the map, its zombie spawns, the kit, the claws, the box's guns and that the minigun has `infiniteAmmo`.

The wall's opening is authored separately to match. A door may have a **`cost`** instead of a `key` (not both): it starts locked, and `useDoor` buys it with points (`bought`, or `poor`), setting `DoorState.gone`, which `syncDoors` passes to `CollisionWorld.setDoorGone` (its solid moved away, as broken glass's is) and the renderer hides; a gone door can't be used. A door's **`look`** (a prefab id, compiled into `CompiledDoor.look` shapes in its frame) draws it as that instead of a slab, never swinging: the couches. Its `size` and `thickness` are still its solid, so they're made tall enough not to vault. **`name`** is what the use button calls it ("Clear the couch"). All are in the map editor's marker tool, which draws barricades boarded up full. **A barricade is placed by clicking a wall** (2026-11-05, after one placed on a wall face came out buried in it, invisible): it goes in the middle of the wall's thickness at the sill (a window's own sill and size if clicked in a wall node's opening, else 0.9 m and 1.4 × 1.1 m), facing the side clicked; anywhere else it goes where clicked as before. The editor also draws its opening's outline and an arrow pointing inside through walls, since the wall hides the planks until it has a window to match. **Outside a zombies game** (a play-test of a map with barricades but no zombie spawns), barricades are still drawn, boarded up full (`barricadeWindows`), as their blockers are still there. **The marker tool's mystery box comes with its box** (2026-11-05, the user's request): it places a group named "Mystery box" holding the `mystery-box` prefab (Two Rooms' box: a dark base, a purple box and a gold lid, slots `wood-dark`, `paint`, `glow`) where clicked, and the marker 1 m in front of it, facing it, as the game expects; the box can still be any geometry. **The editor's zombies checkbox** (2026-11-05, the user's request), beside the marker picker, swaps which markers it offers: an extraction map's (enemy spawns, patrols, loot containers, loose loot, extractions, quest markers) for a zombies map's (zombie spawns, barricades, wall guns, the mystery box); player spawns and doors are in both. A door shows its key in an extraction map and its points cost in a zombies one (either still shows if set). It's an editor setting, not saved in the map: it starts ticked when the map already has any zombies-only marker. **Play ▸ on a map with zombie spawns plays a zombies game** (2026-11-05), with the rules and kit of the zombies mode that uses the map (else the first mode's); the editor refuses to play-test a map with no player spawn unless it starts at the camera target. A zombies map has no extraction (the content test expects one only on maps without zombie spawns).

## Item format
Started in session 6 with what combat needs; session 6b added attachments (format 2), session 9 the rest of the item types and grid sizes (format 3), and session 10b draw times and the knife's stats (format 4). The schema is `packages/shared/src/content/items.ts`, whose comments are the field-by-field reference.
- **Files:** `content/items/<id>.json`, one item each, loaded like maps (`formatVersion`, migrations, strict zod objects). The `type` field picks the kind: `weapon`, `ammo`, `armour`, `attachment`, `med`, `container`, `melee`, `grenade`, `key`, `quest`, `loot` or `repair`.
- **Every item** has `size`, `[width, height]` in grid cells, unrotated. Only `ammo` (required) and `loot` (optional) have `stack`, the most in one cell.
- Format 2 → 3 (session 9) guesses a size from the type (rifle-held guns 4×2, pistols 2×1, helmets 2×2, body armour 3×3, anything else 1×1) and gives ammo a stack of 60.
- **med:** `effect` (`bandage`, `splint`, `surgery` or `heal`), `useTime`, `uses` (default 1; not for heal) and, for heal only, `hp` (its pool). One effect per item keeps the heal button's choice simple.
- **container:** `slot` (`rig` or `backpack`) and `grid`, the size inside. **key:** optional `uses` (session 11c; an item instance keeps what's left in `left`, like meds); no format change, as it's optional. **quest** and **loot** have nothing else yet.
- **melee** (the knife, format 4): `damage`, `level` and `armourDamage` (format 9, as for ammo), `bleedChance`, `swingTime` (seconds between swings), `reach` (metres from the eye) and `drawTime`.
- Format 3 → 4 (session 10b) gives weapons a `drawTime` by hold (pistol 0.4 s, otherwise 0.8 s) and melee items the knife's first-guess stats. **repair:** `points`, the durability it can restore in all (used from session 13).
- **Format 4 → 5 (session 13b):** every item has a **`value`** (whole money, 0 or more: what vendors sell it for; see design.md → Economy); **loot** may have **`money: true`** (cash: deposited at full value); **repair** gained **`useTime`** (seconds, in a raid). The migration guesses a value by type and gives repair kits 8 s; the content files set their own.
- **Sounds (format 7, session 19):** `weapon` has `sounds: { shot, suppressed, reload }`, `melee` `{ swing }`, `med` and `repair` `{ use }`, each a sound file's id (`content/sounds/`). `defaultSounds` gives the first ones by hold or effect; format 6 → 7 uses it, as do blank and test items. `checkSounds` (`content/sounds.ts`) checks every sound an item names exists, and every sound the game plays itself (`GAME_SOUNDS`, client `audio/sound-ids.ts`); `loadSounds` runs it, and so does the item editor's `itemContentProblem`. The server doesn't load sounds. The content files were rewritten at format 7, except `assault-rifle.json`, which had the user's uncommitted edits (the migration gives it the same sounds); it was brought up to format 8 with the rarities, its sounds written in and its model edits left as they were.
- **Rarity (format 8):** every item has `rarity`: `common`, `uncommon`, `rare`, `epic`, `legendary` or `mythic` (`RARITIES`; the two new ones stayed at format 9, as no file changes), after `value` in the files. Format 7 → 8 makes them all common; blank items start common. The client colours tiles by it (`colourOf` in `ui/raid-screen.tsx`, also the vendors page and the item editor's swatches); the item editor has a picker. Nothing else reads it yet (loot tables and prices could later).
- **Levels (format 9, 2026-10-30; design.md → Ammo and armour levels):** `ammo` has **`calibre`** (any string; guns fire every round of their own round's calibre) and **`level`** (1–`LEVELS`, 6), and `armourDamage` is now required and means **durability per hit** (per pellet). `armour` has **`level`** in place of `absorb`. `melee` has `level` and `armourDamage`. Format 8 → 9 makes each old round its own calibre at level 1 with armour damage ×10, guesses armour's level from `absorb` (×6, rounded), and gives knives level 1 and armour damage 5. `calibreOf` and `firesRound` (`content/items.ts`) answer which guns fire what. The hit itself is `shootCharacter` with `ARMOUR`, `throughArmour` and `armourWear` (`sim/health.ts`). Every item file was bumped by its version line only, so the diffs stay small; the rounds, armour and knife were rewritten.
  - **The round in a gun** is `Item.loaded` (an ammo id of its calibre), left out while it's the gun's own round, so saved guns stay valid. `WeaponState.reloadWith` is the round a reload in progress loads (`restGear` clears it). `loadedAmmo(items, gun)` reads it; `reloadRound(c, items, w, want?)` picks what a reload loads (the round asked for if carried, else the one loaded, else the highest level carried; no allocation). A reload of another round swaps: new rounds are taken first, then the old ones stowed, or dropped with no room. `PlayerInput.ammo` asks for a round with `reload`. Everything that counted a gun's rounds as `WeaponDef.ammo` (unload, magazine changes, sell price, `countItems`) uses `loadedAmmo`, and `checkProfile` refuses a `loaded` round the gun doesn't fire.
  - **Loading by drag:** the inventory action `{ type: 'load', gun, from }`. `loadKind(state, c, items, gun, from, instant)` (`sim/looting.ts`) says what it would do: `'reload'` onto the gun in hand in a raid (sets `reloading` and `reloadWith`, so `finishReload` takes the rounds from what's carried), `'load'` at once elsewhere, or null; `loadGun` does it. The stash calls `loadGun` with `instant` true. The client's `gunZone` gives rounds a `load` drop zone on any `data-gun` element and asks `loadKind` whether it's green, so the outline and the sim agree.
  - **Loadouts** may list `ammo` per weapon (`[{ weight, item }]`): the round it's loaded with and carries spares of; `checkEnemies` checks the gun fires each. AI reloads whenever `reloadRound` finds anything, so an enemy out of its own round switches to another it carries.
  - Client: `ui/levels.ts` (the level colours, `levelOf`), a level tag on ammo and armour tiles, the ammo readout's round name with its level colour, and the reload button's long press opening `HandsHud.showAmmoPicker` (removed 2026-10-30: rounds are chosen by dragging them onto the gun). ## Inventory model
Session 9. All in `packages/shared`, plain JSON-safe data like the rest of the state, so a co-op server can run it and the stash (session 13) reuses it.
- **`Item`** (`inventory/grid.ts`): one item or a stack wherever it is: `item` (the definition's id) and `count`, plus whatever its type needs: `durability` (armour), `left` (uses or HP left in a med, points in a repair kit), `mag` and `attachments` (guns), `grid` (rigs and backpacks). The sim's narrower types are Items with those fields required: `WeaponState` (which also keeps the reload and fire timers), `ArmourState`, `ContainerState`. So an item moves between a slot and a grid as the same object, with no conversion. `createItem` (`sim/create-item.ts`) makes a new one with the fields its type needs.
- **No item instance ids.** An item is found by its grid and index (or its gear slot). Nothing needs a lasting id yet: the heal button picks by state, not by a bound item. Add ids if co-op looting needs them.
- **`Grid`**: `w`, `h`, `containers` (whether rigs and backpacks may go in: true only for the stash and loot containers) and `items`, each with `x`, `y` (top left) and `rotated`. There's no occupancy array; overlap is checked against the item list, which is short. Operations: `findSpot`, `placeAt`, `addItem` (auto-placement with stacking), `dropAt` (drag and drop, merging stacks), `rotateAt`, `transfer` (double-tap), `countOf`, `takeFrom`, `removeAt`.
- **`Gear`** (`sim/gear.ts`) is `Character.gear`: `primary1`, `primary2`, `sidearm`, `knife`, `helmet`, `bodyArmour`, `rig`, `backpack`, `pockets` (4×1) and `vault` (2×3, null for enemies), and `hand` (which gun slot or the knife is out). **`heldWeapon(c)` is the gun in hand**; there's no separate `weapon` field, which would turn into a second copy after a JSON round trip. `equip` and `unequip` check what fits each slot; `switchHand` puts the gun away (its reload stops). `carriedGrid(gear, i)` walks pockets, rig and backpack by index, so `carriedAmmo` and `takeAmmo` (reloading) allocate nothing.
- **`attach` and `detach` return the rounds that no longer fit** the gun (a smaller magazine) for the caller to `stow`.
- **Meds** (`sim/meds.ts`): `treatments(c, items)` lists what the heal button offers, best first, as `MedRef`s (grid, index and item id); `useMed` applies one use. `Health` gained `splinted` per zone; `isBroken` is false for a splinted limb, but `dealDamage` still spills over from any limb at 0 HP.
- **Loadouts** gained optional `rigs` and `backpacks` (worn empty; since session 11 the enemy type's loot goes in them). A rolled gun goes in the sidearm slot if it's a pistol, otherwise the first primary, and the spare rounds are stowed (pockets, then rig, then backpack; what doesn't fit is left out). The format stays 1, since the new fields are optional.

- `equip` into the slot in hand starts a draw too (a gun dropped into your hands from the inventory). `giveWeapon` leaves it ready, for spawning.
- **The knife** (`sim/melee.ts`): a swing casts up to five rays from the eye (the look with recoil, then `MELEE.fan` up, down, left and right), each against the world and then characters within reach; the first that reaches a body part wins. It hurts through `shootCharacter`, which now takes a `Wound` (the damage, armour damage and bleed chance that ammo and melee items share) and a cause (`shot` or `melee`). A `swing` event (hit or miss, and where) drives the slash animations and impact puffs; there's no loudness, so AI hears nothing.

## Looting and inventory actions
Session 10. `sim/looting.ts` in `shared`.
- **Loot containers** are `SimState.loot`: each has its marker's path id, its kind (`content/loot-containers/<id>.json`: `name` and `grid`, format 1), its position and a grid that takes rigs and backpacks. `placeLootContainers` makes them from a compiled map. Dead bodies aren't copied anywhere: you loot their `gear`.
- **Inventory actions** go in `PlayerInput.inventory` and are applied at the start of `step`, before movement, each giving an `inventory` event with `ok`. So a co-op server can apply them in the same place, and the raid doesn't have to pause. An action names an `Owner` (`self`, a `body` by entity id, or a `container` by id), then a grid (`pockets`, `rig`, `backpack`, `vault`, or a container's `loot`) and index, or a gear slot, **plus the item id the sender saw**, so an action that has gone stale fails instead of moving the wrong thing. Reach (`LOOT_REACH`, 2 m across and up or down) and "the body is dead" are checked by the sim, not the UI.
- The client keeps one array of pending actions as the player's `inventory` input and empties it after each tick, so ticks allocate nothing.
- **Attachments (session 10c):** `attach` (`gun`, `from`: a loose attachment in a grid, or a `PartRef` (`gun`, `slot`, `part`) for one on another gun) and `detach` (`gun`, `slot`, `part`: the attachment id the sender saw, `to`: a `GridSpot` or null for what you carry). The gun can be anywhere you can reach: your slots or grids, a body's, a container's. A loose attachment is a plain `Item` made with `createItem`; on the gun it's only its id in `attachments`. When `attach` replaces a part, the old one goes where the new one was (same cell, either way round), else anywhere in that grid, else into what you carry. Rounds a smaller magazine hands back go into **the acting player's** carried grids, never the vault. From another gun (`movePart`), the second gun's old part goes onto the first if it fits there, else into what you carry, and both guns' handed-back rounds are checked together. Since session 11b, what has nowhere to go (the rounds, a displaced part, a part taken off into what you carry) is **dropped at the player's feet** instead of the action being refused, so `roomForRounds` and the undo are gone. Allocating here is fine: it's once per action, not per tick.
- **Items on the ground (session 11b, `sim/ground.ts`):** `SimState.ground` is a list of `GroundItem`s (the `Item`, its position and a yaw for drawing), plain data like the rest. The ground is an `Owner` (`{ kind: 'ground' }`); an item on it is an `OnGround` ref (its index in the list, plus the item id the sender saw, like grids), and a `Target` can be `{ owner: { kind: 'ground' } }`. So the existing actions cover it: `quick` from the ground to `self` picks up (the use button sends this), `quick` or `move` to the ground drops, and `move` from the ground to a gear slot swaps, leaving the old item where the new one lay. Each ground item must be within `LOOT_REACH` (`groundInReach`). `dropItem(state, c, item, world?)` places a drop 0.9 m ahead (or at the feet if a raycast at knee height finds a wall), scattered with the sim's RNG, on `world.groundAt` below; so `applyInventory` takes the world as an optional last argument, and `step` passes it.

## Client (`packages/client`)
- **Build tool:** Vite + TypeScript.
- **3D rendering:** plain three.js, not React Three Fiber, so the game loop and rendering stay outside React.
  - Static map geometry is **merged per chunk** (32 m): one mesh per chunk holding its terrain and every shape whose centre is in it.
  - **Hidden faces and flat ground (2026-11-07, for the phone):** `buildChunks` leaves out faces nobody can see (`render/face-cull.ts`): a face that, moved 1 cm out along its normal, is wholly inside one chunk box (not one with a smaller top), or wholly under the ground (checked exactly where the ground can bend, never over a hole or past its edge). Only the chunks' own shapes cover, since they never change. Flat ground cells drawn whole are merged into rectangles, each a fan from its middle to every cell corner round its edge, so nothing meeting it has a T-junction. Northpoint went from 486k to 305k triangles, and in view at the 95th percentile from 331k to 243k.
  - **Doors and searched looks batched (2026-11-07):** every door at rest (not swinging, rolling up or gone) is in one merged mesh, `MapView.doorBatch`, rebuilt only when a door starts or stops moving; a moving door draws its own mesh. The looks of containers with a searched look are one merged mesh per 32 m chunk, rebuilt when one of them is searched. Northpoint's draw calls in view went from 143 to 69 at the 95th percentile.
  - **Instancing is opt-in per prefab** (`"instanced": true`, session 4), for small props placed many times, like trees and crates. Each instanced prefab and colour set becomes one `InstancedMesh` for the whole map. Merging is the default because it costs no extra draw calls; instancing saves memory and load time but adds one draw call per group, and a group is culled as a whole.
  - Colour is stored per vertex, with each face direction shaded differently; materials are unlit (`MeshBasicMaterial`); distance fog. Static geometry has the shading baked into its colours. Instanced and moving geometry (doors now, characters later) uses `shadedMaterial()`, which applies the same shading on the GPU from the world-space normal, so it stays right as the object turns.
  - Each door is its own mesh, pivoted at its hinge, so it can swing open.
  - Content is bundled into the client with `import.meta.glob`; in dev, saving a content file reloads the page.
  - The camera's far plane follows the fog distance.
  - **The first-person gun is drawn in a second pass** after the world, with the depth buffer cleared, so it never pokes into walls (`render/viewmodel.ts`). One extra draw call. It's built from the item models (session 18b), with the arms (session 8b) in the same mesh: `gunModel` (`render/gun-model.ts`) puts each fitted attachment's parts on its mount, leaves out the gun's parts hidden by it, and takes the sight from the optic (mount + its sight point) and the muzzle from the muzzle device. Aimed, the gun sits so its sight is straight ahead of the eye. The bodies use the same `gunModel` and `knifeModel`.
  - The viewmodel rebuilds its one mesh only when the gun or its attachments change. **Optic reticles and the scope mask are one SVG overlay** (`hud/optic.ts`, rebuilt only when the optic changes), not 3D, so they cost no draw calls; while scoped the gun isn't drawn at all.
  - Tracers and impact puffs come from fixed pools (`render/effects.ts`): one line mesh and one instanced mesh, so shooting allocates nothing and costs two draw calls.
  - Recoil is simulation state, so the camera interpolates it between ticks like the eye position. **The sights don't (2026-11-04):** the gun, reticle and scope mask point with the last tick's recoil, since the next round fires with it; eased, they trailed it by up to 0.4° in an AKM burst, so rounds landed under the reticle. Only the view's share is eased.

Grids holding an item id that doesn't exist are skipped, so a forged result still gets `checkGear`'s error. So a size change in content no longer locks anyone out; the item editor's warning says things will move.
- **The vault as an item (2026-11-06, the user's call):** `content/items/small-vault.json` is a container with `slot: "vault"` (a third value of the container slot), and `VAULT_ITEM` (`sim/gear.ts`) names it. `Gear.vault` is still a plain grid, `GEAR.vault` in size (a content test keeps the item's grid the same), so nothing that reads the vault changed. The item is only drawn (`VaultSlot` in `ui/raid-screen.tsx`, with no ref, so no drag, details, selling or taking off). `canHold` refuses a vault-slot item in any grid, so it can't turn up in a stash, a bag or a crate even if content hands one out, and the admin page leaves it off its list. A bigger vault one day would mean storing which one a player has.
- **Grid sections (2026-11-06, the user's call):** a container's item file can list `sections` (`{ "at": [x, y], "size": [w, h] }`, inside `grid`, not overlapping; optional, so items stayed at format 10). `createItem` copies them onto the bag's `Grid.sections` as `{x, y, w, h}`, and `inGrid` (used by `isFree`, so `findSpot`, `addItem`, drops and swaps all follow) wants an item wholly inside one. A grid without `sections` is one section, as before; pockets, the vault, stash pages and loot containers have none. **Item positions stay in the one grid's coordinates**, so refs, actions, saves and co-op sync didn't change. The profile's grid shape accepts `sections`, and `checkGear` wants a bag's to match its def. `settleBags` (shared; the server runs it with `settleGuns` in `parseProfile` and on raid results) gives every worn or stashed bag its def's shape whenever it differs, through the same `reshape` as `settleVault`, so changing a bag's grid or sections in content no longer breaks saved profiles (the item editor's warning now says things will move instead). **Drawing** (`GridView` in `ui/raid-screen.tsx`): a sectioned grid is a `.inv-sections` box of absolutely placed `.inv-grid` boxes, one per section, `SECTION_GAP` (6 px) apart; each is its own drop target, with `data-at` holding its top-left cell, which `drag.ts` adds to the cell under the pointer. The gaps make a row with more sections slightly wider than one with fewer. The item editor shows how many sections a bag has but can't edit them yet: they're edited in the JSON.
- **Settings:** stored locally first (`localStorage`, key `mes.settings`) and synced to the account (session 12b, see Client → Settings sync). The schema is in `shared` (`settings.ts`), versioned like content files, and every field falls back to its default on its own, so a bad value never wipes the rest. `settings.ts` in the client is the store: changes save and apply straight away.
- **Pausing** (`app/pause.ts`): the game pauses for a reason (portrait, a menu, the page hidden). While paused the frame loop stops, every touch is let go, and the time away doesn't count as a frame. Co-op will need a different rule: the raid can't stop.
- **PWA:** web app manifest (`public/manifest.webmanifest`, landscape, standalone) and Apple meta tags, plus the Safari workarounds in design.md. The icons are placeholders drawn by a one-off script. **No service worker:** iOS doesn't need one to add to the home screen, and session 12b decided against one (see Client → Saving raids).
- **Audio:** Web Audio API, unlocked on the first tap (`app/audio.ts`: the first `touchend`, `pointerup` or key creates the context and plays a silent sample; later taps resume it after iOS suspends it). **Sounds are generated** with Web Audio (the user's call, 2026-10-30), not recorded samples (session 19).
  - **Sound files** (`content/sounds/<id>.json`, format 1, `packages/shared/src/content/sounds.ts`): `gain`, `range` (metres heard to), `pitchJitter` and `layers`, each `noise` (`colour` white, pink or brown) or `tone` (`wave` sine, triangle, square or saw, `freq` [from, to]), with `at`, `attack`, `hold`, `decay`, `curve`, `gain`, optional `drive` (tanh soft clipping), `filter` (lowpass, highpass or bandpass, `freq` [from, to], `q`) and `sweep` (how long the glides take).
  - **`audio/synth.ts`** renders a recipe to samples in plain TypeScript (seeded noise, a phase-accumulator oscillator, an RBJ biquad updated every 32 samples while gliding), not Web Audio nodes: the same in tests as on the phone, and done once per sound, so playing costs a buffer source. A sound peaking over 1 is turned down to fit; a content test keeps every sound under 1.5.
  - **`audio/sounds.ts`** (`SoundPlayer`, one for the game from `sounds()`, at the settings' volume): renders each sound the first time it plays (`prepare()` renders all at raid start, once audio is unlocked), then plays it as **buffer source → lowpass (only if muffled) → stereo panner (only if off centre) → gain → master**. 16 voices; when full, the quietest stops for a louder one; the same sound again within 20 ms is dropped. **`audio/spatial.ts`** (`place`) works out gain, pan and cutoff from the listener: (1 − d/range)² × 40/(40 + d), cutoff from 20 kHz to 700 Hz across the range, duller and quieter from behind, and 600 Hz and ×0.45 through a wall. Cheaper than `PannerNode`'s HRTF, and testable.
  - **`audio/cues.ts`** (`SoundCues`): after each tick, the sim's events and what it doesn't report become sounds: footsteps by distance walked on the ground (a step every 1.1 + 0.1 × speed metres), landing, ladder rungs, a reload or med starting, drawing, the extraction countdown and the two-minute warning. The listener is the player's eye and the controls' yaw. Each positional sound casts one ray (`CollisionWorld.raycast`) to decide if it's muffled. **The sim didn't change.**
  - Menus: a click on a button in `#ui` ticks (`main.ts`); `Stash.post` (buying, selling, pages, quests) plays money on success and a refusal on failure.
- **Item details (2026-10-30, design.md → Inventory and UI):** `ui/item-details.tsx` is the card; the inventory opens it for `InventoryController.selected` (a tap selects after `DOUBLE_TAP_MS`, unless a double-tap, a drag or a drop came first; `inspect` opens at once for right-click), and the vendors page for an offer (a `createItem` of it). The picture is `render/item-portrait.ts`: the item's model (a gun via `gunModel`, with its attachments) drawn once by **one small offscreen `WebGLRenderer`, made on first use and kept**, into a PNG data URL cached by item id (`gunKey` for guns). No WebGL, no picture: the card still opens. The price is `sellParts` (shared `vendors.ts`), which `sellPrice` now sums, so the breakdown can't disagree with what selling pays; `questsFor` (shared `quests.ts`) finds the quests whose hand-over or extract objectives name an item. `InventoryContext.quests` carries the quests in a raid and in the stash.

- **Session 16** (`editor/terrain.ts`, `editor/overlap.ts`):
  - **Terrain brushes** (`applyBrush`) work on a `Float64Array` copy of the corner heights while the mouse is down; the view redraws only the 32 m chunks touched (the terrain is one mesh per chunk, built with the same `TriangleBuilder.terrain` as play) and the bases. On release, `setHeights` writes the heights rounded to a centimetre and moves everything whose base was within 2 cm of the old ground by the change (patrol points one by one; groups' own positions never; buildings never), as one edit. The view rebuilds the ground (terrain, water, zones, sky) only when those change.
  - **Level and hole** (roadmap 19zm) are area modes of the same tool: a drag covers every cell the rectangle touches (`cellRect`, at least one), outlined with the brush's line, and letting go applies it (`levelCells`, `holeCells`) and redraws those chunks. `setHeights` takes the hole flags too and writes them as `terrain.holes`, `[i, j]` cells sorted by row (no field when there are none; an optional field, so still map format 3). Picking over a hole uses a copy of the terrain without holes, so a hole can be dragged over to fill it.
  - **Holes in the sim:** `HeightGridDef.holes` is cols × rows flags (`holeFlags` builds them from the file). `HeightGrid.heightAt` ignores holes; `holeAt`/`isHole` tell them. The terrain raycast skips hole cells, and a ray leaving a hole under the ground beside it hits the hole's side there (normal back along the ray, flat). `CollisionWorld.groundAt` over a hole is the highest solid below, or else `PIT_DEPTH` (60 m) under the lowest terrain, so falling through an empty hole kills by fall damage rather than falling forever. The nav grid adds no ground node over a hole and counts solids under one as surfaces (elsewhere, solids under the terrain are underground). The renderer leaves hole cells out of the terrain mesh.

- **Curve tool (2026-11-01, roadmap 19zl):** `editor/curves.ts`. The editor keeps the hole being placed as `EditorState.hole` (the floor's path, x, z), cleared by any edit or undo (`changed`), the tool or mode changing and Esc; its preview is a 32-sided see-through cylinder and the railing, wrapped in the groups between the scope and the floor so it shows in the scope's frame. `sameSlab` (overlap.ts) skips pairs of solids with the same top and bottom, 0.6 m thick or less. The editor draws with `Drawing.what: 'curve'` (points: centre, start), keeps the sweep in a private field (it changes on every mouse move, so isn't state), remembers the last centre per scope for the next to snap to, and previews with `setPreview` like walls.
- **Prefab browser (2026-10-30, roadmap 19zg):** `editor/prefab-browser.tsx`, opened by `EditorState.browsing`. `Thumbnails` (`editor/thumbnails.ts`) compiles a placement of the prefab at the origin, draws it with its own 160 px `WebGLRenderer` (alpha, `preserveDrawingBuffer`) from (1, 0.75, 1) framing its bounding sphere, and caches the data URL by the compiled shapes and doors.
- **Notes (2026-10-30, roadmap 19zh):** `content/notes/<map>.json`, `{ formatVersion: 1, map, notes: [{ id, pos, text, author, date }] }`. The save plugin serves `GET /__editor/notes?map=` (an empty file if there's none) and `POST /__editor/note` (`{ map, add: { pos, text } }` or `{ map, remove }`; Mac-only like saves), one change at a time; it names the author from `git config user.name` (else the login), dates it locally, writes it laid out and formatted like other content, and sends the `mes:notes` HMR event, which the editor and play-test listen for. Nothing in content.ts globs `content/notes`, so writing one reloads nothing and the game never sees them. `notes.ts` (client) fetches and changes them and makes the labels: canvas-text sprites with `depthTest` and fog off, `sizeAttenuation` off, render order 21. `startPlay` loads `dev-notes.ts` for `raid.map` in every raid when `import.meta.env.DEV` (a dynamic import a build drops), passing `DevHooks`: the scene, the player, and `screen(open)`, which counts in the frame's `cursor.want` like the raid screen, so the game lets go of the cursor rather than losing it; its note box stops keys and clicks from reaching the window's listeners; the editor through `EditorView.setLabels` (drawn on top in the cutaway's last pass too).
- **Session 18 (the item editor, `packages/client/src/item-editor/`):**
  - `/item-editor?item=<id>` (dev only, imported behind `import.meta.env.DEV` like `/editor`) is a React page with no 3D. `ItemEditor` keeps **every item file's JSON** by id (`itemSources`, the files as written, for their key order) and one undo history across them; a snapshot is the whole map of strings, so unchanged files cost nothing. A drag in the reticle designer is one undo step (`beginGesture`, `edit(…, true)`).
  - After each edit every file is parsed with `ITEM_FORMAT`; if all pass, **`itemContentProblem`** (`content.ts`) runs `checkItems`, `checkEnemies`, `checkLootTables`, `checkVendors`, `checkQuests`, every map's door keys, and `newProfile` + `checkProfile` for each starting kit, against the edited items (the other kinds are loaded raw, without the game's checks against content/items). Any problem blocks saving. `itemUses` lists what names an item (`item` fields, kit gear, door keys, guns' ammo, attachments' guns).
  - `storageRisks` (`risk.ts`) compares an item as saved with as edited, mirroring what `checkProfile` limits, and the page warns.
  - The **reticle designer** uses `reticleMarkup` from `hud/optic.ts` (the overlay's own SVG) and `aimedFov` for the person's size, so the preview is what the phone shows.
  - The map editor's form fields moved to `editor/fields.tsx` for both editors. The save plugin accepts `items/<id>.json` and watches `content/items`.
- **Session 19 (the sound editor, `packages/client/src/sound-editor/`):** `/sounds?sound=<id>` (dev only). `SoundEditor` is the item editor's state (every file's JSON, one undo history, gestures, checks, one save request) for sound files; `soundContentProblem` checks the items' and game's sounds are still there. `Audition` plays the open sound as edited with its own `SoundPlayer` (centred, or placed with `place`). The bound fields (`get`, `put`, `N`, `P`, `Row`, `Check`) moved from the item editor's panel to `editor/bound-fields.tsx` for both. The save plugin accepts `sounds/<id>.json`, and its layout keeps objects inside one-line list items on one line (a layer's filter) instead of breaking them.
- **Session 18b (models, `item-editor/model-*.ts`):** a **model** tab beside **stats** (the list's tab buttons). `model-panel.tsx` lists the parts (add box, cylinder or wedge; copy, mirror across x, delete) with each one's fields, and the item's points with x/y/z; `model-view.ts` is the 3D view, kept while switching items. **Build**: each part its own mesh at its place, picked by clicking and moved or turned with `TransformControls` (snap 0–5 cm, 0–45°; W, E), points as dots drawn on top, the sight line dashed; a drag is one undo step, and the view waits for the gizmo to let go before redrawing. What the item goes with is drawn but not pickable: the attachments chosen for each of a gun's slots (its hidden parts faint), the gun an attachment is previewed on (moved so the attachment stays at the origin), and the mannequin for worn gear. **Hip** and **aimed** use the game's own `Viewmodel`, field of view and `reticleMarkup` (only once every item passes its checks). `model-edit.ts`: `setSlots` keeps a gun's mounts and `hiddenBy` in step with its slots (a new slot gets the placeholder's mount), `fitPointsToSlot` an attachment's points with its slot. The model is edited in the item's JSON like everything else, so undo, checks and saving are unchanged.
- **Groups (map and prefab format 3, session 15):** a `group` node has an optional name, pos, yaw and its own nodes, and may hold groups. It only moves and turns what it holds: **it adds nothing to ids** (a marker's path id is the same in a group or out of one, so grouping never breaks a quest or a patrol reference), and ids must be unique across groups. An unnamed node in group #3 gets `#3.<index>`. Unlike a prefab, a group is in the map file itself.

## Server (`packages/server`)
- **Cloudflare Workers (free plan)** with **Hono** for routing and **D1** (SQLite) for accounts, stash, vault, quest progress and vendor state.
- **Responsibilities:** accounts and sessions, profile and stash persistence, starting and ending raids (raid results go through sanity limits), vendor transactions, quest state.
- **Solo raids run entirely on the phone.** The server only sees the start and the result.
- **Co-op (later), decided 2026-10-31 (the user's call): a player's device hosts.** The host's browser runs the shared simulation (as for a solo raid) and the others connect over WebRTC data channels. The Worker only does signalling (the offer and answer, through the party) and makes short-lived TURN credentials; STUN is `stun.cloudflare.com` (free) and the relay is Cloudflare Realtime TURN (1,000 GB a month free). Phones and PC browsers mix. Replaced the earlier plan of one Durable Object per raid: the free plan's 100,000 requests a day count every incoming WebSocket message (a few raids a day), and its CPU limit for Durable Objects is unclear. Measurements and details in [coop.md](coop.md) → Cloudflare check.
- **Free-plan limits are hard caps:** going over makes requests fail until midnight UTC. Nothing is charged.
- **Built in session 12** (`packages/server/src`): Hono routes `auth.ts` (register, login, logout, the `signedIn` middleware), `profiles.ts` (GET and PUT `/api/profile`) and `raids.ts` (POST `/api/raids`, POST `/api/raids/:id/end`). The request and reply types, `ACCOUNT` rules and `ApiErrorCode`s are in shared `protocol.ts`; an error is `{ error, message? }` with a 4xx status (`errors.ts`).
  - **D1 schema** in `packages/server/migrations/` (`accounts`, `sessions`, `profiles`, `raids`). `npm run db:migrate -w @mes/server` applies it locally; `predeploy` applies it remotely. Times are Unix milliseconds.
  - **The profile is one JSON document** (shared `profile.ts`, `PROFILE_FORMAT` with migrations like content): `money`, `stash` (pages of 10×30 that hold containers: format 2 since session 13, which migrates format 1's one grid into the first page; `PROFILE.pagePrices`, `nextPagePrice`, `buyStashPage`), `quests` (format 3 since session 14; see Quests; format 4 in session 19za only renames item ids, `ammo-556` → `ammo-762x39` and `mag-556-45` → `mag-762x39-45`, in grids and fitted attachments; format 5 (2026-11-05) renames reshaped rounds the same way, `ammo-45acp-match` → `ammo-45acp`, `ammo-762x54r-t46m` → `ammo-762x54r-hpbt`, now also in a gun's `loaded`; format 6 renames `pistol` → `m9a3` and takes off any optic on one, since the M9A3 has no optic slot; format 7 renames `sniper-rifle` → `sv-98` and drops its `loaded`, as the SV-98 fires 7.62×54R) and `gear` (the sim's `Gear`, vault and knife included). It's always read and written whole, with a **version** that goes up on every write; writes are `UPDATE … WHERE version = ?`, and a batch's other statements check the same version, so two devices can't interleave (the loser gets `stale`). `checkProfile`/`checkGear` are the sanity limits (design.md → Trust model), `itemGained` the "no items from nothing" rule, `restGear` puts guns down before storing. New accounts get `newProfile` from `content/starting-kits/new-player.json` (a new content kind, format 1) plus the knife.
  - **Raids:** a row per raid, at most one open per account (a partial unique index). `PUT /api/profile` refuses a change in the number of stash pages; `POST /api/stash/pages` (`stashRoute` in `profiles.ts`, with the version read, like PUT) buys the next one. Since session 13, `POST /api/raids/:id/abandon` ends an open raid as missing in action without starting another (the game opening on the menu calls it); for a raid already ended it replies with the profile. Start: an open raid is ended as `mia` (gear → `keptGear(gear, false)`), the new row inserted and the profile bumped, in one batch. End: the gear sent is cut down by `keptGear` (shared `raid.ts`, the knife falling back to the profile's), checked, and stored; the request is stored as `result`, and the same request again replies with the profile (a retry whose reply was lost), anything else `raid-over`.
  - **Accounts:** usernames 3–20 of `A–Z a–z 0–9 _ -`, unique ignoring case; passwords 8–200 characters. **PBKDF2-SHA256 with 50,000 iterations** and a 16-byte salt, stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>`: 100k measured 12 ms on the Mac, over the free plan's **10 ms CPU** per request, 50k about 6 ms. The count is per hash, so it can go up later. Ten wrong passwords in a row lock the account for 5 minutes. **Sessions:** a random 32-byte token in an HttpOnly, `SameSite=Lax` cookie on `/api` (Secure over HTTPS only, so plain-http dev on the LAN still works), stored as its SHA-256, for 180 days, extended when past half.
  - **Party raids (co-op C4–C5, 2026-10-31):** devices connect over WebRTC (`net/peer.ts`, `net/coop-link.ts`), with offers and answers through `/api/party/signal` and `/api/party/signals`, and STUN/TURN from `/api/party/ice`. The host's device runs the raid (`play/coop.ts`) and sends each tick's state patch (shared `net/sync.ts`); guests apply it in place and send inputs. Details and measurements in [coop.md](coop.md).
  - **Friends, presence and the party (co-op C1–C3, 2026-10-31):** `social.ts` serves `/api/friends`, `/api/party` and `/api/presence` (types and `SOCIAL` limits in shared `protocol.ts`), over migration `0003_social.sql`. The menu's `PartyWatch` (client `social.ts`) posts a heartbeat every 10 s with the device kind and gets the party and invites back; invite links are `/join/<code>`, read by `main.ts` and joined on the menu. Details in [coop.md](coop.md).
  - **Wiping accounts (2026-11-05):** `npm run wipe` (`scripts/wipe-accounts.mjs`, SQL from `packages/server/src/wipe.ts`) is a local script over `wrangler d1 execute`, not an admin route, so the live Worker has nothing to attack. Wiped accounts get `newProfile` with the version bumped, never reset (a device holding the old profile gets `stale`). Open raids are closed with outcome `wiped` rather than deleted, so a late result gets `raid-over` and can't put old gear back. A party raid just started is called off. The statements go through `--file` because wrangler's import is all-or-nothing, which leaves no gap for a raid to start between them. Logins, friends, parties, settings and raid history stay. It's a dry run without `--apply`.
  - **Content on the server:** wrangler can't glob like Vite, so `scripts/bundle-content.mjs` writes the items, raids, starting kits and vendors (13b) into `src/generated/content.js` (gitignored), run before the server's dev, deploy, typecheck and tests. While the server runs in dev, `scripts/dev-server.mjs` watches `content/` and rebuilds the bundle on every save, because a stale bundle fails raid ends on items it doesn't know (decided 2026-11-04). `loadById` (moved from the client into shared `content/format.ts`) loads them.
  - **Tests** run the Hono app in Node against a small D1 stand-in over `node:sqlite` (`src/test/d1.ts`), built from the migrations. `@types/node` isn't installed (its globals clash with workers-types); `src/test/node.d.ts` declares the few Node APIs used.

## Hosting and testing
- **One Worker serves both the client and the API** (decided 2026-10-26, session 1). The built client is the Worker's static assets (`packages/server/wrangler.jsonc` points at `packages/client/dist`). Only `/api/*` runs Worker code; any other unknown path falls back to `index.html`. Sharing one origin means no CORS, and session cookies work with no extra setup. Pages was the alternative; Cloudflare is moving new projects to Workers static assets anyway.
- In dev, the client (Vite, port 5180) and the Worker (`wrangler dev`, port 8787) run separately, and Vite proxies `/api` to the Worker. `wrangler dev` refuses to start if the assets folder is missing, and `dist` is gitignored, so the server's `predev` creates an empty `packages/client/dist` (decided 2026-10-30). A fresh clone runs `npm run dev` without building first.
- **Phone testing during development:** run `vite --host` and open it on the iPhone over the local network. When HTTPS is needed (installing as a home-screen app, some browser features), use a Cloudflare preview deployment or a `cloudflared` tunnel.
- Each milestone ends with a performance check on the real iPhone (FPS counter in dev builds).

## Characters (confirmed, see design.md → Characters)
- The base body is a rigged, animated low-poly humanoid from a CC0 pack in glTF format. Recolour it to flat colours and draw it unlit, so it matches the map.
- Gear (helmet, armour, rig, backpack, weapon) is built in the item editor and attached to the skeleton at named mount points (`MOUNTS`: rigs on the armour's bone). Rigs are drawn since session 18b.
- Hit zones are simple capsules, not tests against the mesh itself. **They're a fixed layout in the simulation, not attached to bones** (changed 2026-10-26, session 6, so a co-op server needs no skeleton); the body is drawn to match.
- Distant characters update their animation less often to save performance.

Built in session 8b:
- **The asset:** `packages/client/public/characters/mannequin.glb`, from Quaternius's Universal Animation Library (Standard, CC0; licence and source in the README next to it). `scripts/build-character.mjs` builds it from the pack's GLB with glTF Transform and meshoptimizer: 15 clips kept, UVs dropped, the mesh simplified from 13.7k to 5.8k triangles, only rotation tracks kept (plus the hips' translation). 556 kB, 279 kB gzipped, fetched at startup rather than bundled. Quaternius's site moved new downloads to its own licence (QAL, August 2026), which forbids redistributing the files; this copy is CC0, but check before adding later downloads to the public repo.
- **One draw call per character, gear included** (`render/character.ts`). At load, the body is baked into flat triangles with face normals; each face takes the outfit part of the bone that weighs on it most (joint bands 20% darker). Each look (outfit, worn items, gun) is one geometry, built once and cached, with gear bound rigidly to its mount bone. Shading happens on the GPU from the skinned normal, with the same formula as the map. Bodies cull by a fixed sphere, since animation moves them far from their rest-pose bounds.
- **Animation** (`render/character-body.ts`): two layers, legs and upper body, from clips split by bone. The legs pick idle, walk, jog, sprint, crouch, crouch walk, jump or death by speed and stance, paced to the speed. When strafing, the hips turn towards where it's going (up to about 70°) and the chest turns back to face forward; going backwards plays the clip in reverse. The upper body leans with the look pitch and flinches when hit. **Leaning** (2026-11-01) turns the lower and upper spine (60/40) about the body's forward axis by the sim's lean angle, smoothed, and cants the gun by the same angle; the IK'd arms follow the shoulder. `CapsuleBody` tips its upper capsules about the same pivot, so `/bodies` (poses "lean left/right aimed", "crouch lean right") and `?hitzones` show them matching. **Gun hold by IK:** a two-bone IK per arm, with the hand rotations measured once from the pistol aim clip. The gun's position and tilt per hold are in `HOLD` there.
- **three.js's mixer only writes a bone when its clip value changes**, so posing on top of clips must put each bone back to its clip rotation before every update; otherwise turns pile up frame after frame. `CharacterBody` does this for the bones it poses.
- **LOD:** a body animates every frame within 20 m, every 2nd frame to 45 m, every 4th beyond, and every 8th off screen. It uses IK within 30 m; beyond that the gun goes in the hand. The dead stop animating 3 s after falling. Positions and yaw are interpolated between ticks.
- `/bodies` shows every pose with the hit zones over them, and `?hitzones` does the same in play.
