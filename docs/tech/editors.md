# Tech stack: Editors

Part of the [tech-stack.md index](../tech-stack.md). Record decisions here, in the topic they belong to.

## Editors (`/editor` route in the client)
- Desktop only (mouse and keyboard).
- **Saves through a Vite dev-server plugin** that writes JSON into `content/`.
  - The editor routes and the save endpoint exist **only in the dev server**, never in the production build. That makes them admin-only without needing an auth system.
  - Content changes go through git like code.
  - **Admin page (2026-10-30, the user's call):** the main menu's **Admin** button (dev builds only) gives items into your stash free, for testing, through `POST /api/admin/give`. The Worker allows `/api/admin/*` only when `ADMIN` is `"1"`, which only the server's `npm run dev` sets (`wrangler dev --var ADMIN:1`); the deployed Worker answers not-found, before sign-in, so nothing hints the route exists. It works from the iPhone when it plays against the dev server over the LAN, not in the live game.
  - **Admin accounts in the live game (2026-11-09, the user's call):** the Worker's `ADMIN_USERS` secret (`wrangler secret put ADMIN_USERS`, comma-separated usernames) names admins. GET /api/profile, logging in and registering reply with `admin` (`isAdminUser` in `admin-users.ts`; on the dev server, with `ADMIN` "1", everyone). It grants nothing on the server, only admin UI: the client keeps it as `isAdmin` (`account.ts`). **The stats overlay** (`#stats` and `#server`, fps, timings, enemy states) and its **Show performance stats** setting are dev builds only (2026-11-10, the user's call: never in prod, admin or not, on phone or PC). The admin routes and cheats still need `ADMIN`.
  - **Cheats:** infinite health, infinite ammo and peaceful are sim flags on the player (`Character.admin`, optional, so saved raids without it still load), so a co-op server could honor them the same way. The client sets them only in dev builds. Keeping your gear on death is the server's to grant: the end-of-raid request's `keepGear` is ignored unless `ADMIN` is `"1"`. Infinite consumables is a sim flag too (`AdminCheats.infiniteConsumables`); the stash screen sets it on its stand-in player before each action so a stash repair keeps the kit's points, and the stash save (`PUT /api/profile`) sends `freeRepairs`, which skips the over-repair check only when `ADMIN` is `"1"`; enemy health bars are client-only (`hud/enemy-bars.ts`, a DOM overlay like the quest markers).
  - **Spawner guns:** a weapon's optional `spawns` (an enemy type id, checked by `checkEnemies`) makes an admin gun. No item format bump: the field is optional. The sim can't spawn the enemy itself (it has no enemy types or loadouts), so a shot that hits something pushes a `spawnRequest` event and whoever runs the raid spawns and arms it: today the client, between ticks, like `?respawn`. A co-op server would do the same. The raid save keeps them as `spawner:<type>:<entity>` keys in its enemy map.
- **Loot editor (2026-11-02, the user's call over putting kinds in the map editor):** `/loot-editor` (`packages/client/src/loot-editor/`), like the sound editor: loot tables (name, rolls, items with weight and count, each item's odds and the table's worth from `stats.ts`, where it's used) and container kinds (name, grid, default loot mix, where they're placed), one undo history, saved together and refused on any problem. Both can be made or copied, not deleted or renamed. `?open=loot-tables/<id>` or `loot-containers/<id>`. The save plugin now takes `loot-tables/` and `loot-containers/` files. **A file an editor creates** clears Vite's module graph (`invalidateAll`), so the content globs list it on the next load; before, the plugin's no-reload for its own writes also kept new files out of the globs until the dev server restarted. The map editor's container fields (`editor/loot-mix.tsx`, shared with the loot editor) show the kind's loot, or the container's own mix after **Own loot…**. **Made easier to use (2026-11-02, the user's picks):** items are picked from a searchable list of their tiles (rarity color, size, type, value; several at once with **+ add items…**), rows reorder by dragging their handle, weights are sliders by ratio (0.05–50; a drag is one undo step and the odds follow it live) with share bars for a table's items, a mix's tables and a table's rarities; **rolled** shows 8 sample containers filled as a raid would (`rollMix` into a kind's grid, a new seed per **Roll again**, what didn't fit counted); a kind's grid is picked by pointing at cells. Links: "used by" map lines open the map editor, the map editor's container fields open the kind and each table here (`↗`), and a kind's tables open in place. Items have no icons yet, so tiles are their rarity color, as in the raid's inventory.
- **Built in session 15** (`packages/client/src/editor/`, plugin `packages/client/editor-save.mjs`):
  - `main.ts` imports the editor only behind `import.meta.env.DEV`, so a build leaves it out. `?map=<id>` picks the map.
  - **The save plugin** (`apply: 'serve'`) takes `POST /__editor/save` with `{ files: [{ file, doc, create? }] }` (a batch since session 16b) for `maps/` or `prefabs/` only, **from the Mac only** (loopback, same origin, `application/json`; the dev server listens on the LAN for the phone). It lays the JSON out like the hand-written files (objects one key per line, items of lists other than `nodes` and `zones` on one line) and formats it with Prettier, so an unchanged map saves to the same bytes. It skips the reload for a file it just wrote, so the editor keeps its state; other open tabs need a reload to see the change. **Held reloads (2026-11-12, so a Claude session's saves don't interrupt editing):** on the editor pages (`/editor`, `/item-editor`, `/loot-editor`, `/quest-editor`, `/layout`, `/sounds`), `dev/hold-reload.ts` returns a pending promise from Vite's `vite:beforeFullReload` listener (Vite awaits it), so a code or content change from elsewhere shows a **Reload** bar instead of reloading; the page keeps its loaded code and content until it's pressed. Saving an item someone else changed on disk meanwhile overwrites their change.
  - **The editor edits the file's own JSON**, not the parsed copy (zod gives keys in schema order), with a JSON snapshot before each edit for undo (200 deep). After every edit it rebuilds the scene and runs the same checks the game would (schema, `compileMap`, enemy, key, loot and quest-marker references); a map with a problem can't be saved.
  - **Camera for a trackpad** (`EditorView.wheel`): the page takes the wheel events itself, so a pinch (a wheel with `ctrlKey`) zooms the scene, not the page. OrbitControls does only the drags; its left button is switched to rotate while Option is held (a capture listener on `window`, before it and the gizmo see the press).
  - **Each node is its own object** at its pos and yaw, its mesh built by shared `compileNodes` at the origin (shaded on the GPU, so turning it shades right); a group's object holds its nodes' objects. Markers and patrols are drawn with `buildDebug`, doors with `buildDoor`. Nothing is merged, unlike in play; it's the desktop. The terrain is one mesh per chunk and can't be selected (the "locked ground layer").
  - **The gizmo** is three.js's `TransformControls` on a pivot in the frame of the group being edited, unturned so the grid lines up with it: on the one selected node, or the middle of several. The editor does its own snapping (absolute for one node, whole steps for several) and drops what's dragged sideways onto the first surface from 0.3 m above its base (not markers), or the terrain. A drag ends as a move-and-turn about the pivot (`moveWith`), which also carries a patrol's points.
- **Session 16** (`editor/terrain.ts`, `editor/overlap.ts`):
  - **Terrain brushes** (`applyBrush`) work on a `Float64Array` copy of the corner heights while the mouse is down; the view redraws only the 32 m chunks touched (the terrain is one mesh per chunk, built with the same `TriangleBuilder.terrain` as play) and the bases. On release, `setHeights` writes the heights rounded to a centimeter and moves everything whose base was within 2 cm of the old ground by the change (patrol points one by one; groups' own positions never; buildings never), as one edit. The view rebuilds the ground (terrain, water, zones, sky) only when those change.
  - **Level and hole** (roadmap 19zm) are area modes of the same tool: a drag covers every cell the rectangle touches (`cellRect`, at least one), outlined with the brush's line, and letting go applies it (`levelCells`, `holeCells`) and redraws those chunks. `setHeights` takes the hole flags too and writes them as `terrain.holes`, `[i, j]` cells sorted by row (no field when there are none; an optional field, so still map format 3). Picking over a hole uses a copy of the terrain without holes, so a hole can be dragged over to fill it.
  - **Holes in the sim:** `HeightGridDef.holes` is cols × rows flags (`holeFlags` builds them from the file). `HeightGrid.heightAt` ignores holes; `holeAt`/`isHole` tell them. The terrain raycast skips hole cells, and a ray leaving a hole under the ground beside it hits the hole's side there (normal back along the ray, flat). `CollisionWorld.groundAt` over a hole is the highest solid below, or else `PIT_DEPTH` (60 m) under the lowest terrain, so falling through an empty hole kills by fall damage rather than falling forever. The nav grid adds no ground node over a hole and counts solids under one as surfaces (elsewhere, solids under the terrain are underground). The renderer leaves hole cells out of the terrain mesh.
  - **Extend** (roadmap 19zn, `extendMap`): rows or columns copied from the edge onto one side of `terrain.heights`; north (−z) and west move `terrain.origin` out by the cells added and shift `terrain.holes`, so world positions (all nodes, zones, water) stay put.
  - **Overlaps** (`findOverlaps`) are worked out after every edit from each placed thing's collision solids (`compileNodes` boxes and ramps, cached per prefab), as rectangles turned about y with a bottom and top, by the separating axis test with 5 cm of tolerance. Buildings compare footprints only. `edit` refuses a change that raises the number of overlapping building pairs (counting, since indices shift). The view draws bases itself from each object's world matrix (`compileNodes` has no terrain), so they follow a drag.
  - The save plugin watches `content/maps` and `content/prefabs` (outside Vite's root, so new files there weren't seen), and `create: true` refuses to overwrite.
- **Session 16b (prefabs):**
  - **Paths step into prefabs:** `nodesAt(map, path, prefabs)` goes into a placed prefab's file as into a group, so the scope can be inside a prefab (inside a prefab…). The view builds the entered copy part by part (outlined purple; the panel says every copy changes, and how many there are); every other copy is one mesh, rebuilt with the edited prefab after each edit. Entering or leaving rebuilds the scene.
  - **One undo history across files:** the editor keeps the map and every prefab as their files (`MapEditor.prefabs`), and a snapshot is every file's JSON by name. Unchanged files share their strings between snapshots, so only what an edit changed costs memory. After an edit, a changed prefab gets a new object, and the overlap cache (`forgetPrefabSolids`) is dropped, since prefabs nest.
  - **Saving** sends every changed file in one request (new prefab files with `create`, before the map); the plugin formats them all before writing any. It's refused while the map has a problem or a changed prefab fails its own schema, or if **any other map** gets a problem it didn't have with the prefabs as saved (`check` on each, from `mapSources`). The plugin runs `enforce: 'post'` and skips the reload in `hotUpdate`, which, unlike `handleHotUpdate`, also sees new files: the content globs would otherwise reload the page when a new prefab is written.
  - **Making a prefab** (`makePrefab` in `doc.ts`) groups the selection (middle, lowest point), moves the group's nodes into a new prefab file and puts one placement where the group was. The file's color slots that they use come along with their values, and the placement passes the file's own slots on (`"colors": { "paint": "paint" }`), so nothing changes color. A placement gets an id (from the prefab's, made unique) when what's in it has ids, and the prefab tool does the same for buildings. Ids inside a prefab compile as `placement/id`, so the edit is refused if the map then has a problem it didn't have (a quest's marker, say).
  - **Unpacking** (`unpackPrefab`) puts a group (named after the placement, at its pos and yaw) of copies of the prefab's nodes in its place, slot colors resolved to the placement's (a hex color, or the enclosing file's slot), ids made unique and patrols repointed (`copyNode`); refused the same way.
  - The **prefab's own settings** show when nothing inside it is selected: name, instanced, color slots (default color, add, remove), building footprint (size, center, base color) and **Fit footprint**, which fits the solids whose bottom is within 0.3 m of the floor (so a roof's overhang doesn't count). A placement's inspector has a color per slot: the prefab's, custom, or a slot of the file it's in.
- **Session 17 (gameplay):**
  - **Markers, doors, patrols and zones** have their own fields in the inspector, filled from the content they name (enemy types, loadouts, loot tables, containers, key items, quests). Patrols and zones are drawn a click at a time (`EditorState.drawing`); their points are **handles** (`EditorView.setHandles`, worked out from the state in `MapEditor.handles` on every change), dragged onto surfaces, or the terrain for zones. The format didn't change.
  - **Nav overlay:** `NavGrid` from the compiled map, rebuilt a moment after each edit, drawn with `buildNavOverlay` colored by `Exposure.kind`. **`Exposure`** (`packages/shared/src/nav/exposure.ts`, no rendering) labels each node reachable, seen or hidden, `step(n)` at a time; the editor runs it in 30 ms slices. It's in shared so a content check could use it later.
  - **Play-test:** `writePlayTest` puts the map and prefab files in localStorage; `/play-test` (dev only, like `/editor`) compiles them and runs `startPlay` with `test: { map, raid }`, which skips the result, the snapshot and the server. The profile is `newProfile` with the new-player kit. **Back and drafts (2026-11-01):** a "← Editor" button at the top of the play-test focuses the tab that opened it and closes itself, or opens `/editor?map=` if that tab is gone. The editor keeps its unsaved changes in localStorage (`mes.editorDraft.<map file>`, per file `{ base, json }`, written 0.5 s after an edit, at once on Play, cleared on save) and restores them on load wherever the file on disk still equals `base`, so going to the play-test, reloading or a crash loses nothing, and a stale draft never overwrites a file changed on disk since.
- **Editor ease 1 (2026-10-30, roadmap 19zf):**
  - **Joints:** `solidsOverlap(a, b, tolerance, joint)` doesn't count a cut no deeper than `joint` (0.45 m, `JOINT` in `overlap.ts`) on two of its three axes, in either rectangle's frame; the depth on an axis is at most either solid's thickness. Only props use it; building footprints don't.
  - **Cutaway** (`editor/cut.ts`, `EditorView.cut`): one `THREE.Plane` in an array every scene material shares as `clippingPlanes` (the shared materials once, the rest by `clip()` after each build; three recompiles when the count changes), with `localClippingEnabled`. While it's on, the shaded material draws both sides and back faces at 0.45 brightness (`darkenBackFaces`, a fragment patch). Every pick, drop and placing raycast skips hits above it (`seen`). `floorLevels` takes the tops of boxes at least 1.5 m both ways, 6 m² and at most 0.6 m thick from the compiled world, merged within 0.5 m.
  - **Object snapping** (`EditorView.objectSnap`): at drag start, a snapping frame (`snapFrame`, in the scope, turned to the first dragged mesh's yaw mod 90°), and the bounds in it of every mesh square to it (from its geometry's bounding box) and of what's dragged. The gizmo drags along the scope's axes, so per dragged axis each of the frame's axes the drag runs at least a quarter along gives the four face pairings (flush either side, in line either side) as a gap ÷ that rate; the smallest move within 0.25 m among things within 1 m wins over the grid. A `Box3Helper` in the frame outlines the target.
  - **Caps** (`EditorView.render`, cutaway on): the scene without the overlays; then `root` and `bases` again with `scene.overrideMaterial` as stencil-only materials, back faces incrementing and front decrementing (no depth test, clipped); then a plane at the cut where the stencil isn't 0; then the outlines, handles and gizmo. The later passes turn off `autoClear` and the scene's background, which would otherwise paint over them.
  - **Wall drawing:** `EditorView.setPreview` shows `wallBoxes` up to the mouse (a `hover` event) in a see-through shaded material. `wallEnds` (walls.ts) are thin boxes' middle-line ends in the compiled world, put in the scope's frame and cached until the next edit or scope change; `nearestEnd` is checked on the raw click before the grid.
  - **Wall tool** (`editor/walls.ts`): `wallBoxes` (a box per side, length + thickness, yaw from local +x = (cos, −sin)), `snapCorner`, `cutWall` (sides, sill and lintel along the box's longer horizontal side; refused if tilted or too small; pieces copy the wall, so they keep its key order, and only the first keeps an id) and `doorIn` (yaw −90 when the length is local z). **Glass (2026-11-02):** window mode's **glazed** toggle (on by default) and tint put a `glass` node in the gap (`glassIn`); the **glass** mode glazes an existing window from a click on its sill or lintel (`windowAt` finds the next piece of the same wall above or below, and refuses one already glazed or a side piece). **Wall nodes (2026-11-02):** cutting a window into a box makes it a `wall` node (`toWall`: turned −90° if the box was long along its z) with the window as an opening; cutting into a wall node adds openings. A doorway in a wall node splits it (`splitWall`: the wall left, keeping its id and openings, the lintel box, the wall right, and the door). Selecting one wall node shows **a handle per window** that slides along it (`Handles.slide`: the closest point on the wall's line to the mouse's ray, snapped to the grid from its middle); a slide onto another window or past the end is refused. Delete with a handle picked fills that window in. The inspector lists the windows (at, width, bottom, top, glass and its tint, ×) and **Space evenly** (`spaceEvenly`: equal gaps, widths kept). Glass mode on a wall node glazes the opening clicked over or under. Walls cut before this stay plain boxes. **Count (2026-11-02):** door and window modes take a **count**; over 1, a click cuts that many of the bar's width spaced evenly along the whole wall (`evenOpenings`: equal gaps between and at the ends, at least 10 cm; or with the bar's **gap** set, that far apart in a row centered on the wall, and **Space evenly** on a wall node does the same), and `cutWall` takes a list of openings. The editor's grid has an optional **y** (`EditorState.gridY`); blank, it follows the cutaway or the camera's target. `EditorView.pickLeaf` finds the deepest node hit inside the scope and the point in its parent's frame, so a wall in a group is cut without going in. Drawing reuses `EditorState.drawing` (`what: 'walls'`).
  - **Railings** (roadmap 19zo, `edgeRailing`, `isRailing`): the side of a box (any of four) or a ramp's or stairs' long side nearest the click, found in the node's own frame from `pickLeaf`'s point. On a box, one box `RAILING_THICKNESS` (0.1 m) thick on the top, outside face flush with the edge; on a slope, tilted boxes of about 1 m (`pitch` = −the slope, since a positive pitch tips +z down) just outside the footprint, so they only touch it. A tilted box collides as its bounding box, so short pieces keep the invisible part small (height × sin slope at each joint). `findOverlaps` skips pairs that are pieces of one run (`sameRun`: same thin size and yaw, in line, at different heights). Clicking a box `isRailing` takes (no tilt, ≤ 1.5 m tall, ≤ 0.3 m thin, over 3× as long) cuts a full-height gap with `cutWall`.
- **Curve tool (2026-11-01, roadmap 19zl):** `editor/curves.ts`. An `Arc` is center, radius (the inside edge) and `start`/`sweep` in degrees from +x towards +z. `curveBoxes(arc, settings, color)` makes sector boxes: piece i at angle a faces out with yaw 90 − a (local +z = (cos a, sin a)), `size` = [2·outer·tan(step/2), height, depth] centered at radius + depth/2, so its outside face is a side of the polygon round the outer circle. `pieceCount` keeps a piece within 15°, 2 m of outside edge and 0.35 m of overlap with its neighbor (`PIECE_OVERLAP`, under `JOINT`), at most 120. Stairs: `stepCount` (about 0.25 m a step, and at least `pieceCount`), step i's top at raise + (i+1)·rise/n, two steps deep. `followSweep` follows the mouse the short way from the last sweep, held to ±360; `snapArc` snaps the radius to the grid and the angles to the angle snap. **Round holes:** `cutHole(floor, hole, railing, color)` works in the floor's own frame (hole `x`, `z` from its middle): four rectangles outside a square of half side radius + 0.5, then `sectorBoxes` pieces whose depth reaches the square's furthest edge across each piece (`squareReach`; a corner between its ends is √2 out), each checked to lie inside the floor, then everything placed back in the floor's parent frame. `sectorBoxes` takes a per-piece callback (depth, bottom, top) for this. The editor keeps the hole being placed as `EditorState.hole` (the floor's path, x, z), cleared by any edit or undo (`changed`), the tool or mode changing and Esc; its preview is a 32-sided see-through cylinder and the railing, wrapped in the groups between the scope and the floor so it shows in the scope's frame. `sameSlab` (overlap.ts) skips pairs of solids with the same top and bottom, 0.6 m thick or less. The editor draws with `Drawing.what: 'curve'` (points: center, start), keeps the sweep in a private field (it changes on every mouse move, so isn't state), remembers the last center per scope for the next to snap to, and previews with `setPreview` like walls.
- **Prefab browser (2026-10-30, roadmap 19zg):** `editor/prefab-browser.tsx`, opened by `EditorState.browsing`. `Thumbnails` (`editor/thumbnails.ts`) compiles a placement of the prefab at the origin, draws it with its own 160 px `WebGLRenderer` (alpha, `preserveDrawingBuffer`) from (1, 0.75, 1) framing its bounding sphere, and caches the data URL by the compiled shapes and doors.
- **Notes (2026-10-30, roadmap 19zh):** `content/notes/<map>.json`, `{ formatVersion: 1, map, notes: [{ id, pos, text, author, date }] }`. The save plugin serves `GET /__editor/notes?map=` (an empty file if there's none) and `POST /__editor/note` (`{ map, add: { pos, text } }` or `{ map, remove }`; Mac-only like saves), one change at a time; it names the author from `git config user.name` (else the login), dates it locally, writes it laid out and formatted like other content, and sends the `mes:notes` HMR event, which the editor and play-test listen for. Nothing in content.ts globs `content/notes`, so writing one reloads nothing and the game never sees them. `notes.ts` (client) fetches and changes them and makes the labels: canvas-text sprites with `depthTest` and fog off, `sizeAttenuation` off, render order 21. `startPlay` loads `dev-notes.ts` for `raid.map` in every raid when `import.meta.env.DEV` (a dynamic import a build drops), passing `DevHooks`: the scene, the player, and `screen(open)`, which counts in the frame's `cursor.want` like the raid screen, so the game lets go of the cursor rather than losing it; its note box stops keys and clicks from reaching the window's listeners; the editor through `EditorView.setLabels` (drawn on top in the cutaway's last pass too).
- **Session 18 (the item editor, `packages/client/src/item-editor/`):**
  - `/item-editor?item=<id>` (dev only, imported behind `import.meta.env.DEV` like `/editor`) is a React page with no 3D. `ItemEditor` keeps **every item file's JSON** by id (`itemSources`, the files as written, for their key order) and one undo history across them; a snapshot is the whole map of strings, so unchanged files cost nothing. A drag in the reticle designer is one undo step (`beginGesture`, `edit(…, true)`).
  - After each edit every file is parsed with `ITEM_FORMAT`; if all pass, **`itemContentProblem`** (`content.ts`) runs `checkItems`, `checkEnemies`, `checkLootTables`, `checkVendors`, `checkQuests`, every map's door keys, and `newProfile` + `checkProfile` for each starting kit, against the edited items (the other kinds are loaded raw, without the game's checks against content/items). Any problem blocks saving. `itemUses` lists what names an item (`item` fields, kit gear, door keys, guns' ammo, attachments' guns).
  - `storageRisks` (`risk.ts`) compares an item as saved with as edited, mirroring what `checkProfile` limits, and the page warns.
  - The **reticle designer** uses `reticleMarkup` from `hud/optic.ts` (the overlay's own SVG) and `aimedFov` for the person's size, so the preview is what the phone shows.
  - The map editor's form fields moved to `editor/fields.tsx` for both editors. The save plugin accepts `items/<id>.json` and watches `content/items`.
- **Session 19 (the sound editor, `packages/client/src/sound-editor/`):** `/sounds?sound=<id>` (dev only). `SoundEditor` is the item editor's state (every file's JSON, one undo history, gestures, checks, one save request) for sound files; `soundContentProblem` checks the items' and game's sounds are still there. `Audition` plays the open sound as edited with its own `SoundPlayer` (centered, or placed with `place`). The bound fields (`get`, `put`, `N`, `P`, `Row`, `Check`) moved from the item editor's panel to `editor/bound-fields.tsx` for both. The save plugin accepts `sounds/<id>.json`, and its layout keeps objects inside one-line list items on one line (a layer's filter) instead of breaking them.
- **Session 18b (models, `item-editor/model-*.ts`):** a **model** tab beside **stats** (the list's tab buttons). `model-panel.tsx` lists the parts (add box, cylinder or wedge; copy, mirror across x, delete) with each one's fields, and the item's points with x/y/z; `model-view.ts` is the 3D view, kept while switching items. **Build**: each part its own mesh at its place, picked by clicking and moved or turned with `TransformControls` (snap 0–5 cm, 0–45°; W, E), points as dots drawn on top, the sight line dashed; a drag is one undo step, and the view waits for the gizmo to let go before redrawing. What the item goes with is drawn but not pickable: the attachments chosen for each of a gun's slots (its hidden parts faint), the gun an attachment is previewed on (moved so the attachment stays at the origin), and the mannequin for worn gear. **Hip** and **aimed** use the game's own `Viewmodel`, field of view and `reticleMarkup` (only once every item passes its checks). `model-edit.ts`: `setSlots` keeps a gun's mounts and `hiddenBy` in step with its slots (a new slot gets the placeholder's mount), `fitPointsToSlot` an attachment's points with its slot. The model is edited in the item's JSON like everything else, so undo, checks and saving are unchanged.
- **IE-1 (many parts, many guns, 2026-11-09):** parts have optional `name` and `group` (`content/models.ts`; `modelShapes` ignores them, item format unchanged). `Picked` is `{ kind: 'parts', indices }` or a point. `ModelView` attaches the gizmo to a `pivot` (one part's place and turn, local space; several parts' middle, world space); on a drag it keeps the pivot's and each part's start matrix and applies the pivot's change to each, sending `movedParts`. A left-drag off the gizmo draws `.ie-band` and picks the parts whose centers project inside (`boxPick`); shift adds. `model-panel.tsx`: `PartList` (folded by group), `PickedFields` (shared group via `Combo`, color, hidden by; name and shape for one), `Cost` (triangles via `budget.ts`: the item's own parts minus hidden ones, plus fitted attachments for a gun). The clipboard is `mes.itemEditor.parts` in local storage, checked with `partSchema` on read. `fits-panel.tsx` (**fits** tab): per gun, nothing fitted and each fitting attachment alone, a side picture (`shapesPortrait` of `gunModel`) and, for irons and optics without zoom, an aimed one (`aimed-picture.ts`: the game's `Viewmodel` fully aimed at `AIM_FOV`, 640×360, shown cropped to the middle at 2× with `reticleMarkup` over it); drawn ~14 ms a frame, kept by an FNV hash of the gun and attachment JSON. A tile opens the model tab with that fit (`ModelTab`'s `request`).
- **IE-2 (views, colors and reticles, 2026-11-09):** reticle shapes may be `arc` (clockwise from `from` to `to`, degrees from up; the schema wants 0 < to − from ≤ 360) or `triangle` (filled), and any shape may set `color` (else the reticle's); the item format is unchanged. `reticleMarkup` gives a shape with its own color its own `fill` or `stroke` inside the reticle's group; `arcPath` draws an arc (a full turn as two halves). `reticle-edit.ts` holds the designer's pure edits (`dragged`, `mirrored`, `repeated`, `NEW_SHAPES`). `ModelView` has a `Look`: the orbit camera or one of three `OrthographicCamera`s, each with its own `OrbitControls` (rotation off, pans with the right or middle button) since OrbitControls fixes a camera's up when made; the gizmo, picking and box picking use the active one, the grid group turns to lie a meter behind the item, and `screenAxes` tells the panel which model axes are right, up and out for the arrows. `setReference` puts a picture on a plane at x = 0.95 facing −x, shown only in the side look; `reference-store.ts` keeps each item's (`Blob`, width, middle, opacity, flip) in IndexedDB `mes-item-editor`, failing quietly. `palette.ts` is the house item palette and `colorsOf`. The eyedropper goes through a ref the view's pick event checks first. `mirrorPart(p, axis)` negates the two angles about the axes in the mirror's plane and, for a part not symmetric along that axis of its own (`halfTurn`: wedges along y and z, cones along y, odd-sided cylinders along x), composes a half turn with three.js quaternions and reads yaw, pitch and roll back.
- **Plates and carriers (GZ-4, 2026-11-12):** a **Plate** kind whose **Material** buttons are presets (picking one fills the level, durability and repair loss, all still editable); body armor and armored rigs get a **Carrier** group (plate slots, what plates and its own rating cover, comes-with plates, bulky, footstep noise, swap time).
- **Visors and night vision (GZ-5, 2026-11-12):** **Visor** and **Night vision** kinds (a visor: armor stats and its view, the preview cracked as at half wear; goggles: tint, brightness, grain, softness, tube); helmets gain **Visor mount** and **Night vision mount** ticks. The view fields are one `ViewFields` for helmets and visors.
- **Headsets and helmets (GZ-2, 2026-11-12):** a **Headset** kind (hearing); on helmets a **Head** group: covers the ears, hearing (labeled as a loss unless the ears are covered, when a boost is allowed), vignette, hard shape, and a 16:9 preview of the view drawn as in the game (`visionBackground`).
- **Magazines (MG-1, 2026-11-12):** a gun has **Takes magazines** (`feed`); a magazine-slot attachment has **A magazine (keeps its own rounds)**, then **Holds** and **Caliber** (from the rounds in content). Saving warns (`storageRisks`) when a magazine holds fewer rounds or changes caliber, or a gun switches between magazines and loose rounds.
- **Footprints (WF-2, 2026-11-12):** a magazine gets **Adds rows**, a muzzle device **Adds columns** (cleared when the slot changes). The size card says "with what it comes with (W×H bare)".
- **Stocks (WF-1, 2026-11-12):** an attachment in the `stock` slot gets **Adds cells** / **Folded adds** and **Folds by itself** (hinge x and z, turn, slide z; ticked on, a left side-folder); a gun gets **Comes with** (a picker per slot: `defaults`) and, with a stock slot, **Folding stock mount** (`model.stockFold`). `setSlots` drops defaults and the mount's fold with their slot. The model tab previews a gun with what it comes with, and a **folded** toggle shows the fitted stock (or the stock edited, on a gun) folded; it's drawn as context, so nothing can be picked meanwhile. The size card and pictures show a gun with its default stock (`withDefaults` in `render/item-portrait.ts`) and say its size without.
- **Groups (map and prefab format 3, session 15):** a `group` node has an optional name, pos, yaw and its own nodes, and may hold groups. It only moves and turns what it holds: **it adds nothing to ids** (a marker's path id is the same in a group or out of one, so grouping never breaks a quest or a patrol reference), and ids must be unique across groups. An unnamed node in group #3 gets `#3.<index>`. Unlike a prefab, a group is in the map file itself.
- **Generated maps (MK-2, 2026-11-12):** a generator script builds its whole map fresh each run and hands it to `writeGenerated` (`scripts/mapkit/generated.mjs`), which merges it into the file on disk. Every named group the script makes gets a `gen` key from its name path (`east-end/rail-yard`; names must be unique among siblings, and every top-level node must be a named group), and the map's `generated` record (`by`, `fields`, `groups`) keeps a 12-hex sha1 of each group's own content as last written, with keys sorted and any keyed group inside counted only as its key, so moving a shed doesn't take the yard around it away from the script. It also hashes each top-level field the script writes (terrain, zones, floors, …). On a re-run: a group matching its hash is replaced; one that doesn't was **edited by hand and is kept**, with a note if the script's version changed too; a key in the record but missing from the map was **deleted by hand and isn't put back**; a group the script no longer makes is removed unless edited; nodes without a key (the user's own) stay where they are; new groups go in after their neighbor from the script, inside a hand-kept group too. A field is the same, so a sculpted terrain is kept whole. Hand ownership is detected by the hash, not marked by the editor, so edits made any way count; the editor's only part is that copies drop `gen` (`copyNode`), and a second group with a used key (a copy made outside it) counts as the user's. **Options:** `--dry-run` prints the table and writes nothing; `--reclaim <key>,…` or `all` hands groups (with everything under them) or fields back to the script. A map without a record is taken over by keying its groups by name path as if the script had last written today's output: what matches is the script's, the rest is kept. Files a generator only starts (the raid) go through `writeOnce` and are never overwritten. **What it costs:** a terrain brush that moves things standing on the ground makes their groups the user's; a node added inside a generated group makes that group the user's. Tests: `scripts/mapkit/generated.test.mjs` (the `mapkit` vitest project, where MK-6's pieces are tested too). `--dump <file>` (MK-6) writes the fresh map there and nothing else.
- **Layout board (MK-3, 2026-11-12):** `/layout?map=<id>` (dev server only; `/layout` alone lists the files) edits `content/layouts/<id>.json` (format in tech/content-formats.md → Layout files) and saves through `/__editor/save` (`layouts` added to its folders; a missing file is created on first save). Code in `packages/client/src/layout-board/`: `board.ts` (the view, pointer tools, undo, save), `panel.tsx` (fields), `sketch.ts` (the drawing). **It edits the file as written** (key order kept, defaults left out) and checks it against the schema after every change; while it's invalid, the panel shows why, save is refused, and the last valid version stays drawn. **Tools:** select (V; drag to move, corners resize with the opposite corner fixed, the stalk on the front turns in 5° steps, Shift 15°), area (A), pad (P) and landmark (L) drag out a rect, road (O) and zone (Z) click points (Enter or double-click ends; a zone also closes on its first point), way in (E) clicks a side of an area, rings (G) centers the walking-time rings. Positions snap to 1 m, Alt for 0.1 m. A selected road or zone shows its points (drag; the small dots between add one; Delete removes the picked point). Wheel zooms, F fits, drag empty ground or right-drag pans, arrows nudge (Shift ×10), ⌘D duplicates, ⌘Z/⇧⌘Z undo and redo (a drag or typing into one field is one step). Double-clicking a piece centers the rings on it. **Rings:** 10, 20 and 30 s at 3.5 m/s (solid) and 6 m/s (dashed), the sim's walk and sprint; the readout gives straight-line meters and seconds from the ring center to the cursor. They're crow-flies times, not paths: MK-4's report measures real routes. The ground is shaded by `heightAt` on a 5 m grid (10 m past 400 m across), redrawn when a pad or slope drag ends, not during it.
- **Map report (MK-4, 2026-11-12):** `scripts/map-report.mjs` runs `packages/client/src/map-report/measure.ts` (pure: no three.js, no DOM) and `cost.ts` (the game's `buildMap`) through `importTs`. `measureMap(map, world, nav)` returns the numbers and three 1 m rasters (`lines`, `open`, `nav`, a byte per cell, values in the `Rasters` doc comment) for MK-8 to paint on the editor's ground as they are. The heatmaps are PNGs written by hand (zlib, no dependency). Measures and yardsticks: level-design.md → Map report.
  - **One drawing for board and sketch:** `sketch.ts` is a plain string builder (no DOM), with its styles as `SKETCH_CSS` (light and dark). The board draws its layers with it, adding handles; `node scripts/layout-sketch.mjs <map> [--out f.html] [--rings x,z] [--cell m]` wraps the same SVG in a standalone page to publish as a review artifact. So the sketch a review sees and the board can't disagree.
  - **Scripts use the game's TypeScript through `scripts/mapkit/import-ts.mjs`:** `importTs([files])` bundles them with esbuild (shared's entry by default) into `node_modules/.cache/mapkit/<hash>.mjs` and imports it, each run. A generator gets `loadLayout`, `heightAt`, `rectCorners`, `entranceEnds` and the rest this way; MK-4's report will get the compiler and nav the same way.

- **Map kit (MK-6, 2026-11-12):** generator pieces in `scripts/mapkit/`, shared by every map script. **Rule: a piece written once lives in its map script; written a second time, it moves here,** with a sim test in `kit.test.mjs` (the `mapkit` vitest project). What's in it:
  - `nodes.mjs`: `r2`, `box` (by extents), `drawn` (no collision), `group`, `prefab`, `label`, `along` (a box tilted from a to b), `yawAlongX`/`yawAlongZ`. Moved from gen-silver-creek.mjs.
  - `terrain.mjs`: `terrainGrid({ origin, cellSize, cols, rows, height })` gives `heights`, `groundAt` (bilinear, as the generators always sampled it), `groundRange`, `steepCells(limit)` and `node(color, holes)` for the map's `terrain`.
  - `building.mjs`: `buildingKit({ C })`, Silver Creek's walls with openings by `at`, doors, windows, gabled roofs, house shells, slabs with holes and porches (was `scripts/silver-creek-kit.mjs`). Built in a local frame.
  - `frame.mjs`: `frame({ x, z, yaw }, y)` gives `toWorld`/`toLocal`, `groundIn(groundAt)` and `group(name, nodes)`. Build square, place turned: a layout rect is a frame as it is (the same turn as the compiler and `layouts.ts`). For District's −140° grid.
  - `ground.mjs`: `layoutGround(layout, { cellSize, margin, color, wallColor, shoulder, grade })` is the terrain grid from a layout's slope and pads, with roads graded level across (eased back over a 4 m shoulder), plus `retainingWalls()`, `roadGrades(over)`, `steep(limit)`, `padHeight` and `inWallBand`. **Wall pads:** the grid can't hold a sheer step (every cell it crosses slopes), so the step sits halfway into a solid band inside the pad's edge, two cells across the step's direction deep (5.7 m on a 2 m grid at −140°, 4.2 m square to the grid). Its top is flush with the higher ground under a drawn cap in the terrain's color, and the face is concrete. On an uphill side the band's top is the ground outside, and the face looks into the pad. **Keep the band's top at or over the ground it hides:** 5 cm under, and the steep cells poked through and stopped a walker (the sim won't walk up steep terrain). Same height rules as `layouts.ts`'s `heightAt` outside the bands, re-implemented in plain JS so generators stay synchronous; a test holds the two equal over District.
    - **Held roads (DS-2, 2026-11-12):** with `maxGrade` a road (not a `path`) keeps to that grade along its length instead of climbing the pads' banks head-on: its centerline profile is the middle of the highest line under the ground and the lowest over it that keep to the grade, eased onto a road it starts or ends on. Such a road also **cuts through a wall pad's band**: inside the pad its ground is the road's, and `retainingWalls()` leaves a gap in the wall pieces where it crosses (the shoulder hides under the pieces either side). Left out, roads follow the ground and stop at walls as before. `carve(x, z, y)` has the last say on each point's height (District's rail cut and culvert). A test drives a held road through a wall into a yard and checks the wall still stands beside it.
  - `runs.mjs`: `stairRun`/`rampRun({ id, x, z, y, yaw, rise, width, flight, going, landing, turn, gap, base, color, sides })`. A climb in flights (stairs at most 2.8 m a flight, going 1.6, about 32°; ramps 1:8 by default, no landings) with landings between, `straight` or a switchback (`left`/`right`), as one group at the foot; it returns the top's place and facing. It throws past 45°. `runDownFrom(kind, { top, topY, yaw, groundAt, … })` lays one out from where it arrives, down to where it meets the ground; `runLength` measures one first.
  - `road.mjs`: `roadStrip(id, points, width, { groundAt, color, piece, lift })`, a drawn strip along a polyline in pieces of at most 4 m, with a disc at each bend. Grade the ground first (`layoutGround`), or the strip leaves it.
  - `fence.mjs`: `fenceRun(id, a, b, { panel, broken, bay, gaps, y })`, prefab panels along a line, where `gaps` take the `broken` prefab or nothing (`null`); `y` can be a ground function.
  - `sim.mjs` (tests): `build(nodes, terrain)` compiles a small map with the real prefabs into the collision world and nav; `joined(nav, a, b)` asks the nav's components, small closed places included (`nearest` otherwise looks past a pocket to a bigger area outside: a closed 9 m yard read as open); `walk(world, from, to | [points], { sprint, seconds })` steers a character there.
  - **Not here yet, on purpose:** storefronts, curbs and markings, angled cover rows with checked gaps. Silver Creek never wrote them, so they wait for the session that first needs them (DS-5/DS-8, the in-between) and come here the second time (the user's call, 2026-11-12).
