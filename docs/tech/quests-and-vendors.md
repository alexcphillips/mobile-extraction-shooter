# Tech stack: Quests and vendors

Part of the [tech-stack.md index](../tech-stack.md). Record decisions here, in the topic they belong to.

## Quests
Session 14. Rules in shared `quests.ts`, content in `content/quests.ts`. See design.md → Quests and vendors.
- **`content/quests/<id>.json`** (format 1): `name`, `vendor`, `description`, `requires` (quest ids), `objectives` and `rewards` (`money`, `items` as `{ item, count? }`). Objectives each have an `id` (progress is kept by it) and optional `text`: `investigate` (`map`, `marker`, a questMarker's path id; `text` required), `handOver` (`item`, `count`), `extract` (`item`, a quest item; optional `find`, a step shown before it that ticks in a raid while you carry the item and isn't saved, 2026-11-11). `checkQuests` checks the vendor, unique objective ids, hand-overs of normal items, extracts of quest items, requirements that exist with no loop, and reward stacks; the client's content test also checks every marker is on its map (`checkQuestMarkers`). Bundled for the server too.
- **State** is in the profile (format 3): `quests` maps a quest id to `{ status: 'active', progress: { [objective]: n } }` or `{ status: 'done' }`; a quest not there hasn't been accepted. `questStatus` adds `locked`, `available` and `ready` (active with everything done). Only the server changes it: `PUT /api/profile` refuses any change (`sameQuests`).
- **Server** (`server/src/quests.ts`): `POST /api/quests/:id/accept`, `/hand-over` (`objective`) and `/complete` (`page`), each with the version read and refused in a raid, like buying. `completeQuest` adds the reward items with `addToStash` (shared `stash.ts`, all or none; `buyOffer` uses it too).
- **In raids (session 14b):** an `extract` objective also has `map` and `spots` (questMarker path ids, at least one); format 1 was changed in place, since session 14 had never been committed or deployed. `checkQuests` refuses two quests extracting the same item; `checkQuestMarkers` checks spots too.
  - Setup: `raidObjectives(profile, quests, map)` lists the active quests' unfinished investigate markers and extract items on that map. The sim's `startQuests(state, map, items, holder, objectives)` (`sim/raid.ts`, after `startRaid`) adds `RaidState.investigate` (`InvestigateSpot`: holder, marker, position, `done`) and puts each quest item on the ground at a spot picked with the raid's RNG. A missing marker throws.
  - Investigating is in the sim, so co-op runs the same rule: `PlayerInput.investigate` (a press) ticks the nearest of that player's spots within `RAID.investigateReach` (2.5 m, and `extractHeight` up or down), with an `investigate` event. `investigateInReach` drives the use button; `investigatedBy` lists a player's done markers.
  - Result: `EndRaidRequest.investigated` (marker ids, at most 50). The server's `/end` runs `raidProgress(profile, quests, items, map, investigated, keptGear)` after `checkGear`: investigate objectives on the raid's map count whatever the outcome; `takeQuestItems` takes every quest item out of the kept gear (every grid, nested too) and those an active extract objective wants count. Quest routes are refused in a raid, so quests active at the end were active at the start: no snapshot is needed. The client runs `raidProgress` on copies for the results screen.
  - Client: `hud/quest-markers.ts` (one DOM element per marker, moved only when it shifts a whole pixel, the window's size read rather than the element's), `ui/raid-quests.tsx` (the Quests tab), `PlayOptions.profile` instead of `gear`. A raid snapshot saved before 14b gets an empty `investigate` list when resumed.

## Vendors and money
Session 13b. Rules in shared `vendors.ts`, content in `content/vendors.ts`. See design.md → Quests and vendors → Economy.
- **`content/vendors/<id>.json`** (format 1): `name`, optional `blurb`, and `sells`, a list of `{ item, count?, attachments? }` (count for stacks, one purchase's worth; attachments a gun comes fitted with, 2026-11-05). `checkVendors` checks the items exist, have a value, aren't money, and fit one stack, and that an offer's attachments fit its gun, one to a slot. `newStashItem` fits them (still with no rounds). Bundled for the server too.
- **Prices:** `buyPrice(items, offer)` is value × count, plus the value of any attachments it comes with; `sellPrice(items, item)` is `floor(value × VENDOR.sellShare × condition(item))` per item, plus a gun's attachments and loaded rounds, or the full value for money (`isMoney`). `cantSell` refuses a rig or backpack with anything in it and anything worth nothing.
- **`buyOffer(profile, items, vendor, index, page)`** puts a new item into copies of the stash pages (page first, then the others) and keeps them only if all of it fit; **`sellItem(profile, items, ref)`** takes an item out by a ref as the stash screen sees it (`stashGridOf` resolves the profile's grids and pages), refusing the knife. **`depositInto(profile, items)`** takes the money out of the gear's grids into the balance (capped at `PROFILE.maxMoney`).
- **Server** (`server/src/vendors.ts`): `POST /api/vendors/:id/buy` (`BuyRequest`: `version`, `offer` index, optional `page`) and `POST /api/vendors/sell` (`SellRequest`: `version`, `from`, a list of up to `MAX_SELL` (200) `ItemRef`s checked for shape; `sellItems` finds them all first and removes them by the item, not the index, all or none), each with the version read, refused in a raid, like buying a stash page. Raid ends (`/end`, and missing in action at start or `/abandon`) call `depositInto` after `keptGear`. `PUT /api/profile` also refuses `overRepaired`.
- **Client:** `StashSaver.buy` and `sell` (and `buyPage`) share `post`, which saves first and builds the body after, so it names the saved version; the stash reopens on the reply, on the page shown. `ui/vendors-page.tsx` is the vendors page (2026-11-10: `VendorsPage` holds the hub and a vendor's page, `TraderShop` the Shop tab; the Quests tab is `TraderQuests` in `ui/quests-page.tsx`, which also has `vendorQuestCounts`; styles under `.trader-*` in style.css, and the Hangar still uses the old `.vendors-layout` ones); selling is `InventoryContext.sell`, set only between raids.
- **Repairs** (`sim/repair.ts`: `repairable`, `repairArmour`, `kitUsedUp`): the inventory action `{ type: 'repair', kit, armour }`. In a raid, `applyInventory` starts it as a `MedUse` with `armour` set (the kit must be in a carried grid; `ownItem` resolves your own refs), and `updateMedUse` finishes it (`finishRepair`) instead of `useMed`. `timeToUse` gives a med's or kit's use time, for the heal button's ring. `applyStash` does it at once with the kit and armour anywhere. Armour items carry `data-armour` (like `data-gun`), and the drag host's `armourZone` makes a `repair` drop zone when a kit is dragged over one.
- **Using from the inventory:** `InventoryContext.use` (a raid only) sets the next tick's `input.use`, as the heal button's picker does: a `MedRef` from **Use**, or `'cancel'` from the top bar's use pill. The raid screen redraws every 3 ticks while something is in use (otherwise every 10). Selling several is the controller's `selling` list (`startSelling`, `canPick`, `picked`); taps toggle picks and `canDrop` refuses everything meanwhile.

## The Hangar
Sessions H1–H6. Rules in shared `hangar.ts`, content in `content/hangar.ts` and `content/recipes.ts`. Design in [hangar.md](../hangar.md).
- **`content/hangar/<id>.json`** (format 1): `name`, `blurb`, optional `order`, and `levels` (1 to `MODULE_LEVELS`, 3), each `{ cost: [{ item, count }], power?, unlocks }`. A module starts at level 0; `power` is the Power grid level a level needs, the level itself if left out (`powerNeeded`; never on the grid's own levels). `checkHangar` checks the grid (`POWER_GRID`, `power-grid`) exists, costs name real non-quest items once per level, and no level needs more power than the grid has. Every cost is one bandage for now. Bundled for the server; the client loads it too (`loadHangar`, `loadRecipes` in client `content.ts`, H3).
- **Profile** format 11: `hangar`, each module's level by id (migration 10 adds `{}`). Only the server changes it: `PUT /api/profile` refuses a change (`sameHangar`).
- **`upgradeModule(profile, module)`** checks `cantUpgrade` (top level, power, the stash has the cost) then takes the cost with `takeFromStash` and adds a level. Instant. `upgradeCost` gives have / need per item for the card.
- **Taking from the stash** (shared `stash.ts`, moved out of quests in H1): `plainItem`, `stashCount(profile, match)` and `takeFromStash(profile, match, count)`, over the pages and the rigs and backpacks on them, never worn gear. Hand-overs use them too.
- **Recipes** (H2, `content/recipes/<id>.json`, format 1, `content/recipes.ts`): `module`, `level` (the module level it needs), `inputs` `[{ item, count }]`, `output` `{ item, count? }` (one stack), `minutes` (up to `MAX_CRAFT_MINUTES`, 480), optional `order`. `checkRecipes`: the module has that level, inputs are real non-quest items once each, the output is a real item, not a quest item or money, within a stack.
- **Crafting** (shared `hangar.ts`): profile format 12 adds `crafts`, a `Craft` by module id (`{ recipe, item, count, done }`): the output is copied in at start, so editing or deleting a recipe never strands one; `done` is ms on the server's clock. `startCraft(profile, module, recipe, now)` checks `cantCraft` (its module, the level, nothing already there, the inputs; `recipeCost` gives have / need) and takes the inputs. `collectCraft(profile, items, module, now, page)` puts a done craft into the stash with `addToStash` (guns empty, as from vendors); no room or not done and it stays. Nothing ticks: `craftLeft(craft, now)` compares when read, so crafts run while the app is closed. `sameHangar` covers crafts too.
- **Server** (`server/src/hangar.ts`): `POST /api/hangar/:id/upgrade` with `{ version }`, `/:id/craft` with `{ version, recipe }` and `/:id/collect` with `{ version, page? }`, all refused in a raid or on a stale version, like the quest routes, and timed with the server's `Date.now()`. Every profile reply carries `now` (the server's clock) so the client shows time left without trusting its own.
- **Decryption** (H5, the Intel desk): a recipe has `output` or a weighted `results` list (not both, `checkRecipes`), each `{ weight, item, count? }` or `{ weight, vendor, rep }`, plus an optional `name` ("Decrypt a flash drive"). `recipeResults` reads either form as one list; `rollResult(recipe, random)` picks one by weight. `startCraft` takes `random` (default `Math.random()`) and stores the roll in the craft, so `Craft` is `{ recipe, item, count, done }` or `{ recipe, vendor, rep, done }` (profile still format 12: the old shape is still valid). Rolling at the start means a full stash can't reroll at collect. `collectCraft` adds a rep craft to `profile.vendors` (no room needed). A module level's optional `craftTime` (0–1) scales its crafts' minutes from that level on (`craftTimeAt`, `craftDuration`); Intel desk III is 0.5. `checkRecipes` takes the vendors to check rep results. The page shows a rolled recipe with its first input's picture, its name and the results with chances (`resultChances`), keeps the roll hidden while it runs ("Decrypting"), and says what came out on collect (`collectedLine`).
- **The page** (H3, client `ui/hangar-page.tsx`; words and times in `ui/hangar-text.ts`): the vendors page's layout with modules for vendors. The clock is `Date.now()` plus the skew from the last reply's `now`, ticking each second while a craft runs. `StashSaver.upgradeModule`, `craft` and `collectCraft` post as buying does (`HangarRequest` and friends in `protocol.ts`).
- **Stash space** (H4, shared `profile.ts`; sizes in `PROFILE`, placeholders until the user balances them): bought pages are 10×20 (`PROFILE.stash`; `settleStash` reshapes stored pages of any other size). `nextPageQuarters`: page n needs Quarters (`QUARTERS`) at level n − 1, so `buyStashPage` checks it and inserts the page after the bought ones (`boughtPages`), before any category page. The vault is `vaultSize(profile)`, `PROFILE.vaults` by Secure locker (`SECURE_LOCKER`) level: 2×1 (w×h, `GEAR.vault`), 2×2, 3×2, 3×3. Category pages (`categoryPages`, all three at Quarters `PROFILE.categoryLevel` 3, 10×10 each) are stash pages at the end of `profile.stash` with `Grid.only` (`guns`, `ammo`, `meds`; `PAGE_CATEGORIES` in `inventory/grid.ts`, the same kinds as the stash chips), which `canHold` enforces, so every move, double-tap and `addItem` respects them; they don't take containers. `settleHangarSpace(items, profile)` reshapes the vault to its size and adds missing category pages: run by `upgradeModule` (which now takes `items`) and `parseProfile` (in place of `settleVault`, removed). Raid results no longer settle the vault: `checkGear(items, gear, vaultSize(profile))` refuses one of the wrong size, so a forged bigger vault can't spill into the stash. `checkProfile` checks bought pages ≤ prices + 1, exactly the unlocked category pages in order, and the vault's size; PUT's same-page-count rule stops adding or dropping one.
- **Auto sort on close** (H4): `sortToCategoryPages(items, profile)` moves what lies loose on the bought pages onto its category page, as much as fits (stacks topped up first; `addItem` lowers the count itself and moves the object when it all fits). The client runs it when the stash screen closes (back arrow, Esc, the controller's close) and saves if anything moved. Vendors, crafts and rewards still land on bought pages first; the next close sorts them.
- **Stash tabs** (H4, `StashPage` in `main-menu.tsx`): bought pages numbered, then the next page's button, then the category pages as their chip icons (`.stash-cat`, a gap above), kept in that order with flex `order`. The next page is a **+** (two taps, the price) once Quarters allows it, else the lock, whose tap says "Page n needs Quarters level m (Hangar)".
- **Item details** (H3): `sourceIndex` takes `hangar` (`HangarContent`: modules and recipes) and lists `crafted` (each module once, at its lowest recipe level); `itemUsage(quests, item, hangar)` adds `recipes` and `upgrades` that take the item.
- **Contracts** (H6, the Intel desk; rules in shared `contracts.ts`, content in `content/contracts.ts`). **`content/contracts/<id>.json`** (format 1): `name`, `vendor`, `description`, `level` (Intel desk level, 1–3), `hours` (up to `MAX_CONTRACT_HOURS`, 24), `objectives` (`kill`: `faction`, optional `map`, `count`; `handOver`: `item`, `count`, always found in raid) and `rewards` (`items`, `rep`; never money). `checkContracts` checks the vendor, unique objective ids, kill maps (the server passes its raids' maps, the client its maps), hand-over items and reward stacks, and that it gives something. Bundled for the server.
  - Profile format 13 adds `contracts` (`ContractState`: `day`, `taken` ids that day, optional `active` `{ id, ends, progress }`; migration 12). `sameContracts` makes PUT refuse a change.
  - Profile format 14 (migration 13, 2026-11-10) only renames items: `encrypted-drive` to `encrypted-usb-drive` and `nuclear-facility-blueprint` to `nuclear-facility-schematics`.
  - `contractBoard(contracts, profile, now)`: the first `CONTRACTS.board` (3) the desk's level allows, ordered by an FNV hash of `day:id` (`contractDay` = UTC days), so it needs no state. `settleContracts` clears `taken` on a new day and drops an active one out of time unfinished (or deleted from content); `takeContract`, `handOverContract`, `claimContract` (rewards with `addToStash`, rep to the vendor) and `dropContract` settle first. `contractStatus`: `running`, `done` (never expires) or `expired`.
  - Kills: the client counts kills by `factionOf` the target at the death event (`KillCounts`, kept in the raid snapshot) and sends `EndRaidRequest.killed`; the server checks whole numbers by faction adding up to no more than `kills`, and `/end` runs `contractKills(profile, contracts, map, killed, started_at)` after quests, whatever the outcome, only if the raid started before `ends`.
  - Server `contracts.ts`: `POST /api/contracts/:id/take`, `/hand-over` (`objective`), `/claim` (`page`), `/drop`, each with the version read, refused in a raid, on `Date.now()`.
  - Client: `ui/hangar-contracts.tsx` (the Intel desk's running card and board; the page ticks each second on the desk), words in `hangar-text.ts` (`contractObjectiveText`, `contractRewards`, `contractRaidLines` for the results screen, worked on a copy and assuming the raid started in time), the menu badge and line count a contract to claim. `StashSaver.takeContract`, `contractHandOver`, `claimContract`, `dropContract`.
