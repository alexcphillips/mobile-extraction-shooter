# Tech stack: Quests and vendors

Part of the [tech-stack.md index](../tech-stack.md). Record decisions here, in the topic they belong to.

## Quests
Session 14. Rules in shared `quests.ts`, content in `content/quests.ts`. See design.md → Quests and vendors.
- **`content/quests/<id>.json`** (format 1): `name`, `vendor`, `description`, `requires` (quest ids), `objectives` and `rewards` (`money`, `items` as `{ item, count? }`). Objectives each have an `id` (progress is kept by it) and optional `text`: `investigate` (`map`, `marker`, a questMarker's path id; `text` required), `handOver` (`item`, `count`), `extract` (`item`, a quest item). `checkQuests` checks the vendor, unique objective ids, hand-overs of normal items, extracts of quest items, requirements that exist with no loop, and reward stacks; the client's content test also checks every marker is on its map (`checkQuestMarkers`). Bundled for the server too.
- **State** is in the profile (format 3): `quests` maps a quest id to `{ status: 'active', progress: { [objective]: n } }` or `{ status: 'done' }`; a quest not there hasn't been accepted. `questStatus` adds `locked`, `available` and `ready` (active with everything done). Only the server changes it: `PUT /api/profile` refuses any change (`sameQuests`).
- **Server** (`server/src/quests.ts`): `POST /api/quests/:id/accept`, `/hand-over` (`objective`) and `/complete` (`page`), each with the version read and refused in a raid, like buying. `completeQuest` adds the reward items with `addToStash` (shared `stash.ts`, all or none; `buyOffer` uses it too).
- **In raids (session 14b):** an `extract` objective also has `map` and `spots` (questMarker path ids, at least one); format 1 was changed in place, since session 14 had never been committed or deployed. `checkQuests` refuses two quests extracting the same item; `checkQuestMarkers` checks spots too.
  - Setup: `raidObjectives(profile, quests, map)` lists the active quests' unfinished investigate markers and extract items on that map. The sim's `startQuests(state, map, items, holder, objectives)` (`sim/raid.ts`, after `startRaid`) adds `RaidState.investigate` (`InvestigateSpot`: holder, marker, position, `done`) and puts each quest item on the ground at a spot picked with the raid's RNG. A missing marker throws.
  - Investigating is in the sim, so co-op runs the same rule: `PlayerInput.investigate` (a press) ticks the nearest of that player's spots within `RAID.investigateReach` (2.5 m, and `extractHeight` up or down), with an `investigate` event. `investigateInReach` drives the use button; `investigatedBy` lists a player's done markers.
  - Result: `EndRaidRequest.investigated` (marker ids, at most 50). The server's `/end` runs `raidProgress(profile, quests, items, map, investigated, keptGear)` after `checkGear`: investigate objectives on the raid's map count whatever the outcome; `takeQuestItems` takes every quest item out of the kept gear (every grid, nested too) and those an active extract objective wants count. Quest routes are refused in a raid, so quests active at the end were active at the start: no snapshot is needed. The client runs `raidProgress` on copies for the results screen.
  - Client: `hud/quest-markers.ts` (one DOM element per marker, moved only when it shifts a whole pixel, the window's size read rather than the element's), `ui/raid-quests.tsx` (the Quests tab), `PlayOptions.profile` instead of `gear`. A raid snapshot saved before 14b gets an empty `investigate` list when resumed.

## Vendors and money
Session 13b. Rules in shared `vendors.ts`, content in `content/vendors.ts`. See design.md → Quests and vendors → Economy.
- **`content/vendors/<id>.json`** (format 1): `name`, optional `blurb`, and `sells`, a list of `{ item, count?, attachments? }` (count for stacks, one purchase's worth; attachments a gun comes fitted with, 2026-11-05). `checkVendors` checks the items exist, have a value, aren't money, and fit one stack, and that an offer's attachments fit its gun, one to a slot. `newStashItem` fits them (still with no rounds). Bundled for the server too.
- **Prices:** `buyPrice(items, offer)` is value × count, plus the value of any attachments it comes with; `sellPrice(items, item)` is `floor(value × VENDOR.sellShare × condition(item))` per item, plus a gun's attachments and loaded rounds, or the full value for money (`isMoney`). `cantSell` refuses a rig or backpack with anything in it and anything worth nothing.
- **`buyOffer(profile, items, vendor, index, page)`** puts a new item into copies of the stash pages (page first, then the others) and keeps them only if all of it fit; **`sellItem(profile, items, ref)`** takes an item out by a ref as the stash screen sees it (`stashGridOf` resolves the profile's grids and pages), refusing the knife. **`depositInto(profile, items)`** takes the money out of the gear's grids into the balance (capped at `PROFILE.maxMoney`).
- **Server** (`server/src/vendors.ts`): `POST /api/vendors/:id/buy` (`BuyRequest`: `version`, `offer` index, optional `page`) and `POST /api/vendors/sell` (`SellRequest`: `version`, `from`, a list of up to `MAX_SELL` (200) `ItemRef`s checked for shape; `sellItems` finds them all first and removes them by the item, not the index, all or none), each with the version read, refused in a raid, like buying a stash page. Raid ends (`/end`, and missing in action at start or `/abandon`) call `depositInto` after `keptGear`. `PUT /api/profile` also refuses `overRepaired`.
- **Client:** `StashSaver.buy` and `sell` (and `buyPage`) share `post`, which saves first and builds the body after, so it names the saved version; the stash reopens on the reply, on the page shown. `ui/vendors-page.tsx` is the vendors page; selling is `InventoryContext.sell`, set only between raids.
- **Repairs** (`sim/repair.ts`: `repairable`, `repairArmour`, `kitUsedUp`): the inventory action `{ type: 'repair', kit, armour }`. In a raid, `applyInventory` starts it as a `MedUse` with `armour` set (the kit must be in a carried grid; `ownItem` resolves your own refs), and `updateMedUse` finishes it (`finishRepair`) instead of `useMed`. `timeToUse` gives a med's or kit's use time, for the heal button's ring. `applyStash` does it at once with the kit and armour anywhere. Armour items carry `data-armour` (like `data-gun`), and the drag host's `armourZone` makes a `repair` drop zone when a kit is dragged over one.
- **Using from the inventory:** `InventoryContext.use` (a raid only) sets the next tick's `input.use`, as the heal button's picker does: a `MedRef` from **Use**, or `'cancel'` from the top bar's use pill. The raid screen redraws every 3 ticks while something is in use (otherwise every 10). Selling several is the controller's `selling` list (`startSelling`, `canPick`, `picked`); taps toggle picks and `canDrop` refuses everything meanwhile.
