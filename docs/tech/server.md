# Tech stack: Server

Part of the [tech-stack.md index](../tech-stack.md). Record decisions here, in the topic they belong to.

## Server (`packages/server`)
- **Cloudflare Workers (free plan)** with **Hono** for routing and **D1** (SQLite) for accounts, stash, vault, quest progress and vendor state.
- **Responsibilities:** accounts and sessions, profile and stash persistence, starting and ending raids (raid results go through sanity limits), vendor transactions, quest state.
- **Solo raids run entirely on the phone.** The server only sees the start and the result.
- **Co-op (later), decided 2026-10-31 (the user's call): a player's device hosts.** The host's browser runs the shared simulation (as for a solo raid) and the others connect over WebRTC data channels. The Worker only does signaling (the offer and answer, through the party) and makes short-lived TURN credentials; STUN is `stun.cloudflare.com` (free) and the relay is Cloudflare Realtime TURN (1,000 GB a month free). Phones and PC browsers mix. Replaced the earlier plan of one Durable Object per raid: the free plan's 100,000 requests a day count every incoming WebSocket message (a few raids a day), and its CPU limit for Durable Objects is unclear. Measurements and details in [coop.md](../coop.md) → Cloudflare check.
- **Free-plan limits are hard caps:** going over makes requests fail until midnight UTC. Nothing is charged.
- **Built in session 12** (`packages/server/src`): Hono routes `auth.ts` (register, login, logout, the `signedIn` middleware), `profiles.ts` (GET and PUT `/api/profile`) and `raids.ts` (POST `/api/raids`, POST `/api/raids/:id/end`). The request and reply types, `ACCOUNT` rules and `ApiErrorCode`s are in shared `protocol.ts`; an error is `{ error, message? }` with a 4xx status (`errors.ts`).
  - **D1 schema** in `packages/server/migrations/` (`accounts`, `sessions`, `profiles`, `raids`). `npm run db:migrate -w @mes/server` applies it locally; `predeploy` applies it remotely. Times are Unix milliseconds.
  - **The profile is one JSON document** (shared `profile.ts`, `PROFILE_FORMAT` with migrations like content): `money`, `stash` (pages of 10×20 since H4, 10×30 before and briefly 9×30 on 2026-11-09; `settleStash` in `parseProfile` reshapes a page saved at another size; category pages from the Stash module at the end, see tech/quests-and-vendors.md → The Hangar; that hold containers: format 2 since session 13, which migrates format 1's one grid into the first page; `PROFILE.pagePrices`, `nextPagePrice`, `buyStashPage`), `quests` (format 3 since session 14; see Quests; format 4 in session 19za only renames item ids, `ammo-556` → `ammo-762x39` and `mag-556-45` → `mag-762x39-45`, in grids and fitted attachments; format 5 (2026-11-05) renames reshaped rounds the same way, `ammo-45acp-match` → `ammo-45acp`, `ammo-762x54r-t46m` → `ammo-762x54r-hpbt`, now also in a gun's `loaded`; format 6 renames `pistol` → `m9a3` and takes off any optic on one, since the M9A3 has no optic slot; format 7 renames `sniper-rifle` → `sv-98` and drops its `loaded`, as the SV-98 fires 7.62×54R; format 8 adds `vendors`; format 9 (2026-11-09) renames `assault-rifle` → `akm`, `shotgun` → `mp-133`, `smg` → `k10`) and `gear` (the sim's `Gear`, vault and knife included). It's always read and written whole, with a **version** that goes up on every write; writes are `UPDATE … WHERE version = ?`, and a batch's other statements check the same version, so two devices can't interleave (the loser gets `stale`). `checkProfile`/`checkGear` are the sanity limits (design.md → Trust model), `itemGained` the "no items from nothing" rule, `restGear` puts guns down before storing. New accounts get `newProfile` from `content/starting-kits/new-player.json` (a new content kind, format 1) plus the knife.
  - **Raids:** a row per raid, at most one open per account (a partial unique index). `PUT /api/profile` refuses a change in the number of stash pages; `POST /api/stash/pages` (`stashRoute` in `profiles.ts`, with the version read, like PUT) buys the next one. Since session 13, `POST /api/raids/:id/abandon` ends an open raid as missing in action without starting another (the game opening on the menu calls it); for a raid already ended it replies with the profile. Start: an open raid is ended as `mia` (gear → `keptGear(gear, false)`), the new row inserted and the profile bumped, in one batch. End: the gear sent is cut down by `keptGear` (shared `raid.ts`, the knife falling back to the profile's), checked, and stored; the request is stored as `result`, and the same request again replies with the profile (a retry whose reply was lost), anything else `raid-over`.
  - **Accounts:** usernames 3–20 of `A–Z a–z 0–9 _ -`, unique ignoring case; passwords 8–200 characters. **PBKDF2-SHA256 with 50,000 iterations** and a 16-byte salt, stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>`: 100k measured 12 ms on the Mac, over the free plan's **10 ms CPU** per request, 50k about 6 ms. The count is per hash, so it can go up later. Ten wrong passwords in a row lock the account for 5 minutes. **Sessions:** a random 32-byte token in an HttpOnly, `SameSite=Lax` cookie on `/api` (Secure over HTTPS only, so plain-http dev on the LAN still works), stored as its SHA-256, for 180 days, extended when past half.
  - **Party raids (co-op C4–C5, 2026-10-31):** devices connect over WebRTC (`net/peer.ts`, `net/coop-link.ts`), with offers and answers through `/api/party/signal` and `/api/party/signals`, and STUN/TURN from `/api/party/ice`. The host's device runs the raid (`play/coop.ts`) and sends each tick's state patch (shared `net/sync.ts`); guests apply it in place and send inputs. Details and measurements in [coop.md](../coop.md).
  - **Friends, presence and the party (co-op C1–C3, 2026-10-31):** `social.ts` serves `/api/friends`, `/api/party` and `/api/presence` (types and `SOCIAL` limits in shared `protocol.ts`), over migration `0003_social.sql`. The menu's `PartyWatch` (client `social.ts`) posts a heartbeat every 10 s with the device kind and gets the party and invites back; invite links are `/join/<code>`, read by `main.ts` and joined on the menu. Details in [coop.md](../coop.md).
  - **Wiping accounts (2026-11-05):** `npm run wipe` (`scripts/wipe-accounts.mjs`, SQL from `packages/server/src/wipe.ts`) is a local script over `wrangler d1 execute`, not an admin route, so the live Worker has nothing to attack. Wiped accounts get `newProfile` with the version bumped, never reset (a device holding the old profile gets `stale`). Open raids are closed with outcome `wiped` rather than deleted, so a late result gets `raid-over` and can't put old gear back. A party raid just started is called off. The statements go through `--file` because wrangler's import is all-or-nothing, which leaves no gap for a raid to start between them. Logins, friends, parties, settings and raid history stay. It's a dry run without `--apply`.
  - **Content on the server:** wrangler can't glob like Vite, so `scripts/bundle-content.mjs` writes the items, raids, starting kits and vendors (13b) into `src/generated/content.js` (gitignored), run before the server's dev, deploy, typecheck and tests. While the server runs in dev, `scripts/dev-server.mjs` watches `content/` and rebuilds the bundle on every save, because a stale bundle fails raid ends on items it doesn't know (decided 2026-11-04). `loadById` (moved from the client into shared `content/format.ts`) loads them.
  - **Pages open across a deploy (2026-11-10):** the assets' single-page fallback answers a missing old chunk with index.html, so a lazy import fails ("text/html is not a valid JavaScript MIME type": Settings while spectating in co-op). The client reloads once on `vite:preloadError` (`app/stale-build.ts`, not again within 30 s), and a raid fetches the screens it opens later (inventory, settings, results) as it starts, so a deploy mid-raid doesn't break them.
  - **Tests** run the Hono app in Node against a small D1 stand-in over `node:sqlite` (`src/test/d1.ts`), built from the migrations. `@types/node` isn't installed (its globals clash with workers-types); `src/test/node.d.ts` declares the few Node APIs used.
